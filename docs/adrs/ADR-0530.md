# ADR-0530: Schema Migrations Run at Startup (Boot 4 Modular Flyway Autoconfig) + Schema Observability

**Status:** Accepted
**Date:** 2026-06-29
**Depends on:** ADR-0520 (Boot 4.1.x migration surface)
**Deciders:** Principal Engineering

---

## Context

A Kafka E2E test boot surfaced `ERROR: relation "outbox" does not exist` from the Execution Service's
scheduled outbox poller. A focused diagnostic (`FlywaySchemaMigrationIT`) confirmed it: **neither
service was migrating its own schema at startup.** The schema only ever existed in tests because the
IT bases (`ExecPostgresIT`, `CpPostgresIT`) run Flyway *programmatically*. The full-context smoke
tests (`ExecutionServiceContextIT`, `ControlPlaneContextIT`) only assert bean wiring, so they stayed
green while the app's own migrations never ran — a latent **production** defect: a fresh deploy would
come up against an empty schema and every DB path would fail.

### Root cause — a Spring Boot 4 breaking change

Spring Boot 4 **extracted per-technology autoconfiguration out of the monolithic
`spring-boot-autoconfigure` into dedicated `spring-boot-<tech>` modules.** `FlywayAutoConfiguration`
now lives in `org.springframework.boot:spring-boot-flyway`, **not** in `spring-boot-autoconfigure`.

Under Boot 3, putting `org.flywaydb:flyway-core` on the classpath was enough — the aggregated
autoconfigure module carried the Flyway integration. Under Boot 4 that is no longer true: with only
`flyway-core` present, **no `FlywayMigrationInitializer` bean is created and migrations never run.**
The tell in the logs was the datasource initializing *lazily on a scheduler thread* rather than
eagerly by Flyway during context refresh.

Both services depended on bare `flyway-core` (+ `flyway-database-postgresql`). Both were affected.

---

## Decision

### 1. Restore startup migration via the Boot starter

Replace bare `flyway-core` with **`org.springframework.boot:spring-boot-starter-flyway`** in both
services. The starter pulls `spring-boot-flyway` (the autoconfig module) + `flyway-core`;
`flyway-database-postgresql` stays explicit for the PG dialect. Versions remain BOM-managed (no
explicit pins — consistent with the other `spring-boot-starter-*` deps).

Boot then runs migrations during context refresh and **fails fast**: a bad or checksum-mismatched
migration aborts startup, so a service never begins serving on a broken schema. Config makes the
posture explicit:

```yaml
spring.flyway:
  enabled: true
  locations: classpath:db/migration
  clean-disabled: true       # `flyway clean` can never wipe the schema
  validate-on-migrate: true  # checksum-validate applied migrations on every boot
```

### 2. Make the schema state observable

A per-service `FlywaySchemaObservability` `@Configuration` snapshots Flyway state once on
`ApplicationReadyEvent` (no per-scrape DB hit on `flyway_schema_history`) and exposes three
low-cardinality Prometheus gauges (no `tenant_id`):

| Metric | Meaning | Alert |
|---|---|---|
| `db.schema.version` | latest applied version as a number (-1 if none/non-numeric) | drift across replicas |
| `db.schema.migrations.applied` | count of successfully applied migrations | — |
| `db.schema.migrations.pending` | count of pending migrations | **non-zero ⇒ a replica is behind its migrations** |

Plus one authoritative startup log line: `schema migration ready: current_version=… applied=… pending=…`.
Fail-fast is the *safety* net; these gauges + log are the *visibility* net (a replica that started on
a stale jar reports a lower `db.schema.version` than its peers).

### 3. Regression guards

`FlywaySchemaMigrationIT` (exec) and `CpFlywaySchemaMigrationIT` (CP) boot the real context and assert
the expected tables exist, `flyway_schema_history` shows applied migrations, and the gauges are
populated with zero pending. These fail loudly if the autoconfig module is ever dropped again —
unlike the wiring-only context tests that masked the original defect.

---

## Consequences

- Fresh deploys of either service now provision their own schema; the scheduled poller/sweep no longer
  error on a missing table.
- Migration failure is a startup failure (fail-fast), not a silent half-broken runtime.
- Schema version and migration backlog are first-class Prometheus signals.
- `ExecutionServiceContextIT` / `ControlPlaneContextIT` now genuinely exercise Flyway (they previously
  did not), at no extra cost.

---

## Residual Risks (explicit)

1. **Shared version sequence across two schemas is fragile.** CP owns `V1,V2,V3,V7,V8`; Exec owns
   `V4,V5,V6,V7`. They are separate databases so there is no collision, but the numbering is
   non-contiguous *per service* (CP skips V4–V6) and **reuses V7 for different content**. Flyway
   tolerates the gaps by default, but a new migration must pick the next number **for its own
   service**, not globally — a foot-gun. A cleaner future state is per-service version prefixes or
   separate history tables.
2. **Fail-fast is relied upon, not independently tested.** We did not add a deliberately-broken
   migration test. Boot's default behavior (initializer throws → context fails) is well-established,
   but the guarantee is by-convention here.
3. **`db.schema.version` is numeric-only.** Semantic (`1.2`) or timestamp versions map to `-1`; our
   integer versions are fine. The startup log always carries the true version string.
4. **Observability is a startup snapshot.** An out-of-band `flyway migrate`/`repair` against a live DB
   is not reflected until restart. Acceptable — migrations are deploy-time events, not runtime.
5. **No `baseline-on-migrate`.** Adopting these services against a *pre-existing*, non-empty database
   without a `flyway_schema_history` would fail until a baseline is set. Greenfield/lab is unaffected;
   document before any brownfield adoption.

---

## Options Considered and Rejected

| Option | Rejection reason |
|---|---|
| Keep bare `flyway-core`, add a manual `Flyway` `@Bean` + `migrate()` call | Re-implements what the starter's autoconfig does correctly (datasource wiring, init ordering, actuator endpoint, health); brittle. |
| Run migrations out-of-band (CI/CD step, not the app) | Valid at scale, but splits schema ownership from the service and needs orchestration the lab does not have; the app-managed model is the project's current posture. |
| Shared `FlywaySchemaObservability` in `chaosforge-common` | `chaosforge-common` is deliberately Spring-free ("No Spring application context here"); a `@Configuration` there also would not be component-scanned. Per-service is consistent with the "independent surfaces / kept local" precedent (e.g. the mirrored outbox pollers). |
