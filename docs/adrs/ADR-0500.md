## Context

ChaosForge's Edge Gateway is the single external-facing surface. Its responsibilities are: JWT extraction and tenant-context propagation, Redis token-bucket rate limiting per tenant, rule-set lookup for applied policies, and WebClient fan-out to the Control Plane. The gateway is I/O-bound end-to-end — it does not perform CPU-intensive work, has no transactional JDBC requirement, and has no use for per-request thread affinity.

The question is whether the reactive opt-in criteria are met sufficiently to justify WebFlux over MVC + virtual threads.

---

## Decision

The Edge Gateway uses **Spring WebFlux + Reactor + Netty**. It is the **only** ChaosForge service that does. The Control Plane and Execution Service remain imperative MVC + virtual threads.

Reactive opt-in criteria met:
1. **Sustained fan-out concurrency** — each gateway request fans out to the Control Plane and may aggregate multiple rule-set lookups concurrently.
2. **Streaming semantics** — SSE telemetry endpoint; WebFlux `Flux<ServerSentEvent>` is the natural fit; MVC + VT would require async emitter plumbing with no benefit.
3. **Reactive-native integration boundary** — Lettuce reactive Redis for rate limiting; reactive `WebClient` to Control Plane. Running reactive Lettuce from a VT-backed MVC thread parks the VT on the round-trip wait, eliminating the non-blocking advantage.

---

## Alternatives

**MVC + virtual threads (same as CP + Exec):** VTs are cheap but park on I/O waits. The gateway's hot path is almost entirely I/O — the savings from VT scheduling are real but non-blocking Netty is structurally superior for sustained fan-out. Also: SSE streaming is awkward on MVC. Rejected.

**WebFlux everywhere (all three services):** The Control Plane has transactional JDBC (Postgres advisory lock + outbox in one transaction). R2DBC does not support advisory locks; switching would require redesigning the replay mutex. Rejected — see ADR-0502.

---

## Consequences

**Positive:**
- Netty event loop handles sustained fan-out with fixed thread count.
- SSE streaming via `Flux<ServerSentEvent>` is idiomatic and requires no special wiring.
- Reactive Lettuce + WebClient compose naturally in one pipeline.

**Negative:**
- `.block()` is forbidden anywhere in the gateway chain — enforced by CI lint. Any developer adding a blocking call (e.g., `RestTemplate`, synchronous JDBC) produces a silent deadlock under load, not a visible error.
- `@Transactional` cannot be used in the gateway — all state mutation must go via WebClient to the Control Plane.
- Mixed reactive + imperative in the same codebase increases cognitive load. Mitigated by physical service boundaries.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| `.block()` introduced in gateway chain | CI lint (`grep -r ".block()" edge-gateway/src`) | Hard fail in `./gradlew check` (build is Gradle — ADR-0516 Deviation 7; "Maven verify" here was drift) |
| Lettuce pool exhaustion | `lettuce.pool.pending > 0` sustained | `GenericObjectPoolConfig` maxTotal + maxWait; Micrometer alert |
| WebClient connection pool saturation to CP | `http.client.requests` p99 spike | Resilience4j CB on WebClient; bulkhead limits concurrent outbound |

---

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| SSE is a gateway responsibility | ACCEPTED | If SSE moves to CP, WebFlux justification weakens |
| Reactive Lettuce is faster than blocking Lettuce on a VT | INFERRED | Lab benchmark with equivalent load; if delta is <5% at target RPS, MVC+VT is viable |

---

## Implementation Notes

- `spring-boot-starter-webflux` on `edge-gateway` module only.
- CI: `./gradlew :edge-gateway:check` must include an ArchUnit rule asserting no `block()` calls in `src/main`.
- `Schedulers.boundedElastic()` is permitted only with an inline comment explaining the blocking operation and why it cannot be eliminated.
