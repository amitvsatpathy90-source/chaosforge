# ADR-0532 — Tenant Trust on the CP `/internal` Path Is Peer-Asserted, Not JWT-Bound

| Field | Value |
|---|---|

| **Status** | ACCEPTED — cert-subject restriction implemented; service-JWT remains optional |
| **Date** | 2026-07-02 |

| **Depends on** | ADR-0524 (JWT re-verified at CP/Exec; `X-Tenant-Id` not trusted), ADR-0509/0510 (three-layer tenant isolation; cross-tenant → 404), ADR-0531 (intra-service mTLS) |

---

## Context

An architecture audit (arch-audit finding 2.1) surfaced a gap between the stated invariant and the code.

architecture specification's Runtime Surface table asserted CP *"accepts inbound only with valid client cert (mTLS)
**and** re-verified JWT."* That is true for the public `/v1` surface but **false for `/internal/**`**:

- `control-plane` `SecurityConfig` sets `.requestMatchers("/internal/**").permitAll()`, and
  `JwtTenantExtractionFilter.shouldNotFilter` returns `true` for `/internal/`. So CP performs **no JWT
  verification** on that path.
- `InternalRuleSetController` (`GET /internal/rule-sets/{ruleSetId}/versions/{version}?tenantId=…`)
  scopes the read by a **caller-supplied `@RequestParam UUID tenantId`**.

The result: on `/internal`, CP derives the authoritative tenant from an **unauthenticated query
parameter** — exactly the "trust a value asserted over an authenticated channel" pattern
`mTLS security policy` forbids. mTLS proves *"a holder of an internal-CA cert is calling,"* **not** *"this is
tenant X's request."*

### Why the value is not JWT-bound here

This path exists for the Execution Service's rule-set loader, whose triggering context is the **Kafka
consumer** — which carries **no HTTP user JWT**. The authoritative tenant on the Kafka path is the
**signed Avro `tenantId`**, verified at pipeline step 1. But that signature does **not survive** the
subsequent HTTP hop to CP: by the time exec calls `/internal/rule-sets?tenantId=X`, the cryptographic
binding is gone and `X` is a bare, peer-asserted UUID.

### Threat

The Edge Gateway holds a valid internal-CA client cert (it needs one for its mTLS calls to CP). A
gateway bug (fan-out/tenant mix-up) or a compromised gateway can open an mTLS channel to CP and issue
`GET /internal/rule-sets/{anyRuleSetId}/versions/{v}?tenantId={arbitrary}`. CP's ownership check is
driven by the attacker-chosen `tenantId`, so **Layer-3 `findByIdAndTenantId` does not protect** — it
filters on the attacker's input. Impact is **cross-tenant confidentiality** (rule-set / scenario-logic
disclosure), not integrity. The Execution Service does **not** share this gap: its `SecurityConfig`
uses `anyRequest().authenticated()`, so its `/internal` (e.g. the kill switch) *is* JWT-authenticated.
The CP/Exec asymmetry is the evidence this is an oversight, not a considered trade-off.

---

## Decision

1. **Name the trust model honestly.** The tenant on the CP `/internal` HTTP path is **peer-asserted**:
   its integrity rests entirely on (a) the mTLS peer being trustworthy and (b) that peer having itself
   verified the tenant (exec, via the signed Avro value). architecture specification and `mTLS security policy` are corrected to
   state this rather than claim JWT binding.

2. **Narrow the trusted peer set (IMPLEMENTED).** `permitAll()` on `/internal` trusted *any* internal-CA
   cert, which includes the gateway. `InternalMtlsSecurityConfig` now adds an `@Order(1)` X.509 filter
   chain scoped to `/internal/**` that authorizes only the client cert whose CN equals
   `chaosforge.mtls.internal-peer-cn` (the exec subject; `SubjectX500PrincipalExtractor` → a
   `UserDetailsService` granting `ROLE_INTERNAL_PEER` only for that CN). A gateway cert — a valid internal
   peer — is rejected **403**. The chain is registered only when the property is set (the `mtls` profile
   sets it in `application-mtls.yml`); absent it, dev/tests keep `/internal` on the main chain's
   `permitAll`. This shrinks the blast radius to "exec is compromised," already the trust root for the
   Kafka path. Proven by `InternalMtlsAuthorizationIT` (exec cert → 200, gateway cert → 403, no cert → 403).

3. **Preferred longer-term fix (still optional).** Have exec present a **service JWT** (client-credentials,
   `sub=execution-service`) on the CP call and have CP authenticate it, so `/internal` stops being
   `permitAll` entirely. The tenant scoping stays peer-asserted (unavoidable — no user JWT exists on the
   Kafka path), but the *caller* becomes cryptographically identified via a token rather than a cert
   subject. Not needed now that (2) restricts the cert subject; revisit if internal callers multiply.

**Caveat on (2):** `internal-peer-cn` must equal the CN in the exec client cert. The default
(`execution-service`) follows the ADR-0531 alias convention; if `docker/mtls/generate-certs.sh` mints a
different subject DN, override `MTLS_INTERNAL_PEER_CN` to match, or the exec call is rejected 403.

---

## Consequences

**Positive** — the real trust boundary is documented, not misrepresented; under the `mtls` profile the
`/internal` surface is now restricted to the exec cert subject, so a gateway (or any non-exec internal
cert) can no longer read a tenant's rule-set by supplying an arbitrary `tenantId`.

**Negative / residual (explicit):** (a) the tenant on `/internal` is still peer-asserted — a compromised
**exec** cert holder could still pass an arbitrary `tenantId` (blast radius reduced from "any internal
cert" to "exec's cert"); (b) the CN allowlist is a single configured value — cert rotation to a new
subject DN needs the property updated in lockstep; (c) the restriction is profile-gated, so a non-`mtls`
deployment (should not exist outside the lab) leaves `/internal` on `permitAll`. Mitigating factor
throughout: rule-sets are pinned `(id, version)` scenario definitions — confidentiality, not integrity or
replay safety — and the mutation surface remains JWT-gated on `/v1`.

---

## Alternatives Considered

| Option | Rejected because |
|---|---|
| Leave `permitAll` + doc it as "fine, mTLS-only" | mTLS authenticates the process, not the tenant value; the audit shows the concrete cross-tenant read. Not fine. |
| Forward the user JWT to `/internal` | The Kafka-triggered path has no user JWT to forward. Impossible for the primary caller. |
| Sign the tenant into an internal header exec re-attaches | Reinvents JWT/mTLS with a bespoke MAC; more surface, no gain over a service JWT (item 3). |
| Drop the `tenantId` param, scope by cert subject | Cert subject is the *service*, not the *tenant*; exec serves all tenants over one cert. Cannot scope tenant from the cert alone. |
