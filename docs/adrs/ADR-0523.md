# ADR-0523 — Execution Transaction Decomposition: Short Claim-Tx + Stateless Step Execution + Short Result-Tx

| Field | Value |
|---|---|

## Context

The Execution Service `@KafkaListener` must perform, in order: fencing check, inbox dedup, step execution (outbound HTTP to tenant targets, bounded at 4 minutes by `max.poll.interval.ms`), and outbox emission of the result event. The naive implementation wraps all of these in a single `@Transactional` method. This is correct for a single-step scenario but breaks under any real concurrency.

### The problem with a single long transaction

The `@KafkaListener` method on a virtual-thread consumer parks the virtual thread during outbound HTTP calls. A JDBC connection from the bounded pool is held open for the duration — potentially 4 minutes. Under concurrent scenario execution:

- `pool_size` concurrent long-running scenarios exhaust the JDBC pool.
- Remaining Kafka poll loop iterations block trying to acquire a connection.
- `max.poll.interval.ms` is exceeded; Kafka triggers a rebalance.
- The rebalanced consumer picks up the in-progress partition; it cannot find an open inbox row (the prior tx is still uncommitted), re-executes from the top, and the step runs twice.

Additionally:

- The `SELECT … FOR UPDATE` on `inbox_fence` (durable fencing) holds a row lock for the full 4-minute execution window. Any competing message for the same `(tenant_id, scenario_id)` key blocks.
- Postgres `xmin` horizon advances slowly; autovacuum cannot reclaim dead tuples on the `inbox_fence` and `message_inbox` tables during long-running txs.
- The attributed safety guarantee — "inbox dedup ensures no duplicate effects on rebalance" — is wrong at the message level. `message_id` dedup catches Kafka redeliveries of the same outbox row; it does not catch a partial execution where some steps succeeded before the crash. What actually provides safety is **step-level idempotency**: `Idempotency-Key = scenario_id:replay_version:step_id` on outbound HTTP, and `scenario_run_log` PK `(scenario_id, replay_version, step_id)` preventing duplicate run-log inserts.

---

## Decision

Decompose the Execution Service processing into three phases, each with its own bounded transaction:

### Phase 1 — Claim (short tx, milliseconds)

```java
@Transactional(propagation = REQUIRED, timeout = 5)
ClaimResult claim(ScenarioRunCommand cmd, long incomingVersion) {
    // 1. Fencing check + max_seen advance (FOR UPDATE on inbox_fence row)
    long maxSeen = fenceRepo.getAndLockMaxSeen(cmd.scenarioId());  // SELECT … FOR UPDATE
    if (incomingVersion < maxSeen) {
        return ClaimResult.stale(incomingVersion, maxSeen);
    }
    fenceRepo.advanceMaxSeen(cmd.scenarioId(), incomingVersion);   // UPDATE max_seen

    // 2. Inbox dedup (same tx — catches Kafka redelivery of same outbox row)
    boolean inserted = inboxRepo.insertIfAbsent(cmd.messageId(), cmd.tenantId(), cmd.scenarioId());
    if (!inserted) {
        return ClaimResult.duplicate(cmd.messageId());
    }

    // 3. Mark scenario as IN_PROGRESS in run_log
    runLogRepo.insertRunHeader(cmd.scenarioId(), incomingVersion, Instant.now());

    return ClaimResult.proceed(cmd);
}
// tx commits here — JDBC connection released; FOR UPDATE row lock released
```

### Phase 2 — Execute (no DB tx, up to 4 minutes)

```java
// No @Transactional. JDBC connection NOT held.
ExecutionResult execute(ClaimResult claim) {
    ScenarioRunCommand cmd = claim.command();
    RuleRef rules = ruleSetRepo.loadPinned(cmd.ruleSetId(), cmd.ruleSetVersion()); // short read-only query; own connection

    List<StepResult> results = new ArrayList<>();
    for (Step step : cmd.steps()) {
        // Step idempotency: stable key across retries and across partial re-execution
        String idempotencyKey = cmd.scenarioId() + ":" + cmd.replayVersion() + ":" + step.id();

        // Check run_log: if step already completed (e.g. prior partial execution), skip
        if (runLogRepo.isStepCompleted(cmd.scenarioId(), cmd.replayVersion(), step.id())) {
            results.add(StepResult.alreadyCompleted(step.id()));
            continue;
        }

        StepResult result = resilience4jExecutor.execute(
            idempotencyKey, step, rules,
            () -> targetClient.call(step.targetUrl(), step.method(), step.faultConfig())
        );

        // Persist step result immediately (short own tx per step)
        runLogRepo.recordStep(cmd.scenarioId(), cmd.replayVersion(), step.id(), result);
        results.add(result);

        if (result.isTerminalFailure()) break;
    }
    return ExecutionResult.of(cmd, results);
}
```

### Phase 3 — Finalize (short tx, milliseconds)

```java
@Transactional(propagation = REQUIRED, timeout = 5)
void finalize(ExecutionResult result) {
    // Emit result event via outbox (same tx as run-log finalization)
    outboxRepo.insert(buildResultEvent(result));
    runLogRepo.finalizeRun(result.scenarioId(), result.replayVersion(),
                           result.outcome(), Instant.now());
}
// tx commits — outbox poller delivers the result event
```

### Ack contract

Manual ack fires **after Phase 3 commits**:

```java
@KafkaListener(...)
void onCommand(ConsumerRecord<String, byte[]> record, Acknowledgment ack) {
    ScenarioRunCommand cmd = deserialize(record);
    long version = parseVersion(record.headers());

    // Schema check + tenant JWT re-verification (no tx)
    validate(cmd, record.headers());

    ClaimResult claim = claim(cmd, version);   // Phase 1 — short tx
    if (!claim.shouldProceed()) {
        ack.acknowledge();   // stale or duplicate — ack without executing
        return;
    }

    ExecutionResult result = execute(claim);   // Phase 2 — no tx

    finalize(result);                          // Phase 3 — short tx

    ack.acknowledge();                         // post-commit ack
}
```

If the process crashes between Phase 2 (steps executed) and Phase 3 (outbox insert), the consumer rebalances, re-delivers the same Kafka record, Phase 1 finds the inbox row already present (conflict → duplicate → ack-and-skip), and Phase 2's step-level idempotency means any steps that already ran are skipped via `runLogRepo.isStepCompleted`. No double-execution.

## Alternatives Considered

### 1. Single long `@Transactional` wrapping all phases (prior implicit design)

**Rejected** per the problem statement: exhausts JDBC pool under concurrency, holds `FOR UPDATE` locks for minutes, rebalance-triggered re-execution bypasses inbox dedup (new Kafka record = new `message_id` = new outbox row), stale safety attribution.

### 2. Single long tx but with a dedicated long-tx JDBC pool

Increases pool size to match max concurrent scenarios. Still holds `FOR UPDATE` lock for 4 minutes, still blocks autovacuum, still attributes safety incorrectly. Masks the problem at operational cost.

### 3. Step execution via a separate thread pool (not virtual threads)

Unnecessary. Virtual threads park cheaply during I/O; the problem is the DB connection being held, not the thread. Decomposing the transaction, not the threading model, is the fix.

## Consequences

### Positive

- JDBC pool connections are held for milliseconds, not minutes. Pool size can be small (10–20 connections for the lab).
- `FOR UPDATE` row lock on `inbox_fence` is held for milliseconds. Competing messages for the same scenario process without blocking.
- Autovacuum can clean `inbox_fence` and `message_inbox` rows normally.
- Safety attribution is correct: step-level idempotency (`Idempotency-Key` + `run_log` PK) is the correctness primitive for partial re-execution; message-level inbox dedup handles Kafka redeliveries. These are disjoint failure classes; the decomposition makes both explicit.
- `@KafkaListener` can return (and ack) promptly if Phase 1 fast-fails (stale or duplicate).

### Negative

- Phase 2 crash leaves the run in an indeterminate state until the Kafka message is redelivered and Phase 1 fast-fails (duplicate → ack-and-skip). The run-log finalizer (Phase 3) never fires for a Phase 2 crash. **Mitigation:** a background sweep job marks runs that have no `finalizeRun` entry after `max.poll.interval.ms + buffer` as `INCOMPLETE`; the tenant is notified.
- Per-step `runLogRepo.recordStep` short transactions add N small DB writes per scenario. Acceptable for the lab's orchestration workload; not a concern until per-step latency becomes meaningful.
- More code complexity: three methods instead of one. Mitigated by the clarity of phase boundaries.

## Failure Modes

| Failure | Phase | Detection | Outcome |
|---|---|---|---|
| Process crash before Phase 1 commits | 1 | Kafka redelivers; Phase 1 re-runs cleanly | Safe — no partial state |
| Process crash after Phase 1 commits, before Phase 2 starts | Between 1 and 2 | Kafka redelivers; Phase 1 finds inbox row → duplicate → ack-and-skip | Safe — no step executed |
| Process crash mid-Phase 2 (K steps of N completed) | 2 | Kafka redelivers; Phase 1 → duplicate → ack-and-skip; completed steps skipped via `isStepCompleted` | Safe — idempotency handles it |
| Process crash after Phase 2, before Phase 3 commits | Between 2 and 3 | Kafka redelivers; Phase 1 → duplicate → ack-and-skip; background sweep marks run INCOMPLETE | Operationally visible; result event not emitted; tenant notified |
| Phase 3 commit fails (DB down) | 3 | Kafka not acked; redelivered; Phase 1 → duplicate → ack-and-skip | Result event not emitted — same as prior case |
| Kafka rebalance during Phase 2 | 2 | `max.poll.interval.ms` exceeded; rebalance triggers; new consumer Phase 1 → duplicate → ack-and-skip | Safe — Phase 2 idempotency handles remaining steps if any; or sweep marks INCOMPLETE |

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| `runLogRepo.isStepCompleted` check adds acceptable latency per step | ASSUMED | If step count N is large (>100) and each DB check is >5ms, Phase 2 adds >500ms overhead. Mitigation: batch-load all completed step IDs at Phase 2 start. |
| Per-step short txs are durable (not batched) | REQUIRED | Batching step inserts would lose progress if the batch tx rolls back. Each step's `recordStep` must commit before issuing the next outbound call. |
| Background sweep correctly identifies INCOMPLETE runs | ASSUMED | Sweep window = `max.poll.interval.ms + grace`. If grace is too short, runs in-progress get incorrectly marked. Tune conservatively. |

## Implementation Notes

- The `inbox_fence` table (`scenario_id`, `max_seen`, `tenant_id`) is the durable fencing state. Phase 1 uses `SELECT … FOR UPDATE` on this row — the short tx releases the lock in milliseconds.
- `scenario_run_log` PK is `(scenario_id, replay_version, step_id)`. `INSERT … ON CONFLICT DO NOTHING` on `recordStep` is the step idempotency primitive.
- The execution rules file `Execution Service architecture rules` must be updated to forbid the `@Transactional` annotation on the `@KafkaListener` method itself.
- `aggregate timeout < max.poll.interval.ms` constraint (already in `architecture specification`) enforces Phase 2's ceiling: if the Resilience4j aggregate timeout fires, Phase 2 returns a `TIMEOUT` result; Phase 3 emits a `ScenarioTimedOut` event and finalizes.
