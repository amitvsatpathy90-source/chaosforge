# ADR-0501 — Three-Service Split: Gateway, Control Plane, Execution Service

**Status:** ACCEPTED
**Date:** 2026-05-20
**Reversal cost:** HIGH
**Owner:** Principal Engineering

---

## Context

ChaosForge could be built as a monolith or as multiple services. The portfolio objective is to demonstrate specific patterns at real architectural seams — not in monolithic plumbing. Each service boundary must teach something distinct and defensible.

---

## Decision

ChaosForge is split into **three services**:

| Service | Runtime | Primary responsibility |
|---|---|---|
| Edge Gateway | WebFlux + Netty | JWT auth, rate limiting, rule-set application, fan-out |
| Control Plane | MVC + virtual threads | Tenant/Scenario/RuleSet CRUD, replay orchestration, outbox relay |
| Execution Service | MVC + virtual threads + Kafka | Fault injection execution, inbox dedup, fencing, step emission |

Each boundary is load-bearing for a portfolio claim:
- **Gateway ↔ CP:** reactive↔imperative interop; demonstrates reactive opt-in criteria are applied per-case.
- **CP ↔ Execution:** outbox + Kafka + inbox; demonstrates publish-side atomicity (claim 2).
- **Execution ↔ target:** Resilience4j + fencing token on every outbound call; demonstrates claim 3.

---

## Alternatives

**Monolith:** Eliminates inter-service latency and operational surface. But collapses the Kafka/outbox/inbox boundary into in-process calls, and collapses the reactive↔imperative boundary into a single process. Both are the portfolio's load-bearing claims — a monolith makes them undemonstrable at a seam. Rejected.

**Two services (Gateway + Backend):** Merging CP and Execution Service eliminates the Kafka boundary. The Execution consumer becomes in-process; the outbox becomes unnecessary; the inbox dedup becomes redundant. The Kafka/outbox/inbox claim disappears. Rejected.

**Four or more services (e.g., split rule-set management):** Adds operational surface with no additional portfolio signal. Scope creep. Rejected.

---

## Consequences

**Positive:**
- Each claim is demonstrable at a real boundary, not inferred from in-process code.
- Services can have different runtimes justified by their responsibility (ADR-0500).
- Physical service boundaries enforce the "no reactive in CP/Exec" rule structurally.

**Negative:**
- Three services = three Compose entries, three Spring Boot apps, three sets of Flyway migrations, three actuator endpoints. Operational surface is proportional.
- Inter-service latency: Gateway→CP is an HTTP hop. Acceptable for the portfolio context.
- Cross-service DB schemas must never be shared (`chaosforge_cp` ≠ `chaosforge_exec`). Shared schema would collapse the service boundary's isolation guarantee.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| CP and Exec share a DB schema | Integration test asserting separate datasource URLs | Separate `DataSource` beans; separate Flyway configs |
| Gateway calls Exec directly (bypassing CP) | ArchUnit rule: no `execution-service` URL in `edge-gateway` config | Enforced at config + code level |

---

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| Three services are independently deployable | ACCEPTED | Each has its own `build.gradle.kts`, Dockerfile, and Spring Boot main class |
| Kafka boundary between CP and Exec is meaningful | INFERRED | If CP and Exec are always co-located, the Kafka boundary teaches less; still correct but weaker demo |

---

## Implementation Notes

- Gradle multi-module: `edge-gateway`, `control-plane`, `execution-service`, `chaosforge-common`, `chaosforge-avro-schemas`.
- `chaosforge-common` contains shared header/topic constants, the DLQ reason enum, and base exceptions across services — no Spring beans.
