# ADR-0541 — Deployment Security Posture: Startup Assertion of the Controls, Not the Profile

**Status:** ACCEPTED — implemented (guard in all three services, alert rule + promtool tests)
**Date:** 2026-07-17
**Reversal cost:** LOW (additive startup validation + one gauge; no schema, no wire contract, no data)
**Depends on:** ADR-0531 (profile-gated intra-service mTLS), ADR-0532 (`/internal` peer-asserted tenant), ADR-0534 (SSRF blast-radius containment)
**Owner:** Principal Engineering

---

## Context

ADR-0531 gated intra-service mTLS behind the `mtls` Spring profile so dev/tests could run on plain
HTTP. ADR-0532 and ADR-0534 then attached two further controls to that same profile. The result was
never recorded as a decision: **three independent security controls collapsed onto one flag**, with
no assertion that the flag was set.

Omitting `--spring.profiles.active=mtls` starts a service with:

- plain HTTP and no client cert required (`server.ssl.*` unset);
- `/internal` falling back to `permitAll` — `InternalMtlsSecurityConfig` is
  `@ConditionalOnProperty(chaosforge.mtls.internal-peer-cn)`, and that path's `tenantId` is
  **peer-asserted** (ADR-0532), so any reachable caller reads **any tenant's** rule-set;
- `TargetUrlGuard` inert — with `block-private-networks=false` and an empty allowlist, `validate()`
  falls through and checks nothing past scheme/host (ADR-0534), on the service that actually fires
  outbound HTTP at tenant-supplied targets;
- `chaosforge.control-plane.base-url` still at its `http://` default, putting the forwarded tenant JWT
  on the wire in the clear (`mtls-rules.md` requires it reach the CP intact for re-verification).

The mTLS keystore passwords fail fast on a missing env var — but only once the profile is already
active, which is the one condition that fails. The 2026-07-17 architecture audit (F2) found the
omission mode **silent and total**: no exception, no log, no metric distinguished it from a healthy
start. This ADR records the containment decision and, deliberately, the limits of what a startup
assertion can achieve.

## Decision

Each service asserts **its own security controls by property** at context refresh: with
`chaosforge.deployment=deployed`, a missing control throws from a `@Configuration` bean constructor,
failing refresh before the listener binds. Because that assertion is conditional on a marker that can
itself be forgotten, every service **also** emits `chaosforge.security.hardened` (1/0) unconditionally,
alerted by `SecurityPostureNotHardened` on `env!="lab"`.

## Alternatives Considered

- **Assert the `mtls` profile (`Environment.acceptsProfiles`)** — rejected after implementation
  proved it wrong. The profile is only the *delivery mechanism* for the properties, and the two
  diverge: `InternalMtlsAuthorizationIT` activates the CN scoping by `@TestPropertySource` with **no
  profile active**, which a profile check reports as unhardened (false negative); the inverse —
  profile on, property lost — reports hardened while the control is off (false positive). Asserting a
  proxy for the posture rather than the posture is the same intent-marker mistake F2 identified.
  Per-property checks also let the failure name *which* control is missing.
- **`@ConfigurationProperties` + `@Validated` + `@AssertTrue`** — rejected on complexity budget. It
  would be the repo's first `@ConfigurationProperties` class (everything else uses `@Value`) and would
  add `spring-boot-starter-validation` to exec and gateway, for a startup check. A per-service
  `@Configuration` bean is the established idiom (`FlywaySchemaObservability`, `PartitionMaintenance`
  are duplicated per service exactly this way) and adds no dependency.
- **A shared guard in `chaosforge-common`** — rejected: that module declares "No Spring application
  context here. Keep dependencies minimal to avoid coupling the three surfaces." The three control
  sets also genuinely differ (see Consequences), so the shared surface would be ~25 lines of
  gap-joining against a new module.
- **`ApplicationReadyEvent` listener** — rejected: it fires *after* `finishRefresh()` starts the web
  server, so the service is already accepting traffic. A singleton bean constructor throws during
  `finishBeanFactoryInitialization()`, before the port opens.
- **Fail-closed default (`deployment=deployed` unless told otherwise)** — rejected: no test in the
  repo uses `@ActiveProfiles`; all run on the default profile, so a fail-closed default fails the
  entire suite. The default is permissive and the deployment artifact opts in.
- **Unqualified alert on `chaosforge_security_hardened == 0`** — rejected: the lab is unhardened *by
  design*, so it would fire permanently — the "background noise" `alerts.yml` explicitly disavows.

## Consequences

**Positive:**

- The silent insecure start is gone in the case that matters: a deployment that sets the marker and
  misses a control **cannot start**, and the exception names every gap.
- The failure names the specific control (`server.ssl.bundle` unset, `client-auth != need`,
  `internal-peer-cn` unset, `base-url` not https, `allowed-hosts` empty) rather than "wrong profile".
- The alert is **fail-closed by omission**: the *lab* stamps `env: lab`, so any Prometheus written
  without an `env` label matches `env!="lab"` and pages. A new deployment that forgets everything
  still alerts.
- Requiring a non-empty `allowed-hosts` when deployed forecloses SSRF open mode there, which also
  moots `block-private-networks` on that path (allowlist mode overrides it — ADR-0534).
- Each service asserts only its true control set, so the checks stay honest: exec has no
  `internal-peer-cn` (it is the *caller* on that path), and the gateway asserts **no server-side TLS**
  at all — its public listener is HTTP by design (public CA cert, TLS terminates upstream), and
  `client-auth: need` there would reject every real public client.

**Negative:**

- **A flag cannot protect against a forgotten flag.** The fail-fast is conditional on
  `CHAOSFORGE_DEPLOYMENT=deployed`; forget the marker and there is no assertion at all — only the
  gauge, and only if someone alerts on it. This ADR moves the trust from one env var to another; it
  does not eliminate it. The residual is real and is the reason the gauge is unconditional.
- **The `deployed` + unhardened state is unobservable by construction** — the process dies, so it is
  never scraped. The alert therefore cannot test the fail-fast; the two mechanisms cover disjoint
  cases and neither can validate the other.
- **The alert cannot fire against live lab data.** Its behaviour is proven only by promtool unit tests
  (`docker/prometheus/alerts_test.yml`), which are a **manual gate** — not wired into
  `./gradlew check`, so the rule's annotations can drift from the tests that assert them verbatim.
- Three near-identical guards, one per service (~25 lines of shared logic duplicated), accepted over a
  new Spring-aware shared module.
- The guard trusts its own property reads: it asserts `server.ssl.bundle` is *set*, not that the
  bundle loads or that the cert is valid. A configured-but-broken bundle fails elsewhere, later.
- `env: lab` in `docker/prometheus/prometheus.yml` is now load-bearing. Removing it re-arms the alert
  against the lab; copying it onto a real deployment silences a genuine incident.
