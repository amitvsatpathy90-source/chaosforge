# ADR-0531 — Intra-Service mTLS via Spring SSL Bundles (Profile-Gated, Env-Sourced Secrets)

|---|---|

---

## Context

ADR-0524 established the two-independent-checks model: **mTLS** answers *"is this request from the
gateway/exec process?"* and the **re-verified JWT** answers *"which tenant?"*. The JWT half shipped.
The mTLS half was, until now, **only a contract on paper** — `mTLS security policy` described the posture and
both client wiring points carried a literal `TODO`:

- `GatewayConfig.controlPlaneWebClient` — *"attach a client SslBundle to the connector here — wired in the mTLS step."*
- `HttpClientConfig.controlPlaneRestClient` (Exec) — same TODO.

No keystores existed, no bundle config existed, and CP/Exec accepted plain HTTP from any sibling. The
channel-authentication leg of the defence-in-depth claim was unenforced. This ADR closes that gap.

### Boot 4 surface

Spring Boot 4 unified client TLS under **SSL bundles** (`spring.ssl.bundle.*`) and a single
`HttpClientSettings` record consumed by both the imperative `ClientHttpRequestFactoryBuilder` and the
reactive `ClientHttpConnectorBuilder`. These builders live in the **`spring-boot-http-client`** module,
which the `web`/`webflux` starters do **not** pull transitively (parallel to the ADR-0530 Flyway split)
— it must be declared explicitly.

---

## Decision

### 1. One reusable bundle name, per-service keystore

A single logical bundle, **`internal-mtls`**, is referenced everywhere. Each service mounts its **own**
keystore (its CA-signed identity, key alias = service name) and the **shared** truststore (the internal
CA cert). Paths/passwords are injected per service:

| Service | Server (`client-auth: need`) | Client (presents cert) | Key alias |
|---|---|---|---|
| Control Plane | ✅ (from Gateway **and** Exec) | — (Ollama is local/plain; no sibling HTTP out) | `control-plane` |
| Execution Service | ✅ (admin/HTTP surface) | ✅ → CP rule-set fetch | `execution-service` |
| Edge Gateway | — (public ingress; its public TLS uses a public cert, lab=HTTP) | ✅ → CP replay/get/policy | `edge-gateway` |

The Kafka consumer path has **no** HTTP JWT and **no** mTLS — tenant identity there is the signed Avro
payload verified at pipeline step 1 (ADR-0524 / `mTLS security policy`). mTLS guards only HTTP surfaces.

### 2. Server side — `client-auth: need`, profile-gated

CP and Exec enable TLS with **mandatory** client auth only under the `mtls` Spring profile
(`application-mtls.yml`). `need` (not `want`) means a missing/untrusted client cert is rejected at the
TLS layer, before any controller or filter runs. Dev/test default profiles stay on plain HTTP so the
test suite needs no cert material.

### 3. Client side — bundle attached iff configured, else fail-fast, never silent-downgrade

Both client beans gained `@Value("${chaosforge.mtls.client-bundle:}")` + `ObjectProvider<SslBundles>`:

```java
// Exec — imperative
HttpClientSettings s = HttpClientSettings.defaults().withConnectTimeout(..).withReadTimeout(..);
if (StringUtils.hasText(clientBundle)) s = s.withSslBundle(sslBundles.getObject().getBundle(clientBundle));
RestClient.builder().requestFactory(ClientHttpRequestFactoryBuilder.detect().build(s))...

// Gateway — reactive (Netty)
if (StringUtils.hasText(clientBundle))
    builder.clientConnector(ClientHttpConnectorBuilder.reactor()
        .build(HttpClientSettings.ofSslBundle(sslBundles.getObject().getBundle(clientBundle))));
```

- **Property empty** (dev/test) → plain HTTP, one code path, no profile-specific beans.
- **Property set but bundle absent** → `getBundle` throws → **startup fails**. We never fall back to an
  unauthenticated channel by accident — the only two states are "mTLS on" or "explicitly off".
- The Exec **target** RestClient (arbitrary tenant scenario URLs) is deliberately **not** bundle-wired —
  those are untrusted external endpoints; the internal CA is irrelevant to them.

### 4. Secrets posture

Keystore/truststore **passwords** come from env vars with **no default** (`${MTLS_KEYSTORE_PASSWORD}`) —
a missing password fails startup. Only lab **file locations** carry a localhost default. No password,
key, or CA material appears in any yaml or source file. Generated material is git-ignored.

### 5. Lab material generator

`docker/mtls/generate-certs.sh` produces a self-signed internal CA, three CA-signed PKCS12 keystores
(SAN: `localhost`, `<service>`, `127.0.0.1`; EKU: `serverAuth,clientAuth`), and the shared truststore.

## Verification

Two real-socket handshake tests (no Spring context, no Postgres/Kafka — fast, deterministic):

- `MtlsControlPlaneClientHandshakeTest` (Exec, JDK `HttpClient`) and
  `MtlsControlPlaneWebClientHandshakeTest` (Gateway, Netty) each stand up a JDK `HttpsServer` with
  `needClientAuth(true)` (the exact `client-auth: need` posture) and assert:
  1. the **actual production bean**, given the internal-CA bundle, completes a mutual-TLS handshake (200);
  2. a client that trusts the server but presents **no** client cert is **rejected at the handshake**.

This proves the security guarantee — `need` rejects an uncertified caller — rather than asserting it.
The full CA-signed chain + `server.ssl.client-auth: need` on the real Spring listener is exercised by
the manual game-day in `docs/chaosforge-mtls-design.md`.

## Alternatives Considered

| Option | Rejected because |
|---|---|
| Build Netty/JDK SSL contexts by hand (no `spring-boot-http-client`) | Avoids one BOM-managed Boot dep but reintroduces bespoke `SslContextBuilder` plumbing the bundle abstraction exists to remove; less uniform across the two services. |
| PEM bundles (`spring.ssl.bundle.pem`) | Cleaner generation, but `mTLS security policy` and the prior commented config specify JKS/PKCS12 + `MTLS_KEYSTORE`/`MTLS_TRUSTSTORE` env vars; kept the documented contract. |
| Gateway mints a short-lived internal service token instead of mTLS | Already weighed and deferred in ADR-0524 §Alt-2; mTLS reuses existing PKI with no new signing key. |
| `client-auth: want` | Makes the cert optional → an uncertified caller is silently accepted. `mTLS security policy` forbids it. |
| Profile-free, always-on mTLS | Forces every unit/IT to provision certs; high friction for a lab. Profile-gating keeps tests cert-free while the deployed profile is locked down. |

---

## Consequences

**Positive** — the channel-authentication leg of ADR-0524 is now real and tested; secrets stay out of
source; one bundle name keeps config uniform; configured-but-broken mTLS fails fast rather than
downgrading.

**Negative / residual risks (explicit):**

1. **Manual rotation.** Lab CA + certs rotate by re-running the script + restart. Automate (e.g.
   cert-manager / SPIFFE) before any real deployment. (Known Limitation, carried.)
2. **Real Spring server TLS is game-day-verified, not unit-tested.** The handshake tests use a JDK
   `HttpsServer` mirroring `need`; booting all three apps with TLS + valid chain is a manual step.
3. **`detect()` picks the JDK factory in Exec** (no Apache/Reactor on its classpath). Intended, but a
   future client dependency change could shift the selected factory — pin with `.jdk()` if that matters.
4. **No CRL/OCSP revocation.** A compromised service cert is valid until expiry; the lab has no
   revocation. Acceptable for lab; note before production.
5. **SAN list is fixed** (`localhost`, `<service>`, `127.0.0.1`). A new hostname/topology (k8s service
   DNS, mesh sidecar) needs a regen with added SANs.
