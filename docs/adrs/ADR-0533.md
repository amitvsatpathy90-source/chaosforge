# ADR-0533 — Steady-State Auto-Abort (C20) Cadence Must Be Time-Based, Not Per-Step

## Context

An architecture audit (arch-audit finding 2.3) showed that the C20 auto-abort, as implemented, cannot
fire for the most common class of chaos scenario.

`ExecutePhase` calls `SteadyStateCheck.breached()` **once per fault step**, and each call performs
**exactly one** health probe. A breach requires `max-consecutive-failures` (default **3**) consecutive
unhealthy probes. Therefore the number of probes in a run is bounded by the number of fault steps:

- A **1- or 2-step scenario can never breach** — the consecutive-failure counter physically cannot
  reach 3. Single-fault experiments ("inject 500 ms latency on `/checkout`") are the *dominant* case, so
  C20's auto-abort is **inert for exactly the scenarios operators most often run**.
- The probe runs *before* each step's injection and there is **no terminal probe**, so the last (or
  only) fault step's blast radius is never evaluated at all.
- Health is derived solely from `steps.get(0)`'s authority (`SteadyStateGuard.deriveHealthUrl`); a
  multi-target scenario only ever probes the **first** target's `/health`.

The C20 gate's tests (`SteadyStateCheckTest`, `ExecutePhaseControlsTest`, `SteadyStateAbortPipelineIT`)
all use step counts ≥ 3, so the limitation is invisible to the suite. The gate is real for long
scenarios and vacuous for short ones.

---

## Decision

Redefine the steady-state breach condition so it is **independent of step count**:

1. **Breach is time-based, not per-step.** Probe the target health on a wall-clock cadence during the
   run (e.g. every `probe-interval` seconds, bounded well below the aggregate deadline), and breach when
   the target has been unhealthy for a continuous `breach-duration` (or N consecutive interval probes) —
   so a 1-step scenario still accumulates enough samples to abort. The reset-on-recovery property (a
   transient blip never aborts) is preserved.

2. **Add a terminal probe.** Evaluate steady state **after** the last fault step, so the final step's
   blast radius is covered.

3. **Probe every distinct target host**, not just `steps.get(0)`, when a scenario spans multiple hosts.

4. **Tests must include a single-step scenario** that breaches and aborts — the case the old suite
   omitted. Without it the gate stays vacuous for the common workload.

**IMPLEMENTED.** `SteadyStateCheck.breached(deadlineMs)` now probes at `chaosforge.steady-state.probe-
interval-ms` (default 1000 ms) until a probe is healthy (streak resets, no breach) or
`max-consecutive-failures` consecutive probes fail (breach), bounded by the aggregate deadline; a healthy
first probe returns immediately so the common path adds one probe of latency. `SteadyStateGuard` derives a
distinct health URL for **every** target host across the steps (not just `steps.get(0)`), and
`ExecutePhase` adds a **terminal** evaluation after the last step. Proven by `SteadyStateCheckTest`
(within-one-evaluation breach, transient-blip reset, deadline bound), `ExecutePhaseControlsTest`
(`steadyStateBreach_onASingleStepScenario_stillAborts` — the regression the old model failed), and
`SteadyStateAbortPipelineIT` (breach → ABORTED persisted to real Postgres). Executor-local change: no
schema, no wire contract, no cross-service impact.

---

## Consequences

**Positive** — C20 now covers single-fault scenarios (the majority) and the terminal step; the gate is no
longer conditional on step count, and multi-target scenarios probe every host.

**Negative / residual:** a persistently-unhealthy target now costs up to `(max-consecutive-failures - 1) ×
probe-interval-ms` of in-boundary probing latency per step boundary (default ≤ 2 s), bounded by the
aggregate deadline — a deliberate trade for making short scenarios abortable. `probe-interval-ms` must
stay well below `aggregate-timeout-ms`; the code clamps the loop to the deadline as a backstop.

---

## Alternatives Considered

| Option | Rejected because |
|---|---|
| Lower `max-consecutive-failures` to 1 | A single transient blip would abort every run — the exact false-positive the streak counter exists to prevent. |
| Probe N times in a tight loop at each step boundary | Injects real latency into the step loop and still ties cadence to step count; time-based is cleaner. |
| Accept the limitation, document only | Leaves the headline C20 guarantee false for the common workload; the fix is cheap and local. |
