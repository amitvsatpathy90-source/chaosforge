# ADR-0518 — AI Determinism Boundary: Authoring and Advisory Only

**Status:** ACCEPTED
**Date:** 2026-06-13
**Reversal cost:** HIGH
**Owner:** Principal Engineering

> **Implementation status (2026-07-16):** both surfaces are implemented. Surface 1 (authoring):
> `OllamaAuthoringClient` + `scenario-authoring-system.txt`. Surface 2 (advisory DLQ triage):
> `DlqTriageController`/`DlqTriageService`/`DlqRecordReader`/`OllamaTriageClient` +
> `dlq-triage-system.txt` — read-only (a group-less consumer that structurally cannot commit),
> `.DLQ`-topics-only, OPERATOR-role-gated, with a required `partition` param (a record is addressed
> by topic+partition+offset — the path documented here predated that detail). Proven by
> `DlqTriageServiceTest` + `DlqTriageIT`. The determinism boundary binds both surfaces.

> **Amendment (ADR-0542, 2026-07-17):** the DLQ triage *surface* is no longer uniformly read-only. The
> **AI advisory path** (`DlqTriageService` / `DlqRecordReader` / `OllamaTriageClient`) stays strictly
> read-only — no replay, no ack, no offset commit, no state write — so this ADR's advisory/determinism
> claim holds for the AI unchanged. ADR-0542 adds a **separate**, OPERATOR-gated write verb
> (`PUT /v1/dlq/{topic}/reviewed`, `DlqTriageWatermarkController`) that advances a human-triage watermark
> in CP Postgres to back the standing-DLQ-depth gauge (arch-audit F5). That write is a *non-AI operator
> action*, touches only a CP row (never a Kafka offset/ack/replay), and is deliberately kept off the AI
> classes. Read "read-only, no state mutation" below as scoped to the AI advisory path.

## Context

ChaosForge's correctness argument (ADR-0502) rests on replay determinism: a scenario run today produces the same execution as a replay next week. The LLM (Spring AI / Ollama) is non-deterministic. If the LLM is called during the execution path, replay determinism is silently destroyed — no error, no signal, just a different execution.

---

## Decision

The LLM is called exclusively at:
1. **Authoring time** — `POST /v1/scenarios/draft` on the Control Plane; returns a `ScenarioDraft` for human review before explicit commit.
2. **Advisory DLQ triage** — `GET /v1/dlq/{topic}/triage/{offset}` on the Control Plane; read-only, no state mutation.

The LLM is **never** called during:
- The replay CAS critical section (ADR-0522/ADR-0528 — `pg_try_advisory_xact_lock` superseded)
- Rule-set loading
- Execution Service processing (any `@KafkaListener` path)
- Outbox/inbox relay
- Any Kafka consumer

**The isolation is structural, not conventional.** The authoring endpoint returns a `ScenarioDraft` requiring an explicit second request (`POST /v1/scenarios`) to commit. No LLM output is ever auto-committed. After commit, replay reads the pinned row — not the model. The LLM is upstream of the replay boundary and cannot influence it post-commit.

---

## Alternatives

**LLM-assisted step execution (generate injection parameters at runtime):** Non-deterministic by definition. Same scenario replay on Tuesday vs Friday could produce different injections if the model response differs. Silently breaks the portfolio's centerpiece claim. Rejected.

**LLM as rule-set recommender during scenario run:** Same non-determinism problem. Rejected.

**LLM auto-commit (no human review step):** Removes the structural upstream boundary. Auto-committed LLM output could contain malformed step definitions or cross-tenant target URLs (prompt injection risk). Two-step flow (draft → explicit commit) is the control. Rejected.

---

## Consequences

**Positive:**
- Replay determinism is preserved structurally — the model cannot influence execution after the commit transaction closes.
- Prompt injection impact is bounded: even if a tenant engineers a malicious prompt, the model's output is validated and the tenant-ownership check runs before persist (see ADR-0519).

**Negative:**
- Two-step authoring flow (draft → review → commit) adds UX friction vs auto-commit.
- DLQ triage is advisory only — AI analysis does not trigger replay. This is correct but means the AI feature has no autonomous action surface, which limits its demo impact.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| AI call added to Execution Service by a developer | ArchUnit rule: no `ChatClient` or `SpringAiClient` bean in `execution-service` module | CI hard fail |
| LLM call inside the CAS critical-section transaction | Code review; `@Transactional` boundary inspection | `Control Plane architecture rules` + `AI integration guidelines` forbid this explicitly; ADR-0528 checklist item |

## Implementation Notes

- `ChatClient` bean defined **only** in `control-plane` module. Zero Spring AI dependencies in `edge-gateway` or `execution-service`.
