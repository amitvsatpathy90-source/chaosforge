# ADR-0510 — Cross-Tenant Access Returns 404, Not 403

**Status:** ACCEPTED
**Date:** 2026-05-20
**Reversal cost:** LOW
**Inherits from:** ADR-0509 (three-layer tenant isolation)
**Owner:** Principal Engineering

---

## Context

When Tenant B requests a resource owned by Tenant A, the correct HTTP response is either `403 Forbidden` or `404 Not Found`. The choice has a security implication.

---

## Decision

Cross-tenant access returns **`404 Not Found`**, never `403 Forbidden`.

Rationale: `403` reveals that the resource exists but the requester is not permitted to access it. A malicious tenant can use `403` responses to enumerate resource IDs belonging to other tenants — a pure information leak with no legitimate use. `404` reveals nothing about resource existence.

---

## Alternatives

**`403 Forbidden`:** Standard HTTP semantics for "resource exists but access denied." Leaks resource existence to the requester. Rejected.

**`401 Unauthorized`:** Wrong — the requester is authenticated; they are accessing a resource outside their tenant scope. `401` implies authentication failure. Rejected.

---

## Consequences

**Positive:** No resource-existence information leak to cross-tenant requesters.

**Negative:** Developers debugging cross-tenant misconfiguration receive a `404` with no indication that the resource exists. Mitigated by server-side structured logging at WARN level: `"cross-tenant access attempt: requestingTenant={} resourceTenant={} resourceId={}"`.

---

## Implementation Notes

- Repository layer: `findByIdAndTenantId` returns `Optional.empty()` when the row exists but `tenant_id` doesn't match — indistinguishable from genuinely not found.
- Service layer: `Optional.empty()` → throw `ResourceNotFoundException` → `404`.
- Log the cross-tenant event at WARN with `tenant_id` masked to last 4 chars.
