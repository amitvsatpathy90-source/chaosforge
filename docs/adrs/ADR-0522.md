## Context

ADR-0502 adopted `pg_try_advisory_xact_lock` as the mutual-exclusion primitive for the replay-start critical section. The design is correct: transaction-bound, crash-safe, non-blocking, auto-released. During the production-hardening pass (architecture specification v1.4.0), the replay critical section was changed to a CAS-on-`replay_version`. ADR-0502 was not superseded at the time — this ADR closes that gap and documents the rationale.

The Kleppmann/Redlock rejection is **unchanged** by this decision. CAS-plus-fencing is strictly in the same family as advisory-lock-plus-fencing; the Redlock critique does not apply to either.

---

## Decision

Replace `pg_try_advisory_xact_lock` with a CAS `UPDATE … WHERE replay_version = $expected_version RETURNING replay_version` on `scenario_replay_state`. This collapses the advisory lock acquisition and the version-bump into a single SQL statement.

```sql
UPDATE scenario_replay_state
   SET replay_version = replay_version + 1,
       last_started_at = now()
 WHERE scenario_id = :id
   AND replay_version = :expected_version
RETURNING replay_version;
-- 1 row updated → winner; new replay_version is the fencing token
-- 0 rows updated → concurrent replay already bumped; return HTTP 409 { Retry-After: 2 }
```

`expected_version` comes from the client's prior `GET /scenarios/{id}` response (`If-Match` header or body field).

> **ADR-0528 supersedes the fallback clause.** The sentence "The Control Plane may also read the
> current version within the same tx if the client omits it" is **FORBIDDEN** and does not reflect
> the current design. Reading `replay_version` and then CAS-ing against it in the same transaction
> makes the predicate trivially true — the 409 contention path can never fire and two concurrent
> runs both "win". `expectedVersion` must always come from the client; there is no
> version-omitted overload. See ADR-0528 §Decision step 3 and its Implementation Checklist.

## Alternatives Considered

### 1. Keep advisory locks (ADR-0502 design)

Advisory locks are correct. Failure modes:
- Advisory lock state is **in-memory on the Postgres primary** and **not WAL-logged**. On primary failover, the new primary has no lock state — a competing request can acquire it immediately. ADR-0502 §3.5 documented this and noted "fencing handles it." True, but requiring a reconciliation pass adds startup complexity.
- `hashtext()` collision: negligible at 10⁵ scenarios but non-zero and untestable without load.
- Two SQL statements (advisory lock + version bump) vs one (CAS). Marginally more surface to audit.

**Rejected** because CAS has strictly better properties without any cost.

### 2. `SELECT … FOR UPDATE NOWAIT` on `scenario_replay_state`

Blocks readers of the same row. CAS does not. Rejected for the same reason as in ADR-0502.

### 3. Distributed lock (etcd, Consul, Zookeeper)

Adds a new operational dependency. Postgres CAS solves the same problem. YAGNI.

### 4. Redlock

Rejected per Kleppmann's critique. Unchanged by this ADR.

## Consequences

### Positive

- **Simpler:** mutex and version allocation in one statement; no separate advisory-lock table operations.
- **Failover-safe by construction:** CAS operates on WAL-logged row state; new Postgres primary inherits the committed `replay_version`; no reconciliation pass needed on startup.
- **No hashtext collision class:** each scenario's CAS predicate is its own row; no shared namespace.
- **Horizontally scalable CP with no per-instance state:** N replicas each issue the same CAS; Postgres serializes at the row level.

### Negative

- **Requires `expected_version` from the client** (or a prior read in the same tx). The advisory-lock design required no client coordination — any replica could call `tryStart(id)`. Under CAS, the client must supply the version it last saw, making this a true optimistic-concurrency API rather than a transparent lock.
- **Thundering-herd on high-contention scenarios:** under burst (50 concurrent POs for the same scenario), all 50 read the same `expected_version`, all 50 issue CAS, 1 wins, 49 return 409. Under advisory locks, they would also all return 409 except the winner — so the behaviour is equivalent from the client's perspective. Neither design blocks under contention.

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| Client sends stale `expected_version` (already incremented by another replica) | 0 rows → 409; client reads fresh version and retries | Documented retry protocol: backoff on 409, re-GET, re-POST |
| CP pod dies between CAS win and tx commit | TX aborts; `replay_version` unchanged; client sees 5xx; safe to retry | PG atomicity |
| Postgres primary failover between CAS commit and outbox poller publish | Outbox row durable on new primary (WAL); poller picks it up | Outbox durability |
| Two pods CAS simultaneously with the same `expected_version` | Postgres serializes the row update; one wins, one gets 0 rows → 409 | Row-level atomicity |

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| `scenario_replay_state` row is always present before `tryStart` is called | ASSUMED | If not, `UPDATE` matches 0 rows — indistinguishable from concurrent replay. Mitigation: create the row at scenario-creation time (INSERT … ON CONFLICT DO NOTHING). |
| Client supplies `expected_version` from a fresh read | ASSUMED | If client caches stale version across retries without re-reading, every retry returns 409. Documented in API contract: re-read before re-POST after 409. |
| `statement_timeout` is set on the CP JDBC connection pool to bound dead-hold | ASSUMED | Without it, a hung tx holds the row update lock. Set `statement_timeout = 5s` on the datasource. |

## Implementation Notes

- `scenario_replay_state` row is created by a trigger or application code at scenario-creation time with `replay_version = 0`.
- The `GET /scenarios/{id}` response body includes `replayVersion` (the current committed value); the `POST /scenarios/{id}:run` request body includes `expectedVersion`.
- The Control Plane returns `Retry-After: 2` on 409 per the idempotency contract.
- `ScenarioReplayOrchestrator.java` (`control-plane/src/main/java/io/chaosforge/controlplane/replay/ScenarioReplayOrchestrator.java`) is the sole implementation site; no other code path writes to `scenario_replay_state.replay_version`.
- The `scenario_replay_state` table is in `chaosforge_cp` (`scenario_replay_state.scenario_id` FK → `scenarios.scenario_id`). `replay_version` is **not** on the `scenarios` table.
