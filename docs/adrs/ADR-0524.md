# ADR-0524 — Tenant Identity Provenance: JWT Re-Verified at CP/Exec; X-Tenant-Id Header Not Trusted

## Context

ChaosForge's multi-tenant isolation model is described as "defence in depth" across three layers:

1. Gateway: JWT validation + `tenant_id` extraction.
2. Service: `@PreAuthorize` + `tenant_id` propagation.
3. Repository: mandatory tenant filter.

The original implementation of Layer 2 propagated `tenant_id` via an `X-Tenant-Id` HTTP header set by the gateway. The description noted "signed via mTLS in prod; lab uses unsigned propagation." This framing conflates two distinct authentication concerns:

- **mTLS** authenticates the *channel peer* — it proves the request arrived from the gateway process holding a cert signed by the internal CA. It says nothing about the *value* inside the request.
- **`X-Tenant-Id` header** carries a claim. It is a byte string in the request. mTLS does not sign it; it only proves who sent it. A bug in the gateway (incorrect header routing, fan-out race, middleware injection), a compromised gateway process, or a misconfigured proxy could set `X-Tenant-Id` to any value and have it accepted as authoritative at CP/Exec.

Layer 3 (repository tenant filter) then enforces isolation perfectly — but against the *wrong* principal. Cross-tenant data access becomes possible without any Layer 3 defect.

This is not a theoretical risk for a portfolio artifact; it is the first thing a security-aware reviewer will probe. The defence-in-depth claim only holds if each layer independently verifies identity from a cryptographically bound source.

---

## Decision

**The original JWT issued by the identity provider is forwarded to CP/Exec by the gateway** as the `Authorization: Bearer <token>` header. Each service's security filter re-validates the JWT (signature, `exp`, `iss`, `aud`) and derives `tenant_id` from the verified claims — never from a mutable HTTP header.

mTLS continues to authenticate the channel: CP/Exec require a valid client certificate signed by the internal CA. Both checks are mandatory and independent:

- mTLS answers: "Is this request from the gateway?" (channel authentication)
- JWT answers: "Which tenant is making this request?" (principal authentication)

```
External client
  │  Authorization: Bearer <jwt>
  ▼
Edge Gateway
  │  Validates JWT: signature, exp, iss, aud
  │  mTLS client cert → CP (proves gateway identity)
  │  Forwards original: Authorization: Bearer <jwt>
  │  Optionally adds: X-Tenant-Id: <id>  ← logging/tracing only; NOT authoritative
  ▼
Control Plane / Execution Service
  │  mTLS: verify client cert signed by internal CA
  │  JWT: re-validate signature, exp, iss, aud → derive tenant_id from claims
  │  TenantContext.set(tenant_id)
  │  X-Tenant-Id header: IGNORED for security purposes
  ▼
Repository layer
  │  All queries: WHERE tenant_id = TenantContext.get()
```

### JWT re-validation at CP/Exec

```java
@Component
public class JwtTenantExtractionFilter extends OncePerRequestFilter {

    private final JwtDecoder jwtDecoder;   // Spring Security 7 JwtDecoder bean

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String header = request.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith("Bearer ")) {
            response.sendError(HttpServletResponse.SC_UNAUTHORIZED);
            return;
        }
        try {
            Jwt jwt = jwtDecoder.decode(header.substring(7));
            UUID tenantId = UUID.fromString(jwt.getClaimAsString("tenant_id"));
            TenantContext.set(tenantId);
            // Propagate as Spring Security authentication for @PreAuthorize
            SecurityContextHolder.getContext().setAuthentication(
                new JwtAuthenticationToken(jwt, extractAuthorities(jwt))
            );
        } catch (JwtException e) {
            response.sendError(HttpServletResponse.SC_UNAUTHORIZED);
            return;
        }
        try {
            chain.doFilter(request, response);
        } finally {
            TenantContext.clear();
        }
    }
}
```

### What `X-Tenant-Id` is used for

The header may still be propagated for structured logging and distributed tracing (correlating log lines without decoding the JWT on every log call). It must be explicitly marked as `for-logging-only` in the service's internal model and must never be read by security filters, `@PreAuthorize` expressions, or repository queries.

---

## Alternatives Considered

### 1. Trust `X-Tenant-Id` header (mTLS as authentication proxy)

The argument: mTLS proves the caller is the gateway; therefore anything the gateway says about `tenant_id` is authoritative. The argument fails because:
- mTLS authenticates the **sender process** not the **header value**. A bug in the gateway is sufficient to produce a wrong header; mTLS cannot detect this.
- Gateway fan-out bugs (routing tenant A's request with tenant B's header) are a real bug class, not a theoretical one.
- This is equivalent to trusting a header set by an authenticated process — a standard pitfall explicitly called out in OAuth2/OIDC literature.

**Rejected**: the cryptographic source of truth for `tenant_id` is the JWT; that is what must be verified.

### 2. Gateway mints a short-lived internal assertion token (service token)

The gateway signs a new short-lived token (e.g. a JWT with a service-specific audience and a 30s TTL) containing the verified `tenant_id`. CP/Exec verify this internal token rather than the original JWT.

**Viable but more complex**: requires the gateway to hold a signing key; requires CP/Exec to trust that key; token rotation adds operational surface. The original JWT forwarding approach reuses the existing public-key infrastructure and adds no new key management. Deferred to post-MVP if the token lifetime or audience-isolation properties become requirements.

### 3. Pass `tenant_id` as a path parameter (enforce at API layer)

Every URL carries `/{tenantId}/...`; the controller extracts it from the path. Still a mutable value; still requires comparison against a verified identity source. Not a replacement for JWT re-verification — would need to be combined with it.

---

## Consequences

### Positive

- Each layer independently verifies identity from a cryptographically bound source. The "defence in depth" claim is now accurate.
- A gateway bug or compromised gateway process cannot produce a cross-tenant data access at CP/Exec — the JWT signature check would fail (or the JWT's `tenant_id` claim would be the correct tenant, making the attack ineffective).
- No new infrastructure: the JWT public key is already distributed to CP/Exec for the existing `@PreAuthorize` wiring.
- The repository layer (Layer 3) now is a true backstop against developer errors, not a substitute for identity verification.

### Negative

- Every CP/Exec request incurs a JWT decode + signature verification. Cost: ~1ms for RS256 with a cached public key. Acceptable; cached JWK sets in `JwtDecoder` make repeat verifications fast.
- JWT forwarding requires the gateway to not strip the `Authorization` header before proxying. Verify WebClient config: `WebClient` must forward the header, not replace it with a service credential.
- JWT `exp` must be long enough to survive the gateway-to-CP hop plus any retry latency. If the original token expires in <30s and the hop is slow, CP sees an expired token. Mitigation: use tokens with ≥5-minute lifetime (standard).

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| Expired JWT reaches CP (clock skew, slow network) | `JwtException` → 401; client must re-authenticate | Standard OAuth2 token refresh; document 5-minute minimum token lifetime |
| Gateway strips Authorization header before proxying | CP returns 401 on all requests | Integration test: assert Authorization header present at CP filter |
| JWK set endpoint unreachable at CP startup | `JwtDecoder` bean fails to initialize; service startup fails fast | Document JWK set URL in config; health check on startup |
| `tenant_id` claim absent from JWT | `ClaimAccessException` → 401 | Document claim requirement in identity-provider setup guide |

---

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| JWT has ≥5-minute lifetime | ASSUMED | If identity provider issues short-lived tokens (<2min), hop + retry may cause expiry at CP. Verify with IdP config. |
| JWK set is cacheable and stable | ASSUMED | Key rotation invalidates cached JWK. Configure `JwtDecoder` with auto-refresh on 401 upstream. |
| Gateway WebClient preserves Authorization header | REQUIRED | Must be verified in gateway integration tests. `WebClient` default: does not propagate inbound headers to outbound — must be explicitly configured. |
| `tenant_id` is a UUID in the JWT claims | ASSUMED | If format changes, `UUID.fromString()` throws. Add explicit claim-shape validation to the filter. |

## Implementation Notes

- `JwtDecoder` bean in CP/Exec configured with the public JWK set URI (`spring.security.oauth2.resourceserver.jwt.jwk-set-uri`).
- Gateway `WebClient` bean: add `ExchangeFilterFunction` that copies the inbound `Authorization` header to outbound CP requests.
- `X-Tenant-Id` header: retain in requests for log correlation; add a `@Documented` annotation or comment marking it as non-authoritative in the filter chain.
- Spring Security 7 filter chain (Boot 4.1.x): use `.oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> jwt.decoder(jwtDecoder)))` DSL. Note: Security 7 DSL differs from Security 6.
- In the Execution Service: the `@KafkaListener` path does not carry an HTTP JWT. Kafka messages carry `x-tenant-id` in the Avro payload and Kafka headers. The Execution Service verifies `x-tenant-id` against the outbox-signed value (signed at CP outbox-insert time). Phase 1 of ADR-0523 enforces this. The HTTP-path JWT re-verification applies to the Execution Service's management/admin HTTP endpoints only.
