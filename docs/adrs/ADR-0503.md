# ADR-0503 — Rule Sets Are Append-Only by (rule_set_id, version)

**Status:** ACCEPTED
**Date:** 2026-05-20
**Reversal cost:** MEDIUM
**Owner:** Principal Engineering

---

## Context

Scenario replay determinism (ADR-0502) requires that a replay next week executes under exactly the same rules as the original run. If a rule set can be mutated in-place, a replay after mutation produces different behaviour — silently, with no error. The rule-set storage model must structurally prevent this.

---

## Decision

Rule sets are stored as `(rule_set_id UUID, version INT, ...)` with `version` as a per-`rule_set_id` monotonic counter. **No `UPDATE rule_sets SET ...` is permitted.** New rule configurations insert a new `version` row. The repository layer enforces this: no update method exists on `RuleSetRepository`.

At replay-start, the Control Plane captures the current `(rule_set_id, version)` and writes it into the outbox `headers`. The Execution Service loads by this exact tuple — never "the latest version of rule_set_id."

**Caching consequence:** cached rule-set values are immutable for their key `(rule_set_id, version)`. No invalidation event is ever emitted for rule sets. The two-level cache is structurally exempt from staleness for this entity — aggressive TTL is safe.

---

## Alternatives

**In-place mutation with versioned audit log:** Allows `UPDATE` but keeps a separate audit table. Does not help replay — the live row is the one the Execution Service would load if we allowed latest-version lookup. The audit log is observability, not a correctness primitive. Rejected.

**Immutable snapshots at replay-start (copy on run):** Copy the full rule-set config into the outbox payload at trigger time. Eliminates the need for a stable `(id, version)` key. But adds payload size, breaks the cache key model, and duplicates data for every run. Rejected.

---

## Consequences

**Positive:**
- Replay is structurally deterministic — same `(rule_set_id, version)` always loads the same config.
- Cache TTL can be set aggressively (hours) without staleness risk for rule-set entries.
- Repository API communicates the constraint: absence of an update method is self-documenting.

**Negative:**
- Users cannot "edit" a rule set — they create a new version. UI must surface version history. Additional UX complexity.
- Table grows monotonically; old versions are never deleted (they may be referenced by historical replays). Purge policy requires care — cannot purge a version referenced by any scenario's pinned tuple.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| Latest-version lookup used in Exec (bypasses pin) | Integration test: run scenario, mutate rule set (new version), replay — assert Exec used the pinned version | `Execution Service architecture rules` forbids latest-version lookup; ArchUnit rule enforces |
| Old version purged while still referenced | FK constraint on `scenarios.rule_set_version` → `rule_sets.version` | Schema-enforced; purge job must respect FK |

---

## Implementation Notes

- Schema: `rule_sets (rule_set_id UUID, version INT, config JSONB, created_at TIMESTAMPTZ, PRIMARY KEY (rule_set_id, version))`.
- `RuleSetRepository`: only `findByIdAndVersion(UUID, int)` and `findLatestVersion(UUID)` (for UI display). No save/update that modifies existing rows.
- Cache key: `"rule_set:" + rule_set_id + ":" + version`.
