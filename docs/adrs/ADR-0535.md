# ADR-0535 — Exactly One Terminal Event Per Run Under DLQ Retry (Heartbeat Sweep + Guarded Finalize)

| Field | Value |

| **Date** | 2026-07-13 |

## Context

An architecture audit (arch-audit H2) found that the "exactly one terminal event per run" contract the
results stream depends on was not actually held once a command was retried through the DLQ lane.

Two independent finalizers exist for every run `(scenario_id, replay_version)`:

- **Phase 3** (`FinalizePhase.complete`) — the normal terminal outcome (COMPLETED / FAILED / ABORTED);
- the **`IncompleteRunSweeper`** — the net for a Phase-2→3 crash, which marks a stuck run INCOMPLETE and
  emits a terminal INCOMPLETE result event.

Three facts combined into a defect:

1. `FinalizePhase.complete` inserted the result event **first**, then ran an **unguarded**
   `UPDATE scenario_run SET status=…` (no `WHERE status='IN_PROGRESS'`).
2. The sweep predicated on `started_at`, which `insertRunHeader` stamped once at the **first** Phase-1
   claim and never moved (`ON CONFLICT DO NOTHING`).
3. Per ADR-0529 a DLQ retry republishes with a **fresh** `message_id`, so it passes the inbox and
   re-executes — and each redelivery recomputes a fresh aggregate deadline (`ExecutePhase`, default
   240s). A run legitimately bouncing through the retry lane therefore stays live for many minutes while
   `started_at` stays frozen at t0.

The sweep threshold (360s = `max.poll.interval.ms` + grace) was chosen to never sweep a run inside **one**
poll budget. But across DLQ redeliveries a run spans **many** poll budgets. So the sweep would fire on a
still-executing run (t0+360s), emit a premature terminal INCOMPLETE event, and — because the later
successful Phase-3 finalize was unguarded — a **second** terminal event was published for the same run
and its status flip-flopped INCOMPLETE→COMPLETED. Concretely reachable at default config for any
latency-fault scenario whose steps approach the aggregate deadline (the core use case for a chaos tool):
one STEP_TIMEOUT (240s) plus a retry that lands after 360s.

Downstream harm: two contradictory terminal events for one run; fault injection continuing after a
terminal event was emitted; and the C27 completion-rate SLO double-counting (`swept_incomplete` and
`execution success` both increment).

## Decision

Hold the singular-terminal-event invariant with **two coupled changes** — neither is sufficient alone.

1. **Status-guarded finalize, event gated on the transition (the correctness half).**
   `RunLogDao.finalizeRun` carries `AND status = 'IN_PROGRESS'` and returns rows affected.
   `FinalizePhase.complete` flips **first**, and emits the result event **only when it affected 1 row**
   (this call won the terminal transition). A finalize that loses the race (the sweep already finalized
   the run, or a duplicate) affects 0 rows and emits nothing. The sweep's own flip is likewise
   `WHERE status='IN_PROGRESS' … RETURNING`, so both finalizers only emit for rows they actually flipped.
   Both directions of the race are now closed.

2. **Heartbeat sweep — measure inactivity, not age (the liveness half).** Migration **V11** adds
   `scenario_run.last_attempt_at`; `insertRunHeader` becomes
   `ON CONFLICT DO UPDATE SET last_attempt_at = now()`, so **every** Phase-1 claim (i.e. every
   fresh-`message_id` redelivery) advances the heartbeat, and `markStaleRunsIncomplete` predicates on
   `last_attempt_at`. A run being actively retried keeps its heartbeat fresh and is never swept; only a
   genuinely quiet run ages out — which is exactly the Phase-2 crash the sweep targets (a crash reuses
   the **same** `message_id`, is ack-skipped by inbox dedup, so Phase 1 never re-runs to refresh the
   heartbeat). `started_at` is retained for observability but no longer gates the sweep.

The sweep index (`idx_scenario_run_open`) moves to `last_attempt_at`. The threshold still exceeds
`max.poll.interval.ms` + grace so an in-flight single delivery is never swept; the heartbeat additionally
covers the multi-delivery retry span.

## Alternatives Considered

- **Only guard the finalize (drop the heartbeat).** Closes the double-event, but the sweep still marks a
  live, actively-retrying run INCOMPLETE prematurely — a spurious terminal event and a false negative in
  the completion-rate SLO. Rejected: fixes the symptom, not the "don't finalize a live run" root cause.
- **Only bump the sweep threshold** to exceed `max-attempts × aggregate-timeout` (~20+ min). Fragile: it
  couples an unrelated timeout to the retry budget, and any future change to either silently reopens the
  race. It also delays the legitimate crash-detection signal for every run. Rejected.
- **Reuse the original `message_id` on retry** so inbox dedup ties redeliveries to one run and the sweep
  can key on the inbox. Directly contradicts ADR-0529 (the fresh id is what lets a retry re-execute at
  all — the original is ack-skipped). Rejected.
- **A distributed lock / lease around finalization.** Heavier machinery for a race a single guarded
  UPDATE + a heartbeat column already resolve atomically in one tx. Rejected on cost.

## Consequences

- One terminal event per `(scenario_id, replay_version)`, proven by `FinalizePhaseTest` (Docker-free:
  winning transition emits one event, lost transition emits none) and by `IncompleteRunSweepIT`
  (heartbeat protects an actively-retried run; late-finalize-after-sweep is a no-op with a single
  surviving event).
- The completion-rate SLO (C27) stops double-counting retried runs.
- Cost: one extra `TIMESTAMPTZ` column and a per-claim `DO UPDATE` write (already inside the Phase-1 tx).
- Enforcement constraint recorded in `Execution Service architecture rules` ("Run finalization —
  exactly one terminal event per run") so neither invariant is silently weakened.
- Residual: the sweep still cannot distinguish a run wedged **mid-Phase-2 on its first delivery** (no
  redelivery, heartbeat never advances) from a crash — both are correctly swept after the threshold, which
  is the intended behaviour.
