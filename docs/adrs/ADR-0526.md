---

## Context

`chaosforge.scenario.commands.v1` carries fault-injection commands. The partition key determines ordering guarantees, load distribution, and tenant isolation at the broker level. Three options were considered.

---

## Decision

**Partition key = `scenario_id` (UUID string).**

---

## Alternatives Considered

### 1. `tenant_id:scenario_id` (compound key — original design in outbox-inbox.md)

**Rejected because:** ordering within a partition is by `scenario_id` anyway once the tenant prefix is stripped. The tenant prefix only groups all of a tenant's scenarios onto the same partition subset — producing HOL-blocking: one tenant's slow 5-minute scenario holds a partition and delays all other scenarios for that tenant (and for other tenants that hash to the same partitions).

### 2. `tenant_id` alone

**Rejected because:** severe HOL-blocking. All of a tenant's scenarios are fully serialized — only one runs at a time per partition. This eliminates the parallelism that makes the system useful for tenants with many concurrent scenarios.

### 3. `scenario_id` alone (chosen)

- Per-scenario ordering is the meaningful constraint: steps for scenario S must arrive at the Execution Service in submission order.
- Different scenarios for the same tenant can land on different partitions → parallel execution up to partition count.
- Hot scenarios (same `scenario_id` replayed rapidly) serialize on one partition — correct, because the CAS 409 prevents true concurrent runs of the same scenario anyway.
- Tenant fairness is enforced at the **gateway rate limiter** (Redis sliding window per tenant), not at the broker. This is the correct layer: the broker should not be the fairness enforcement point for multi-tenant workloads.

---

## Consequences

### Positive
- True parallel execution across scenarios within a tenant (bounded by partition count).
- No HOL-blocking across tenants.
- Correct ordering for per-scenario replay version sequencing.

### Negative
- If a `scenario_id` is extremely hot (many rapid replays), it serializes on one partition. Mitigated by the CAS 409 which prevents more than one concurrent run per scenario.
- Changing the partition key requires recreating the topic and reprocessing in-flight messages. Size partitions correctly at creation time.

---

## Partition Count

Default: 12. Size for peak concurrent scenarios: `partition_count ≥ peak_concurrent_scenarios`. Parallelism is bounded by `min(partition_count, consumer_instances × threads_per_instance)`. In the lab: 12 partitions, 1–2 Execution Service instances, 1 listener thread per consumer. Resize before go-live, not during.
