## Context

If ADR-0513 adopts OTel on the Execution Service, a downstream question arises: does the OTLP pipeline go directly to Tempo, or through an OTel Collector? The Collector is what enables tail-sampling — the key capability that motivated the OTel stretch in the first place. This ADR decides the Collector topology.

**Do not read this ADR if ADR-0513 = ACCEPTED-STAY.** The Collector is irrelevant if OTel is not adopted.

---

## Options

### Option A — OTLP direct to Tempo (no Collector)

```
Execution Service ──OTLP──▶ Tempo
Other services ──Zipkin──▶ Tempo
```

**Properties:**
- Simplest possible: one fewer infrastructure component.
- No tail-sampling — Tempo receives all spans as they arrive; sampling is head-only (either 100% on the OTel service or a probabilistic sampler in the SDK).
- No span transformation, filtering, or batching beyond the SDK's built-in batcher.
- Removes the primary motivation for OTel adoption (tail-sampling) but preserves the span-fidelity and OTLP format learning.

**When to choose:** if the Week 11 experiment shows OTLP span fidelity is the portfolio signal and tail-sampling adds disproportionate operational complexity for a lab.

---

### Option B — OTLP → OTel Collector → Tempo (chosen default)

```
Execution Service ──OTLP──▶ OTel Collector ──OTLP──▶ Tempo
Other services ──Zipkin──────────────────────────────▶ Tempo
                                              (direct; Collector is not on their path)
```

**Properties:**
- Tail-sampling at the Collector: 100% of error traces, 1% of success traces.
- Collector is on the hot path for Execution Service spans only. Other services bypass it.
- Failure mode: Collector down → Execution Service spans lost. Mitigated by direct OTLP fallback (see §Implementation Notes).
- Demonstrates the tail-sampling capability that was the primary rationale for OTel exploration (architecture §10.1).

**When to choose (default):** the tail-sampling benchmark is the portfolio demonstration. The Collector adds one Compose service and one YAML file — acceptable lab overhead.

---

### Option C — OTLP → OTel Collector → Tempo + Prometheus remote write

```
Execution Service ──OTLP──▶ OTel Collector ──OTLP traces──▶ Tempo
                                           ──metrics────────▶ Prometheus remote write
Other services ──Zipkin──▶ Tempo (direct)
               ──metrics─▶ Prometheus scrape
```

**Rejected:** doubles the metric pipeline for one service. The Micrometer + Prometheus scrape already works. Adding remote write via the Collector creates two sources of truth for metrics on the Execution Service, which is exactly the "naming convention drift" failure mode identified in architecture §10.4.

---

## Decision: Option B (Collector with tail-sampling)

**Rationale:** tail-sampling is the core capability distinguishing OTel from Micrometer Tracing. If the Collector adds no demonstrable value (i.e., all scenarios complete successfully and no error-trace sampling pressure is visible in the lab), then the Week 11 finding is "tail-sampling does not add value at lab scale" — itself a valid documented result. Option A produces a lesser finding.

## Collector Configuration

```yaml
# otel-collector-config.yml — added to docker-compose_chaosforge.yml as `otel-collector` service
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  tail_sampling:
    decision_wait: 10s         # wait 10s to see if a trace has errors before sampling
    num_traces: 50000          # max traces held in memory during decision window
    policies:
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ERROR] }    # 100% of error traces
      - name: success-sample
        type: probabilistic
        probabilistic: { sampling_percentage: 1 } # 1% of non-error traces
  batch:
    timeout: 1s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 1s
    limit_mib: 256

exporters:
  otlp:
    endpoint: tempo:4317     # Tempo OTLP receiver endpoint
    tls:
      insecure: true         # lab only; mTLS in prod

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters: [otlp]
```

```yaml
# docker-compose_chaosforge.yml addition
otel-collector:
  image: otel/opentelemetry-collector-contrib:0.102.0
  command: ["--config=/etc/otel-collector-config.yml"]
  volumes:
    - ./otel-collector-config.yml:/etc/otel-collector-config.yml
  ports:
    - "4317:4317"     # OTLP gRPC
    - "4318:4318"     # OTLP HTTP
  depends_on:
    - tempo
```

## Failure Mode: Collector Down

If the Collector is unavailable, Execution Service spans are lost (OTLP export will backpressure and eventually drop). Mitigated:

```yaml
# Execution Service application.yml — dual-export with Collector as primary
otel:
  exporter:
    otlp:
      endpoint: http://otel-collector:4317
      # Fallback: if OTLP export fails N times, SDK backs off and drops spans
      # Zipkin is NOT re-enabled on failure — that would produce dual spans
  sdk:
    disabled: false
```

**Accept the loss:** in the lab, losing Execution Service spans when the Collector is down is acceptable. P1 observability (Micrometer + Prometheus scrape) is unaffected. This is explicitly not a load-bearing path.

## Tail-Sampling Benchmark (to document at Week 11)

After running a 1000-scenario suite (mix of successful, timed-out, and STEP_FAILED scenarios):

| Metric | Expected | Actual (fill at Week 11) |
|---|---|---|
| Error traces captured (should be 100%) | 100% | |
| Success traces captured (should be ~1%) | ~1% | |
| Memory used by Collector at peak (`memory_limiter` gauge) | < 256 MiB | |
| Trace latency (time from span emit to visible in Tempo) | < 15s (tail window + batch) | |
| Collector OOM events | 0 | |
| Orphaned spans in Tempo (claim→worker handoff) | 0 | |

The benchmark is the §10.3 deliverable: "a documented benchmark showing tail-sampling cost/benefit on representative ChaosForge traffic."

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| Grafana Tempo in the lab stack has OTLP receiver enabled | REQUIRED | Check the Tempo config's `distributor.receivers.otlp`. If not enabled, add before Week 11. |
| `tail_sampling` processor correctly identifies error traces from OTel `StatusCode.ERROR` | ASSUMED | Verify with an intentionally failed step; trace must appear in Tempo despite 1% success policy. |
| 10s decision window is sufficient for 5-minute scenarios | ASSUMED | Tail sampler holds span data for 10s before deciding. For a 5-min scenario, only the first and last spans matter for error detection. If a scenario fails at step 4 of 10, the error spans arrive within the window. |
| Collector `num_traces: 50000` is sufficient for lab concurrency | ASSUMED | Lab peak: ~50 concurrent scenarios × ~20 spans each = 1,000 active traces. 50,000 is 50× headroom. |
