## Context

A terminology inconsistency crept into `architecture specification` v1.4.0 when Apicurio Schema Registry was introduced: the entry read *"JSON Schema enforcement on chaosforge.scenario.commands.v1."* Meanwhile, every other document in the corpus used the word **Avro** consistently for the wire format and mentioned Avro plugin, Avro encode/decode, and Avro schema compatibility mode `BACKWARD`.

Apicurio Schema Registry supports multiple serialization formats (Avro, JSON Schema, Protobuf). The phrase "JSON Schema enforcement" was accurate as a description of what Apicurio *can* do, but misleading because it implies the serialization format is JSON. The actual serialization format is Avro binary. This ADR resolves the ambiguity by formally confirming the decision and documenting the rejection of JSON Schema serialization.

---

## Decision

**Avro binary is the Kafka wire format for all ChaosForge canonical topics.** Apicurio Schema Registry is used for schema registration, compatibility enforcement, and consumer-side validation — using Avro schemas, not JSON Schema definitions. The producer validates and serializes to Avro before writing to the outbox; the consumer deserializes from Avro at step 1 of the pipeline.

| Property | Value |
|---|---|
| Serialization format | **Avro binary** |
| Schema registry | Apicurio (Redpanda-compatible) |
| Schema type in registry | Avro schema (`.avsc`) |
| Subject naming | `<topic>-value` |
| Compatibility mode | **`FULL_TRANSITIVE`** — superseded by ADR-0527 (was `BACKWARD minimum; FULL preferred`) |
| Producer behaviour | Register schema subject before first send; validate payload against schema; serialize |
| Consumer behaviour | Step 1: fetch schema by subject + version from registry; deserialize; validate shape; `SCHEMA_INVALID` → DLQ (not replayable) |
| Build tooling | **Gradle Avro plugin** (pinned in `gradle/libs.versions.toml`) |
| Outbox payload column | `BYTEA` — Avro-encoded bytes stored at insert time (schema-at-write) |

## Alternatives Considered

### 1. JSON Schema serialization (what the ambiguous phrase implied)

Avro and JSON Schema serve different roles in Apicurio. JSON Schema serialization means the Kafka message payload is a JSON byte string validated against a JSON Schema definition.

**Rejected because:**
- **No compact binary format:** JSON is 3–5× larger than Avro binary for typical message shapes. Irrelevant at lab throughput but inconsistent with the corpus.
- **No native code generation:** JSON Schema does not produce strongly-typed Java POJOs via a build plugin without third-party tooling. The Gradle Avro plugin is the standard here.
- **Weaker schema evolution story:** JSON Schema has no equivalent of Avro's field-default + schema-fingerprint based reader/writer schema resolution. `BACKWARD` compatibility in Avro has precise semantics; in JSON Schema it is policy-level.
- **All existing code assumes Avro:** `avro.encode(...)`, `avro.decode(...)`, Avro builder pattern for `ScenarioRunCommand`. Changing to JSON Schema would require rewriting the entire producer/consumer path.
- The phrase "JSON Schema enforcement" in `architecture specification` was imprecise language, not a decision.

### 2. Protobuf

**Considered for:** compact binary, strong typing, gRPC ecosystem alignment.
**Rejected because:** Apicurio + Redpanda support both Avro and Protobuf, but Avro is the P1 canonical choice (per `kafka-topology-map.md`). Introducing Protobuf in P2 would diverge from the workspace standard for no architectural gain at this scale. Acceptable in a future Tier 3 feature if gRPC fan-out is added.

### 3. Plain JSON (no schema registry)

**Rejected because:** no schema evolution contract; no compatibility enforcement at the registry; consumer silently accepts structural drift. The schema registry is load-bearing for the `SCHEMA_INVALID → DLQ` step 1 guarantee.

## Schema Definitions

Canonical `.avsc` files live in `src/main/avro/` (shared module `chaosforge-avro-schemas`):

```json
// ScenarioRunCommand.avsc
{
  "type": "record",
  "name": "ScenarioRunCommand",
  "namespace": "io.chaosforge.schema.v1",
  "fields": [
    { "name": "scenarioId",       "type": "string" },
    { "name": "tenantId",         "type": "string" },
    { "name": "replayVersion",    "type": "long" },
    { "name": "ruleSetId",        "type": "string" },
    { "name": "ruleSetVersion",   "type": "int" },
    { "name": "steps",            "type": { "type": "array", "items": "Step" } },
    { "name": "commandIssuedAt",  "type": { "type": "long", "logicalType": "timestamp-millis" } }
  ]
}
```

Schema evolution rules:
- Adding a new field: **must have a default value** (`"default": null` or a domain default). This preserves `BACKWARD` compatibility — old consumers can read new records by ignoring the new field.
- Removing a field: **may only remove fields that have a default**. Removing a required field is a `BACKWARD` incompatible change.
- Renaming a field: use `"aliases"` to preserve compatibility. Removing the old name without an alias is incompatible.
- Changing a field type: only widening promotions are compatible (e.g. `int` → `long`).

## Consequences

### Positive

- Consistent with the entire P1/P2 corpus — no terminology split.
- Avro build-time codegen produces type-safe Java classes (Gradle Avro plugin in this repo — the Maven plugin named in earlier drafts is illustrative of the toolchain only, see schema-rules.md); no runtime reflection for serialization.
- `BACKWARD` compatibility mode enforced at Apicurio registration time — incompatible schema changes fail the build/deploy before reaching consumers.
- Compact binary reduces broker storage and network I/O (relevant if throughput claims are benchmarked).

### Negative

- Avro binary is not human-readable in Kafka UI or `kafka-console-consumer`. Use `kafka-avro-console-consumer` with the Apicurio deserializer, or the Apicurio UI's schema-aware viewer.
- Schema evolution mistakes (removing a required field) cause `SCHEMA_INVALID` at the consumer and send the message to DLQ. This is the correct failure mode — but it requires discipline during schema updates.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| Schema subject not registered before producer send | `SerializationException` at producer; outbox insert fails; row not committed | Gradle Avro plugin registers subjects on build; CI gate checks compatibility before deploy |
| Consumer receives a schema version it cannot deserialize (forward-incompatible change) | `SCHEMA_INVALID` DLQ with Avro deserialization error | Enforce `BACKWARD` compatibility at registration; rolling deploy ensures consumer version ≥ producer schema version at cutover |
| Apicurio Registry unreachable at consumer startup | Consumer fails to fetch schema; should fail fast rather than cache stale schema | Configure `auto.register.schemas=false` and a circuit breaker on the schema fetch; alert on registry unavailability |
| Avro schema cached by consumer, registry updated incompatibly | Consumer uses stale cached schema; `SCHEMA_INVALID` on new records | TTL on local schema cache (5m); force refresh on decode error |

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| Apicurio is Redpanda-compatible for Avro subjects | CONFIRMED | Redpanda's schema registry API is Confluent-compatible; Apicurio supports the Confluent API surface used by Avro serializers |
| Gradle Avro plugin generates classes compatible with Boot 4.1.x / Java 21 | ASSUMED | Verify plugin version in `gradle/libs.versions.toml`; generated code uses standard Java types; no known Boot 4 incompatibility |
| Schema fingerprint collision across topics | NEGLIGIBLE | Avro schema fingerprints are per-subject; cross-topic collision has no runtime effect |

## Implementation Notes

- Gradle Avro plugin config in `chaosforge-avro-schemas/build.gradle.kts`, pinned in `gradle/libs.versions.toml`; codegens Java from `src/main/avro/` at build time.
- Apicurio client dependency: `apicurio-registry-serdes-avro-serde`.
- Producer serializer: `io.apicurio.registry.serde.avro.AvroKafkaSerializer`.
- Consumer deserializer: `io.apicurio.registry.serde.avro.AvroKafkaDeserializer`.
- `architecture specification` Known Limitations: the "JSON Schema enforcement" reference has been corrected to "Avro binary" in v1.5.0.

## Amendment (2026-06-14)

**Compatibility mode:** The phrase `BACKWARD minimum; FULL preferred` in this ADR is superseded by
**ADR-0527**, which mandates `FULL_TRANSITIVE` for all ChaosForge canonical topics. Schema evolution
and CI gate rules follow ADR-0527. The compatibility mode table entry above has been updated
to reflect this.

## Amendment 2 (2026-07-15, coverage audit)

**Wire serde:** the Implementation Notes above name `io.apicurio.registry.serde.avro.AvroKafkaSerializer`
/ `AvroKafkaDeserializer` as the producer/consumer serdes. That is **superseded by the implemented
design**: the runtime encodes/decodes with a **local Avro codec** (`SpecificDatumWriter`/reader in
`AvroCommandPayloadCodec` / `AvroResultPayloadCodec`), because encoding runs inside transactions (the
CAS replay critical section; the Phase-3 finalize tx) where registry HTTP is forbidden. Apicurio's role
is CI/build-time only — registration (`avroSchemaRegister`) and compatibility (`avroSchemaCompatibilityCheck`,
C29) — never a per-message runtime call. `docs/adrs/ADR-0527.md` carries the authoritative
correction; these Implementation Notes are the historical record. `apicurio-registry-avro-serde-kafka`
remains a declared-but-unreferenced Gradle dependency from this ADR's original design pass.
