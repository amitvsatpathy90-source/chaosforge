# ADR-0519 — PII Egress Controls for LLM Prompt Construction

**Status:** ACCEPTED
**Date:** 2026-06-13
**Reversal cost:** MEDIUM
**Owner:** Principal Engineering

---

## Context

LLM prompts are a new PII egress surface not covered by existing logging or metrics rules. A tenant's scenario description, target URLs, and `tenant_id` sent verbatim in a prompt to a non-local model would represent a data egress event. Three distinct risks: (1) data sent to a cloud API, (2) `tenant_id` used as a correlation key allowing model providers to link requests, (3) prompt injection — a malicious tenant crafting a description that instructs the model to include another tenant's endpoint in the output.

---

## Decision

Three controls, applied in order of strength:

**Control 1 — Local model default (primary mitigation):** Ollama runs in the Compose stack. Prompts never leave the local network. This eliminates the cloud data-egress risk for the default deployment and the free-tier deploy.

**Control 2 — Redaction before prompt construction:** `tenant_id`, target URLs, and any payload field values are never included verbatim in prompts. Violation shape is described in boolean/magnitude terms only — consistent with the exception-message PII rule (from RPE RPE Decision Record #14 pattern). User-supplied text appears only in the `user()` prompt slot, never concatenated into the `system()` slot.

**Control 3 — Structural injection defence:** The system prompt is static configuration loaded from `classpath:prompts/`. User-supplied text goes into the `user()` slot only. Any instruction in the user text to "override the system prompt" or "ignore previous instructions" is rendered inert by the model's instruction-following hierarchy — the system prompt takes precedence. The tenant-ownership check at the repository layer is the backstop: whatever the model emits, cross-tenant target URLs are rejected regardless.

**Cloud opt-in (developer convenience, not default):** an optional `cloud` Spring profile may wire `spring-ai-ollama`. A `CloudSafePromptBuilder` wrapper enforces Control 2 before any non-local call. This profile is never active in Compose or on the free-tier deploy.

---

## Alternatives

**No redaction (send raw tenant data to model):** In local Ollama default: data stays in-cluster, risk is low. For the cloud opt-in profile: unacceptable without explicit egress control. Rejected for cloud path.

**Disable cloud opt-in entirely:** Simpler. But removes a developer convenience that has zero production risk if correctly profile-gated. Rejected.

---

## Consequences

**Positive:** Local default means PII never leaves the process network by default. Cloud opt-in is a deliberate, documented deviation with an enforcement wrapper.

**Negative:** `CloudSafePromptBuilder` is a convention-enforced control — a developer bypassing it in the cloud profile would silently send raw data. Mitigated by profile gate + code review.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| `tenant_id` verbatim in prompt in cloud profile | Code review of `CloudSafePromptBuilder` usages | ArchUnit: all `ChatClient.prompt()` calls in cloud-profile path go through the builder |
| System prompt loaded from user-controllable source | Static resource path assertion in test | `system-prompt-resource` is always `classpath:` — never a runtime-configurable URL |
