# ADR-0508 — DLQ Failure-Class Taxonomy

**Status:** ACCEPTED — **see Amendment below**
**Date:** 2026-05-20
**Reversal cost:** LOW
**Owner:** Principal Engineering

> **Amendment (architecture specification v1.4.0 / 2026-06-14):** The Kafka header name was renamed from
> `x-failure-class` to **`x-dlq-reason`** and the Micrometer tag was renamed from `failure_class`
> to **`dlq_reason`**. The five class values were also renamed (see mapping in `DLQ policy specifications`).
> All new and edited code uses the names in `DLQ policy specifications`; this ADR is the historical record.

---

## Context

The canonical DLQ pattern routes unprocessable messages to a dead-letter topic. Without a failure-class taxonomy, DLQ messages are opaque to the triage consumer — every failure requires deserialization and log inspection to determine root cause and next action.

---

## Decision

Every message routed to a ChaosForge DLQ carries an `x-failure-class` Kafka header with one of five values:

| Class | Meaning | Suggested action |
|---|---|---|
| `stale-replay-version` | `x-replay-version` ≤ `max_seen` for this scenario | Discard; a later replay superseded this message |
| `tenant-mismatch` | `x-tenant-id` in header does not match scenario's tenant | Security alert; investigate CP bug |
| `schema-violation` | Message cannot be deserialized to target type | Fix schema; replay from source if needed |
| `business-error` | Step execution failed with a non-retryable business condition | Manual triage; inspect step result |
| `infrastructure-error` | Resilience4j CB open / timeout / target unreachable after retries | Investigate infrastructure; replay when target recovers |

The triage consumer logs the `x-failure-class` tag on every DLQ message. Micrometer counter `chaosforge.dlq.depth` is tagged by `{topic, failure_class}`.

---

## Alternatives

**No taxonomy (raw exceptions in DLQ envelope):** Triage requires log inspection for every message. No operational signal without deserialization. Rejected.

**Separate DLQ topics per failure class:** Operational overhead of N×topics. The single DLQ per source topic with header-based classification achieves the same observability. Rejected.

---

## Consequences

**Positive:** DLQ dashboard immediately shows failure distribution without opening individual messages. `stale-replay-version` failures are expected and auto-triageable; `tenant-mismatch` failures page on-call.

**Negative:** The five classes must be kept in sync across CP and Exec. Any new failure mode requires updating both the producer and the triage consumer.

---

## Implementation Notes

- `x-failure-class` header set at the point of DLQ routing (Spring Kafka `DeadLetterPublishingRecoverer` customizer).
- Micrometer: `meterRegistry.counter("chaosforge.dlq.depth", "topic", topic, "failure_class", failureClass)`.
