# ADR-0538 — Steady-State Health Probes Run on an Isolated Short-Timeout Client Inside a Top-Guarded Loop

| Field | Value |
|---|---|
| **ID** | ADR-0538 |
| **Status** | ACCEPTED — implemented (dedicated `probeRestClient`; deadline guarded at top of the probe loop) |
| **Date** | 2026-07-13 |
| **Reversal cost** | LOW (one extra `RestClient` bean + a loop-order change; no wire/schema change) |
| **Deciders** | Principal Engineering |
| **Depends on** | ADR-0533 (steady-state cadence: time-based, multi-host), C19 (aggregate deadline < `max.poll.interval.ms`), C20 (steady-state auto-abort) |

---

## Context

An architecture audit (arch-audit M1) found that the C20 steady-state health probe could overshoot the
aggregate step deadline far enough to trigger a **self-inflicted consumer rebalance**.

Two facts combined:

1. **The probe reused `targetRestClient`** — the client for fault *steps*, whose read timeout is
   deliberately generous (30s) because a fault step may legitimately exercise a slow target. A health
   check has no business waiting 30s: a connected-but-slow (or hanging-after-connect) target makes a
   single probe block for the full 30s read timeout.
2. **The probe loop was under-guarded.** `SteadyStateCheck.breached()` checked the deadline only *before
   the inter-probe sleep*, not before the probe pass itself. `allHealthy()` probes **every distinct
   target host** serially (ADR-0533 made the check multi-host — which is exactly what makes N>1 reachable
   here). So a single `allHealthy()` pass costs up to `N × 30s`, and the loop could enter that pass with
   the aggregate budget already spent.

Failure chain: a slow-but-reachable system under test → each probe eats ~30s → one `allHealthy()` pass
overshoots the 240s aggregate deadline by up to `N × 30s` → at N≥2–3 distinct hosts the overshoot crosses
`max.poll.interval.ms` (300s) → the broker considers the consumer dead → **rebalance** → the in-flight
command is redelivered → its `message_id` is inbox-deduped (ack-skipped) → the run can never finalize and
is eventually swept INCOMPLETE. A single hanging host wastes budget (~one pass) but stays under the poll
interval; the rebalance is the multi-host case.

## Decision

1. **Dedicated probe client (`probeRestClient`).** A separate `RestClient` with short timeouts —
   `chaosforge.steady-state.probe-connect-timeout-ms` (default 1s) and `probe-read-timeout-ms`
   (default 2s) — wired into `HttpTargetHealthProbe`. The step client keeps its 30s read timeout; the two
   concerns no longer share a timeout budget. `SteadyStateGuard` derives the probe URL from the step
   authority, so the SSRF/blast-radius guard (ADR-0534) still applies to the probe unchanged.
2. **Guard the deadline at the top of the loop.** `breached()` checks `now >= deadlineMs` **before**
   calling `allHealthy()`, not only before the sleep. A probe pass is never entered once the budget is
   spent; out of budget → no breach, and the aggregate-deadline control in `ExecutePhase` takes over.

Worst-case overshoot is now bounded to one `allHealthy()` pass = `N × probe-read-timeout` (2s), which
stays well inside the ~60s margin between the 240s aggregate deadline and the 300s poll interval for any
realistic host count.

## Alternatives Considered

- **Reuse `targetRestClient` with a per-call timeout override on the probe.** Brittle — the override is
  easy to drop in a refactor, and the coupling ("why is the health check on the 30s client?") is exactly
  what caused the bug. Rejected in favour of an explicit, separate bean.
- **Bound `allHealthy()` internally, stopping mid-scan when the deadline passes.** Conflates "out of
  budget" with "unhealthy": a partial scan can't confirm all-healthy, and counting it as a failure risks
  a spurious breach/abort. Rejected — the top-of-loop guard yields cleanly without a false signal.
- **Probe only the first host (cap N at 1).** Removes the overshoot but regresses the ADR-0533 guarantee
  that every distinct target host is probed, so a multi-host blast radius could go undetected. Rejected.

## Consequences

- A slow or hanging system under test no longer risks a self-inflicted rebalance; probe cost per boundary
  is bounded and small.
- The healthy path adds one 2s-timeout probe per boundary (a healthy first probe returns immediately).
- Proven by `SteadyStateCheckTest` (an already-expired deadline yields without entering a probe pass) and
  `HttpTargetHealthProbeTest` (real local server: 2xx healthy; 4xx/5xx/refused/timeout unhealthy).
- Enforcement constraint recorded in `Execution Service architecture rules` (probe over
  `probeRestClient`, never `targetRestClient`; keep the top-of-loop deadline guard).
- Residual: the probe still resolves and connects at probe time; the DNS-rebinding TOCTOU discussed in
  ADR-0534 is unchanged and out of scope here.
