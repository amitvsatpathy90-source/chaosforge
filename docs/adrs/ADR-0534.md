## Context

An architecture audit (arch-audit HIGH-2) found that ChaosForge's Execution Service fires HTTP at
tenant-supplied `targetUrl`s with **no host validation** — no scheme check, no private-range block, no
allowlist. `StepExecutor` (and the steady-state `HttpTargetHealthProbe`, which reuses the step
authority) opens a socket to whatever the pinned rule-set contains.

The only guard that existed — `TenantTargetValidator`, with a full SSRF/metadata/RFC1918 block — was
wired **exclusively** into the AI-authoring path (`ScenarioAuthoringService`). The normal creation path
(`RuleSetService.create`) stored the rule-set `definition` verbatim, and execution loaded and called it
verbatim. So any authenticated tenant who created a rule-set through the ordinary API — or any row
written directly to `rule_sets` — could make the executor pod issue requests to `169.254.169.254`
(cloud metadata → credential theft), `localhost`, or any in-mesh / RFC1918 service.

This matters because ChaosForge's *purpose* is to inject faults against a system under test (in this
portfolio, RPE). The injector must have a hard, verifiable ceiling on where it can reach; it did not,
and — unlike RPE, which ships egress NetworkPolicies — the exec service has no network-layer
compensating control.

## Decision

1. **One policy, one implementation.** Extract the SSRF/allowlist logic into a framework-free
   `TargetUrlGuard` in `chaosforge-common` (scheme ∈ {http, https}; optional private-network block
   covering loopback / link-local / site-local / any-local / multicast / the metadata host; optional
   host allowlist). `TenantTargetValidator` now delegates to it, so the AI path and the general path
   share exactly one policy.

2. **Enforce at both ends of the trust boundary.**
   - **Authoring** — `RuleSetService.create` parses the definition, pulls every `targetUrl`, and guards
     it → HTTP 422 on rejection (early, good UX).
   - **Execution** — `CpRuleSetLoader` guards the pinned steps once on cache-load, **outside** the
     circuit-breaker-wrapped CP fetch, so a blocked host is terminal `STEP_FAILED` (a bad definition,
     human review) and is never re-wrapped as a replayable `INFRA_TRANSIENT`. This is the hard control:
     it catches a rule-set persisted before the guard existed or written straight to the DB.

3. **Profile-gated, secure in deployment.** `chaosforge.target.block-private-networks` and
   `allowed-hosts` default off so dev/tests/local-Compose can target `localhost`. The deployed
   (`mtls`) profile turns the private-network block on; operators pin `allowed-hosts` to the sanctioned
   system(s) under test. Blast-radius containment travels with the same profile as mTLS. The AI path
   always blocks private networks regardless of the toggle (an LLM is never trusted to propose a host).

   The **allowlist overrides the private-network block**: a non-empty `allowed-hosts` is the precise
   ceiling, so an operator can sanction an in-mesh RPE ingress (a private IP) to inject faults at it
   while everything else — including metadata and other internal hosts — is still refused. An empty
   allowlist falls back to the coarse public-only SSRF guard.

## Alternatives

**Execution-time check only.** Simpler, but leaves unsafe rule-sets persisted and re-exposes the risk on
every future replay; no early feedback to the author. Rejected — keep both, authoring for UX, execution
for safety.

**Rely on an egress NetworkPolicy alone.** Not present in the Compose deployment, and it cannot stop
lateral hits to legitimately-reachable in-mesh tenant services. A network policy is complementary
future hardening, not a substitute for the application-layer ceiling. Rejected as the sole control.

**Secure-by-default (block on always).** Would break every existing test and local run (they target
`localhost`). The codebase already gates production hardening behind the `mtls` profile (ADR-0531);
matching that convention keeps dev ergonomics and is the least-surprise choice.

## Consequences

- A tenant can no longer aim the executor at internal infrastructure once the deployed profile is
  active; an unsafe target is a 422 at create and a terminal `STEP_FAILED` at execution.
- One SSRF policy to reason about and evolve (`TargetUrlGuard`), enforced in three call sites that all
  delegate to it. Reasons stay shape-tokens (PII rule).
- Deferred (unchanged): per-tenant `tenant_targets` ownership table — `tenantId` remains the contract
  seam, the SSRF block + allowlist is the enforced control. An egress NetworkPolicy on the exec pod is
  recommended defense-in-depth before the C31 staging game day.
- Enforced as an always-apply constraint in `Target validation policy`.
