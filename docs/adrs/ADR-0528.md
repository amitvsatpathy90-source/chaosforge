# ADR-0528: Replay Critical Section — Ownership-First CAS with Idempotent Client Semantics

**Status:** Accepted  
**Date:** 2026-06-17  
**Supersedes:** ADR-0502 (advisory lock — rejected), narrow on ADR-0522 (adds ownership-first ordering, tenant predicate, idempotency, outbox hardening)  
**Depends on:** ADR-0509 (tenant isolation), ADR-0510 (cross-tenant 404), ADR-0522 (CAS mechanism), ADR-0524 (JWT provenance), ADR-0525 (Avro binary), ADR-0526 (partition key), ADR-0527 (FULL_TRANSITIVE), ADR-0508 (DLQ taxonomy)  
**Deciders:** Principal Engineering

---

## Context

`POST /scenarios/{id}:run` is the highest-contention, highest-security write in ChaosForge. It must:

1. Prevent two concurrent replays of the same scenario from both "winning."
2. Enforce tenant isolation such that a cross-tenant request returns an indistinguishable 404 — never a 403, never a 409, and never a version disclosure (ADR-0510).
3. Guarantee the Execution Service receives exactly the rule-set tuple pinned at claim time, not `latest`.
4. Make client retries safe when a success response is lost in transit.
5. Deliver the run command to Kafka via a transactional outbox that is safe for concurrent CP instances and resistant to poison rows.

ADR-0522 established the CAS mechanism and rejected `pg_try_advisory_xact_lock` (ADR-0502). This ADR closes gaps identified in the ADR-0522 design:

- **P0 — enumeration side-channel:** ADR-0522's SQL bumps the version *before* checking tenant ownership. A cross-tenant attacker scanning `expectedVersion` gets 404 when the guess hits the real version, 409 otherwise — disclosing existence and the current version, plus causing a transient cross-tenant write that rolls back.
- **P0 — missing row disambiguation:** A 0-row CAS cannot distinguish "version moved" (409) from "scenario does not exist" (404). That mapping is wrong for non-existent scenarios.
- **P0/P1 — pessimistic degeneration:** While a competing writer's tx is open, the CAS row-lock *waits*. Without `lock_timeout < statement_timeout`, contention surfaces as a 5-second statement timeout → 500, not a fast-fail 409.
- **P1 — client idempotency gap:** `expectedVersion`/`If-Match` solves concurrency; it does not solve "my 202 was lost and I need to retry safely."
- **P1 — outbox production gaps:** No `SKIP LOCKED` → concurrent pollers double-publish. No attempt ceiling → poison rows block the poller forever. No lag metric → a stalled poller is invisible.

---

## Decision

The `initiateReplay` critical section runs **five SQL statements, strictly ordered, inside one `@Transactional` method.** All five commit or roll back atomically.

### Ordering rationale (load-bearing)

Steps 1–2 establish **who you are and whether you own this scenario** before the CAS (step 3) touches any version. This collapses {non-existent, cross-tenant} into one indistinguishable code path that never reaches the CAS — so the 404/409 disambiguation problem is structurally impossible, not just guarded.

### The five steps

```
Step 1  OWNERSHIP + PIN          Tenant-scoped SELECT — proves existence, ownership, yields pinned rule-set tuple.
Step 2  IDEMPOTENCY CLAIM        INSERT … ON CONFLICT DO NOTHING on (tenant_id, idempotency_key).
Step 3  CAS BUMP                 UPDATE with tenant_id + expectedVersion predicate.
Step 4  OUTBOX INSERT            Born PENDING, carries fencing headers + UUIDv7 message_id.
Step 5  IDEMPOTENCY COMPLETE     Stores the result so a replayed POST returns the original token.
```

A throw at any step rolls back all five, including the idempotency claim (failed attempts do not burn the key) and the version bump (a 404/race never mutates state).

## Implementation Contract

### Value objects

```java
package io.chaosforge.controlplane.replay;

import java.util.UUID;
import org.jspecify.annotations.NonNull;

/**
 * All inputs to the critical section. Validated at construction — bad input never reaches the DB.
 */
public record ReplayCommand(
        @NonNull UUID scenarioId,
        @NonNull UUID tenantId,       // Authoritative: from re-verified JWT only (ADR-0524). Never X-Tenant-Id.
        long expectedVersion,         // Client's last-observed replay_version (If-Match header). CAS predicate.
        @NonNull UUID idempotencyKey  // Client-generated per logical attempt. At-most-once guard.
) {
    public ReplayCommand {
        // Compact constructor — same discipline as GeoSnapshot.
        // expectedVersion < 0 is structurally impossible on a valid row; reject pre-DB.
        if (expectedVersion < 0)
            throw new IllegalArgumentException(
                "expectedVersion must be >= 0, got: " + expectedVersion); // -> HTTP 400
    }
}

/**
 * Result of a successful (or idempotently-replayed) claim.
 * fencingToken == new replay_version. Monotonic. Clock-free.
 * outboxMessageId (UUIDv7) correlates this token into the Execution Service consumer span.
 */
public record ReplayToken(
        @NonNull UUID scenarioId,
        long fencingToken,
        @NonNull UUID ruleSetId,
        long ruleSetVersion,
        @NonNull UUID outboxMessageId
) {}
```

### Interface

```java
/**
 * Executes the replay-start critical section.
 *
 * <p>Mutual exclusion: CAS on scenario_replay_state.replay_version (ADR-0522, superseding ADR-0502).
 * pg_try_advisory_xact_lock is FORBIDDEN on this path.
 *
 * <p>Tenant isolation: ownership is established BEFORE the CAS (ADR-0509, ADR-0510).
 * Cross-tenant and absent scenarios produce ResourceNotFoundException -> 404 — indistinguishable,
 * no information leaked about the other tenant's row or version.
 *
 * <p>Idempotency: keyed on (tenant_id, idempotency_key). A replayed POST with a COMPLETED key
 * returns the original ReplayToken without re-executing the CAS.
 *
 * @implSpec Annotate the implementing method @Transactional.
 *           Run per-tx: SET LOCAL lock_timeout='750ms'; SET LOCAL statement_timeout='5s'.
 *           No LLM call, no outbound HTTP, no blocking log inside this transaction (ADR-0518).
 *           The sole writer of scenario_replay_state.replay_version.
 */
public interface ScenarioReplayOrchestrator {

    /**
     * @param command  validated command (scenarioId, tenantId, expectedVersion, idempotencyKey)
     * @return ReplayToken on new claim (202) or idempotent replay (200)
     * @throws IllegalArgumentException    expectedVersion < 0           -> HTTP 400
     * @throws ResourceNotFoundException   absent or cross-tenant        -> HTTP 404 (never 403)
     * @throws ConcurrentReplayException   CAS matched 0 rows            -> HTTP 409 + Retry-After (jittered)
     * @throws IdempotencyKeyInProgressException  key exists, IN_PROGRESS -> HTTP 409 + Retry-After
     */
    @NonNull
    ReplayToken initiateReplay(@NonNull ReplayCommand command);
}
```

### Exceptions

```java
/** CAS matched 0 rows: version moved (concurrent replay or stale expectedVersion). -> 409 */
public final class ConcurrentReplayException extends RuntimeException {
    private final UUID scenarioId;
    private final long expectedVersion;
    // Message: no PII, no raw version disclosure to untrusted callers.
    public ConcurrentReplayException(UUID scenarioId, long expectedVersion) {
        super("Replay version conflict on scenario " + scenarioId
              + ": expected=" + expectedVersion + " did not match current");
        this.scenarioId = scenarioId;
        this.expectedVersion = expectedVersion;
    }
    public UUID scenarioId() { return scenarioId; }
    public long expectedVersion() { return expectedVersion; }
}

/** idempotency_key exists with status=IN_PROGRESS (concurrent duplicate POST). -> 409 */
public final class IdempotencyKeyInProgressException extends RuntimeException {
    public IdempotencyKeyInProgressException(UUID tenantId, UUID idempotencyKey) {
        super("Idempotency key in progress for tenant=" + tenantId); // key not echoed (client already has it)
    }
}

// ResourceNotFoundException — existing shared CP exception. -> 404.
// Used for: cross-tenant AND absent. Callers MUST NOT distinguish the two cases.
```

### SQL — critical section (execute inside one @Transactional method)

```sql
-- Per-transaction timeouts. SET LOCAL scopes to this tx only.
-- lock_timeout < statement_timeout is LOAD-BEARING:
--   lock_timeout = fast-fail on row-lock wait (contention -> 409, not 500)
--   statement_timeout = backstop for a genuinely hung statement
SET LOCAL lock_timeout = '750ms';
SET LOCAL statement_timeout = '5s';

-- STEP 1: OWNERSHIP + PIN
-- Tenant-scoped. Proves existence AND ownership AND yields the pinned rule-set tuple.
-- Empty result -> ResourceNotFoundException -> 404.
-- NOTE: This reads rule_set_id/rule_set_version, NOT replay_version.
-- This is NOT the forbidden "read-then-CAS" pattern. The CAS predicate (step 3)
-- still uses the client-supplied expectedVersion — it is never derived from this read.
SELECT rule_set_id, rule_set_version
  FROM scenario_rule_binding
 WHERE scenario_id = :scenarioId
   AND tenant_id   = :tenantId;

-- STEP 2: IDEMPOTENCY CLAIM
-- Inserts IN_PROGRESS. ON CONFLICT means:
--   - 1 row returned -> new claim, proceed.
--   - 0 rows returned, status=IN_PROGRESS  -> IdempotencyKeyInProgressException -> 409.
--   - 0 rows returned, status=COMPLETED    -> return stored ReplayToken -> 200 (short-circuit, no CAS).
INSERT INTO replay_idempotency (tenant_id, idempotency_key, status)
VALUES (:tenantId, :idempotencyKey, 'IN_PROGRESS')
    ON CONFLICT (tenant_id, idempotency_key) DO NOTHING
RETURNING tenant_id;
-- Application code checks rows-affected and queries status on 0-rows-returned.

-- STEP 3: CAS BUMP
-- tenant_id is in the WHERE as defense-in-depth (ownership already proven in step 1,
-- but belt-and-suspenders at the write prevents any cross-tenant mutation under future
-- code changes that reorder or skip step 1).
-- 0 rows -> ConcurrentReplayException -> 409.
-- 1 row -> RETURNING replay_version is the fencing token for this run.
UPDATE scenario_replay_state
   SET replay_version  = replay_version + 1,
       last_started_at = now()            -- tx-start time; metadata only. Fencing is clock-free.
 WHERE scenario_id    = :scenarioId
   AND tenant_id      = :tenantId
   AND replay_version = :expectedVersion  -- client-supplied; never derived from step 1
RETURNING replay_version;                 -- fencing token

-- STEP 4: OUTBOX INSERT
-- Born PENDING. Carries fencing headers. UUIDv7 message_id for trace correlation.
-- Avro payload (ADR-0525). Schema compatibility: FULL_TRANSITIVE (ADR-0527).
INSERT INTO outbox (
    message_id, scenario_id, tenant_id,
    fencing_token, rule_set_id, rule_set_version,
    payload, status, attempts, next_attempt_at, created_at
) VALUES (
    :msgId,        -- UUIDv7 generated by application
    :scenarioId, :tenantId,
    :newVersion,   -- fencing token from step 3
    :ruleSetId, :ruleSetVersion,
    :avroBytes, 'PENDING', 0, now(), now()
);

-- STEP 5: IDEMPOTENCY COMPLETE
-- Stores the full ReplayToken so a replayed POST (COMPLETED key) can return the original result.
UPDATE replay_idempotency
   SET status             = 'COMPLETED',
       scenario_id        = :scenarioId,
       fencing_token      = :newVersion,
       rule_set_id        = :ruleSetId,
       rule_set_version   = :ruleSetVersion,
       outbox_message_id  = :msgId
 WHERE tenant_id       = :tenantId
   AND idempotency_key = :idempotencyKey;
```

### Schema

```sql
-- scenario_replay_state
-- Row MUST be created in the same transaction as the parent scenario INSERT.
-- FK + CASCADE ensures no orphaned state rows.
CREATE TABLE scenario_replay_state (
    scenario_id     UUID PRIMARY KEY REFERENCES scenarios(id) ON DELETE CASCADE,
    tenant_id       UUID        NOT NULL,
    replay_version  BIGINT      NOT NULL DEFAULT 0 CHECK (replay_version >= 0),
    last_started_at TIMESTAMPTZ
);

-- Backfill for pre-existing scenarios (run at rollout, idempotent):
INSERT INTO scenario_replay_state (scenario_id, tenant_id, replay_version)
SELECT s.id, s.tenant_id, 0
  FROM scenarios s
 WHERE NOT EXISTS (
     SELECT 1 FROM scenario_replay_state r WHERE r.scenario_id = s.id
 );

-- replay_idempotency
CREATE TABLE replay_idempotency (
    tenant_id         UUID        NOT NULL,
    idempotency_key   UUID        NOT NULL,
    status            TEXT        NOT NULL CHECK (status IN ('IN_PROGRESS','COMPLETED')),
    scenario_id       UUID,
    fencing_token     BIGINT,
    rule_set_id       UUID,
    rule_set_version  BIGINT,
    outbox_message_id UUID,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, idempotency_key)
);
-- TTL janitor (e.g. nightly: DELETE WHERE created_at < now() - INTERVAL '24 hours'):
CREATE INDEX idx_idem_gc ON replay_idempotency(created_at);

-- outbox
CREATE TABLE outbox (
    message_id      UUID        PRIMARY KEY,   -- UUIDv7
    scenario_id     UUID        NOT NULL,
    tenant_id       UUID        NOT NULL,
    fencing_token   BIGINT      NOT NULL,
    rule_set_id     UUID        NOT NULL,
    rule_set_version BIGINT     NOT NULL,
    payload         BYTEA       NOT NULL,       -- Avro (ADR-0525)
    status          TEXT        NOT NULL DEFAULT 'PENDING'
                                CHECK (status IN ('PENDING','SENT','DEAD')),
    attempts        INT         NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    sent_at         TIMESTAMPTZ,
    last_error      TEXT
);
-- Poller uses this index exclusively. Partial index keeps it lean.
CREATE INDEX idx_outbox_due ON outbox(next_attempt_at) WHERE status = 'PENDING';
```

## Outbox Poller

### Concurrent-safe row claiming

```sql
-- Each CP instance claims a disjoint batch. No leader election required.
-- SKIP LOCKED: rows locked by another instance are skipped, not blocked on.
SELECT *
  FROM outbox
 WHERE status          = 'PENDING'
   AND next_attempt_at <= now()
 ORDER BY created_at
   FOR UPDATE SKIP LOCKED
 LIMIT :batchSize;   -- recommend 50
```

### Per-row lifecycle

```
claim row (SKIP LOCKED)
  -> publish to Kafka (key=scenario_id per ADR-0526, Avro per ADR-0525)
     -> on broker ACK: UPDATE outbox SET status='SENT', sent_at=now()
                       WHERE message_id=:id   [own short tx + connection]
     -> on failure:    UPDATE outbox SET attempts=attempts+1,
                                        next_attempt_at=now()+backoff(attempts),
                                        last_error=:msg
                       WHERE message_id=:id
                       -- when attempts >= MAX_ATTEMPTS: SET status='DEAD'
                       -- DEAD rows -> alert. NOT the consumer DLQ (ADR-0508). Producer-side only.
```

### Producer config (required)

```yaml
spring.kafka.producer:
  acks: all
  properties:
    enable.idempotence: true
    max.in.flight.requests.per.connection: 5
    delivery.timeout.ms: 120000
```

> **Amendment (2026-07-15, coverage audit):** the implemented producer (both relays — CP command
> outbox and exec result outbox, `KafkaProducerConfig` in each) additionally pins
> **`max.block.ms=2000`** (Kafka default: 60s). A full RecordAccumulator or lost metadata during a
> broker partition makes `send()` itself block, degrading the "async" batch dispatch to serial 60s
> stalls per record. Failing the send fast costs nothing the outbox doesn't already guarantee: the
> row stays PENDING, backs off, and retries from durable state (arch-audit A-2). This is the
> `max.block.ms=2s` bound the architecture specification architecture section references.

### Delivery invariant (stated, not assumed)

Duplicate and out-of-order outbox delivery are **tolerated by fencing + consumer inbox dedup**, not prevented. The consumer's inbox is keyed on `message_id` (UUIDv7); a SENT-flip that fails after a broker ack republishes the same `message_id`, which the inbox dedupes. The fencing token rejects any stale or superseded start. This is the contract that keeps the poller simple — no strict per-scenario ordering, no exactly-once delivery guarantee required at this layer.

## HTTP Contract

### Success

| Condition | Code | Headers | Body |
|---|---|---|---|
| New claim | `202 Accepted` | `Location: /scenarios/{id}/runs/{fencingToken}` `ETag: <newVersion>` | `ReplayToken` |
| Idempotent replay (COMPLETED key) | `200 OK` | `ETag: <originalFencingToken>` | original `ReplayToken` |

### Errors

| Exception | Code | `Retry-After` |
|---|---|---|
| `IllegalArgumentException` (bad input) | `400 Bad Request` | — |
| `ResourceNotFoundException` (absent or cross-tenant) | `404 Not Found` | — |
| `ConcurrentReplayException` (CAS 0 rows) | `409 Conflict` | jittered 1–3 s |
| `IdempotencyKeyInProgressException` | `409 Conflict` | jittered 1–3 s |
| `lock_timeout` exceeded | `409 Conflict` | jittered 1–3 s |

`Retry-After` is jittered (not fixed) to prevent synchronized retry storms. Client implementations MUST cap total retry attempts to avoid livelock.

The `ETag` on a 202 response is the *new* `replay_version`. Clients that wish to trigger a subsequent replay use this value as the next `If-Match`.

## Consequences

### What becomes correct that was not before

- Cross-tenant and absent scenarios return identical 404 with zero version disclosure and zero write side-effect — the CAS is never reached (ADR-0510 fully enforced).
- Contention under live load fast-fails at 750ms as a distinct 409, not a 5s timeout 500.
- Client retries after a lost 202 recover the original token without re-executing the CAS.
- Concurrent CP poller instances drain the outbox without double-publishing.
- A poison outbox row is quarantined after `MAX_ATTEMPTS`; the rest of the outbox drains.

### What becomes harder

- Five SQL statements per request vs. one in the ADR-0522 literal design. At expected concurrency this is negligible; under extreme load profile the `replay_idempotency` and `outbox` inserts add two row writes per request. Index-backed; acceptable.
- Idempotency table requires a TTL janitor (nightly sweep). Operational burden is low; must be monitored.
- `scenario_replay_state` row creation must be coupled to scenario creation. This is a hard invariant: if the row is absent at claim time, step 1 returns empty → 404, which hides a data-integrity failure. Enforce via FK + application-layer discipline, or an `AFTER INSERT` trigger on `scenarios`.

### What is explicitly out of scope

**Superseding a running replay** (not just a stale start): a newer claim does not interrupt an in-flight execution. If that semantic is needed, the consumer must re-check the current fencing token between steps and short-circuit when a newer version is detected. File a separate ADR; do not extend this one.

## Options Considered and Rejected

| Option | Rejection reason |
|---|---|
| `pg_try_advisory_xact_lock` (ADR-0502) | Non-portable, single-writer (no horizontal CP scaling), fencing token must be layered separately. Rejected by ADR-0522. |
| Read-then-CAS in one tx (ADR-0522 §Decision fallback) | Makes the CAS predicate trivially true — 409 can never fire, two concurrent runs both "win." Forbidden by architecture specification and this ADR. |
| CAS without ownership probe | Cannot distinguish 404 from 409 on 0 rows. Leaks version via 404/409 status code difference. Rejected above (P0). |
| CAS + ownership in a single statement (subquery) | Does not close the enumeration window — 0 rows still conflates missing/cross-tenant with version-moved. Ordering matters. |
| Exactly-once outbox delivery | Requires idempotent producer + transactional Kafka producer + consumer in same broker tx. Operationally expensive; fencing + inbox dedup achieves correctness at lower cost. |

## Gap Closure Traceability

| Gap (source: pre-ADR-0528 review) | Closed by |
|---|---|
| P0 — CAS before ownership leaks 404/409 status as version oracle | Steps reordered: ownership probe (step 1) precedes CAS (step 3). Cross-tenant and absent both → identical 404. |
| P0 — Cross-tenant CAS causes transient write then rollback | Ownership probe short-circuits before CAS is reached. No write occurs on a 404 path. |
| P0 — Missing `replay_state` row → wrong 409 | Step 1 (ownership probe) returns empty → 404. FK + same-tx creation + backfill ensure row existence. |
| P0/P1 — Contention degenerate to pessimistic 5s statement timeout → 500 | `SET LOCAL lock_timeout='750ms'` < `statement_timeout='5s'`. Contention → fast-fail 409. |
| P1 — Lost 202, client retry ambiguous | `replay_idempotency` table. COMPLETED key returns original token → 200. |
| P1 — Concurrent CP pollers double-publish | `FOR UPDATE SKIP LOCKED` on outbox poll. |
| P1 — Poison outbox row blocks poller indefinitely | `attempts` ceiling → `DEAD` + alert. Poller continues on remaining rows. |
