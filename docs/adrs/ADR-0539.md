## Context

An architecture audit (arch-audit M3) found a gap between the documentation and the code: both
`architecture specification` and `partitioning-rules.md §1` asserted that a skewed-clock `msg_ts` is rejected at consumer
step 1 by `CommandDecoder.verifyMintClock` — **but the method did not exist.** Doc-ahead-of-code drift on
exactly the invariant the C28 partition scheme cannot self-heal.

The `inbox` is RANGE-partitioned by `msg_ts`, and `msg_ts = UuidUtil.getInstant(message_id)` — the
timestamp embedded in the UUIDv7 `message_id` (this determinism is what makes `(msg_ts, message_id)`
dedup equivalent to `message_id` dedup across redeliveries). A `message_id` minted with a badly skewed
clock therefore yields a far-past or far-future `msg_ts` with **no matching daily partition**, so the row
cascades into the un-droppable `inbox_default` partition. That is the one C28 failure mode with no
self-heal: `cf_drop_partitions_before` matches only `_pYYYYMMDD` children, so a default-partition row is
never purged, and its presence permanently blocks creating that day's real partition — unbounded growth
and the exact autovacuum-free purge guarantee C28 exists to provide, defeated.

The `chaosforge.partition.default_rows` gauge (ADR-0537 makes it alertable) detects the poison *after* it
lands. The design intent (partitioning-rules §1) is to keep it out of the table entirely.

## Decision

Implement `CommandDecoder.verifyMintClock(messageId)` and call it at **pipeline step 1** — alongside Avro
decode and tenant verification, **before any DB write** (before the fence claim and the inbox insert).

- Reject a `message_id` whose embedded UUIDv7 timestamp is outside
  `[now − inbox-retention, now + lookahead]` as **SCHEMA_INVALID → DLQ** (not replayable; human triages
  the clock-skew source).
- The window uses the **same config keys** as the partition create-ahead/drop machinery
  (`chaosforge.partition.inbox-retention-days`, `chaosforge.partition.lookahead-days`), so the validation
  window and the partition coverage can never drift apart: a message that would route to a real partition
  always passes, and one that would hit the default is always rejected.
- A `message_id` that is not a time-ordered UUID (no embedded timestamp — `UuidUtil.getInstant` throws) is
  likewise SCHEMA_INVALID: it is structurally unroutable to a partition.

Step 1 is the correct location because SCHEMA_INVALID precedes fencing (ADR-0523 ordering); rejecting here
means the poison never touches the fence table or the inbox.

## Alternatives Considered

- **Validate in `InboxDao` at insert time.** Later in the pipeline — after the fence write — and it
  couples a persistence component to the DLQ taxonomy. Step 1 keeps the structural check with the other
  step-1 structural checks and rolls back nothing. Rejected.
- **Clamp an out-of-range `msg_ts` into the window.** Corrupts the invariant that `msg_ts` is a pure
  function of `message_id`; a clamped redelivery would land in a different partition than its original and
  silently break inbox dedup. Rejected outright.
- **Rely on the `default_rows` alert + manual repair.** Detects the leak after the fact and requires a
  human to purge an un-droppable row — the manual data repair C28/C31 exist to eliminate. Prevention at
  ingest is strictly better. Rejected.
- **Widen the default partition's handling / make it droppable.** Fights PostgreSQL partitioning
  semantics and still admits a row with no valid daily home. Rejected.

## Consequences

- A clock-skewed or non-time-ordered `message_id` is DLQ'd at step 1 and never reaches the partitioned
  table; the `inbox_default` trap is closed at the source, matching partitioning-rules §1.
- Doc-vs-code drift resolved: the method the docs referenced now exists and behaves as documented.
- Proven by `CommandDecoderTest` (a freshly-minted id passes; a far-future or far-past mint time and a v4
  random UUID are each SCHEMA_INVALID, not replayable).
- Enforcement constraint already recorded in `Partitioning constraints §1` (reject impossible
  `msg_ts` at the source; never move the check downstream of the inbox insert).
- Residual: a legitimately >`inbox-retention`-delayed redelivery is DLQ'd rather than processed — it is
  already past the dedup window (step-level idempotency would absorb it) and the relay-lag SLOs fire long
  before a backlog reaches that age, so this is an acceptable, alertable trade rather than silent loss.
