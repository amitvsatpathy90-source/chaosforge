# ADR-0502 — Replay Engine: Postgres Advisory Lock + Monotonic replay_version + Fencing Tokens

**Status:** ACCEPTED — **SUPERSEDED, see Amendment below**
**Date:** 2026-05-20
**Reversal cost:** HIGH
**Owner:** Principal Engineering

> **Amendment (2026-06-14 / architecture specification v1.4.0):** The Postgres advisory-lock mutex decided here was
> **superseded by ADR-0522** (CAS optimistic lock on `replay_version`), later narrowed by **ADR-0528**
> (ownership-first ordering, idempotency claim, outbox hardening). `pg_try_advisory_xact_lock` must not
> appear anywhere on the replay path — see `Control Plane architecture rules`. This ADR is retained
> as the historical record of that design and of the Redlock-rejection analysis (§Alternatives), which
> ADR-0522 explicitly carries forward unchanged.

---

## Context

A chaos scenario run must be idempotent and replayable: concurrent trigger requests must produce exactly one execution, retried Kafka messages must not re-execute steps, and every outbound target call must carry a token that lets the target reject a duplicate injection. Three distinct problems require a coordinated primitive:

1. **Mutual exclusion at trigger time** — only one `POST /scenarios/{id}/run` wins; concurrent requests return 409.
2. **Monotonic version for consumer-side fencing** — the Execution Service must be able to reject stale Kafka messages without a distributed lock of its own.
3. **Outbound idempotency** — target systems receiving `LATENCY` / `ERROR` / `TIMEOUT` injections must be able to reject duplicate step calls.

---

## Decision

Three-component primitive, all resolved in a single Postgres transaction on the Control Plane:

```sql
BEGIN;
  SELECT pg_try_advisory_xact_lock(hashtext('scenario:' || $scenario_id));
  -- returns false → ROLLBACK; HTTP 409 Conflict
  UPDATE scenario_replay_state
    SET replay_version = replay_version + 1
    WHERE scenario_id = $scenario_id
    RETURNING replay_version;           -- new_version
  SELECT rule_set_id, version
    FROM scenarios WHERE id = $scenario_id;   -- pin at replay-start
  INSERT INTO outbox (..., headers = jsonb_build_object(
    'x-replay-version', new_version,
    'x-tenant-id',      $tenant_id
  ));
COMMIT;
```

**Lock:** `pg_try_advisory_xact_lock` — transaction-scoped, auto-released on commit or rollback. No TTL, no GC-pause zombie window. Returns `false` immediately if lock is held; no blocking wait.

**Fencing token:** `replay_version` propagated as Kafka header `x-replay-version`. Execution Service stores `max_seen_replay_version` per scenario and rejects any message where `x-replay-version ≤ max_seen`. Stale messages → DLQ with reason `stale-replay-version`; no retry.

**Outbound idempotency:** every target call carries `Idempotency-Key: {scenario_id}:{replay_version}:{step_id}`. All three components are required — `scenario_id` alone is insufficient (same scenario, different replay); `scenario_id:step_id` is insufficient (same step, different replay run).

**Rule-set pinning:** `(rule_set_id, version)` captured at the advisory-lock critical section. Execution Service loads by this exact tuple — never "the latest version of rule_set_id". Ensures a replay next week uses the same rules as the original run (ADR-0503 is the append-only guarantee that makes this safe).

**Redlock rejected** — see §Alternatives.

---

## Alternatives

**Redlock (Redis distributed lock):** Rejected per Kleppmann's 2016 analysis. Core problem: no fencing tokens. A process that holds a Redlock can be paused (GC, page fault, OS scheduling) for longer than the lock TTL; the lock expires and another process acquires it; when the first process resumes it believes it still holds the lock and proceeds — two processes believe they hold the lock simultaneously. Redlock provides no mechanism to detect this. The advisory lock + fencing token combination solves this: even if a CP process crashes after committing the `replay_version` bump, the Execution Service's fencing check will reject any message from a stale CP process (its version will be ≤ max_seen). The lock is an efficiency primitive; the token is the correctness primitive.

**Optimistic locking (version field + compare-and-swap):** Could work for mutual exclusion but requires a retry loop at the HTTP layer and does not provide a natural fencing token propagation path into Kafka headers within the same transaction. More complex; no correctness advantage. Rejected.

**Application-level mutex (Hazelcast, Zookeeper):** Adds an infrastructure dependency not otherwise present in ChaosForge. Advisory locks are already available via the existing Postgres instance. Operational complexity with no correctness advantage. Rejected.

## Consequences

**Positive:**
- Lock and fencing token are derived from a single atomic transaction — no window where the lock is held but the token is not yet propagated.
- Lock is auto-released on any outcome (commit, rollback, connection loss) — no zombie lock cleanup path.
- Fencing check at the Execution Service is stateless from the CP's perspective — no coordination on unlock.
- Rule-set determinism falls out naturally from pinning at the critical section.

**Negative:**
- Advisory lock is per-Postgres-instance. Multiple CP instances can coexist safely (each `pg_try_advisory_xact_lock` contends at the DB level, which is correct), but horizontal Postgres scaling (Citus, CockroachDB) requires care around lock-key hashing behaviour. Lab: single Postgres instance — no issue.
- `hashtext()` collision: two different scenario IDs could hash to the same advisory lock key (birthday problem over a 32-bit space). Mitigation: `hashtext('scenario:' || scenario_id)` uses the full string — collision requires two scenarios whose full string representations hash identically. Negligible risk in lab; use `pg_advisory_xact_lock_shared` variants for production scale.
- `pg_try_advisory_xact_lock` returns immediately on contention — this is correct for the 409-on-concurrency requirement, but means no queuing. A burst of concurrent replay requests all fail-fast; only the first wins. Acceptable for a chaos control plane.

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| CP crashes after `replay_version` bump but before outbox insert | Outbox never gets the message; scenario stuck | On restart: outbox poller finds no PENDING row; operator retriggers `POST /scenarios/{id}/run`; new `replay_version` is issued; fencing check at Exec sees higher version — safe |
| Exec receives stale `replay_version` | DLQ message with `x-failure-class: stale-replay-version` | No retry; DLQ triage consumer alerts ops; no action needed unless the gap indicates a CP bug |
| `max_seen_replay_version` table in Exec not persisted across restart | Fencing check misses stale messages post-restart | `max_seen_replay_version` is durable in `chaosforge_exec` Postgres; not in-memory |
| Advisory lock key collision | Two unrelated scenarios block each other | Monitor `pg_stat_activity` for unexpected lock wait; `hashtext` collision is astronomically unlikely in lab |
| Idempotency-Key not forwarded on target retry | Duplicate fault injection on the same step | Resilience4j retry on Execution Service must preserve the `Idempotency-Key` header — enforced in `Execution Service architecture rules` |

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| Single Postgres instance in lab | ACCEPTED | Multi-instance Postgres requires advisory lock scope verification |
| Target systems honour `Idempotency-Key` | INFERRED | If targets ignore the header, duplicate injection occurs; document as a target contract requirement |
| `replay_version` is strictly monotonic within a scenario | ACCEPTED | `UPDATE ... SET replay_version = replay_version + 1` under advisory lock; no concurrent increment possible |

## Implementation Notes

- `scenario_replay_state` table: `(scenario_id UUID PK, replay_version BIGINT NOT NULL DEFAULT 0)`. Row created at scenario creation with `replay_version = 0`.
- `max_seen_replay_version` table in `chaosforge_exec`: `(scenario_id UUID PK, max_version BIGINT NOT NULL)`. Upserted at the fencing check step.
- Integration test: Concurrency Verification — 10 concurrent `POST /scenarios/{id}/run`; assert exactly 1 HTTP 200, 9 HTTP 409, exactly 1 outbox row, exactly 1 Kafka message delivered to Exec.
