# ADR-0516 — RPE-Specific Deviations from ChaosForge Canonical Patterns

## Context

ChaosForge and revenue-protection-engine (RPE) share a workspace and are co-developed. ChaosForge documents the canonical patterns: Postgres-as-source-of-truth, inbox dedup, two-level Caffeine+Redis cache, advisory/CAS replay, Gradle build, Avro wire format, FULL_TRANSITIVE compatibility, and the AI determinism boundary.

RPE shares the same runtime (Spring Boot 4.1.x, Java 21 virtual threads), the same operational discipline (Micrometer, RED metrics, structured logging), and the same AI boundary rule (advisory only, never on the detection path). However, the problem domain — high-throughput payment event stream processing — produces justified deviations in six areas. This ADR enumerates them, explains the rationale for each, and marks which ChaosForge canonical patterns do not apply.

This ADR exists so that a reviewer reading RPE code and comparing it to the ChaosForge design documents does not conclude that RPE is inconsistent. It is intentionally different. Every deviation below was made consciously against the ChaosForge baseline.

---

## Deviation 1 — Primary state store is Redis, not Postgres

**ChaosForge canonical:** Postgres is the source of truth for all domain state. Redis is used only as an L2 cache (two-level cache pattern) and for rate-limit buckets. Cache is best-effort; Postgres is authoritative.

**RPE decision:** Redis owns ALL hot-path state: deduplication, velocity counters, z-score statistics (Welford algorithm), and geo-data. Postgres is touched only for durable correctness: the `outbox` table and `processed_alerts` (and `triaged_alerts` in the triage module). This covers approximately 1% of events (alert events only). Clean events (99%) complete with a single Redis round-trip and never touch Postgres.

**Rationale:** RPE's workload is fundamentally different from ChaosForge's. A payment event stream processing system requires sub-millisecond hot-path decision latency. Postgres on the hot path (even with connection pooling) introduces P99 latency jitter that makes the velocity/z-score detection windows unreliable. Redis Lua atomic scripting provides the correct primitive for the dedup+velocity+z-score+geo detection in a single round-trip.

**Accepted risk:** Redis state is not durable in the same way Postgres WAL is. AOF `appendfsync everysec` means up to 1s of dedup/velocity state is lost on a hard crash (RPE Decision Record #13). This is accepted because: (a) the alert boundary is durable via `processed_alerts` + deterministic UUIDv5 `alert_id`, and (b) the detection pipeline is self-healing — a brief window of re-processed events results in re-detection at worst, which the `processed_alerts` dedup absorbs.

**Reversal cost:** HIGH — the entire hot-path architecture assumes Redis as state store.

## Deviation 2 — Dedup primitive is deterministic UUIDv5 + `processed_alerts`, not canonical inbox

**ChaosForge canonical:** inbox dedup uses `INSERT … ON CONFLICT DO NOTHING` on a `message_inbox` table keyed by `message_id` (UUIDv7 — time-ordered random, assigned at outbox creation). This is the canonical inbox-dedup pattern.

**RPE decision:** RPE uses deterministic UUIDv5 `alert_id` derived from event content (account_id + event_type + timestamp bucket + amount bucket). The `processed_alerts` table deduplicates at the alert boundary: `INSERT INTO processed_alerts(alert_id) ON CONFLICT DO NOTHING`. Within the Redis window (1s AOF interval), Redis dedup catches duplicates before they reach Postgres.

**Why UUIDv5 instead of UUIDv7:**
- UUIDv7 is assigned at outbox-row creation. If the same payment event is replayed from Kafka, it goes through the same detection path, generates the same alert condition, but the outbox assigns a new UUIDv7 — the downstream consumer sees two different `message_id` values for the same alert and processes both.
- UUIDv5 is derived from the event content. The same payment event always produces the same `alert_id`. `INSERT ON CONFLICT DO NOTHING` is idempotent across any number of replays.
- This is the "replay safety" constraint in RPE's Immutable Constraints table: "Random UUIDs break replay safety silently and permanently."

**Why `processed_alerts` instead of `message_inbox`:**
- The canonical inbox tracks message delivery. RPE's dedup requirement is at the alert boundary, not the message delivery boundary. A message (payment event) and an alert (anomaly detected) are different entities. `processed_alerts` makes the semantics explicit.

**Reversal cost:** MEDIUM — changing the ID scheme requires schema migration and replay-safety analysis.

## Deviation 3 — Reactive Lettuce in the hot path (not just the Gateway)

**ChaosForge canonical:** reactive (WebFlux, Project Reactor) is confined to the Edge Gateway. The Control Plane and Execution Service use Spring MVC + virtual threads. No `Mono`/`Flux` in the CP or Exec hot path.

**RPE decision:** RPE uses `ReactiveRedisTemplate` (Lettuce) in the payment event processing hot path. The mandatory constraint `publishOn(laneScheduler)` after every reactive Redis operation is the operational consequence.

**Rationale:** Redis is RPE's primary state store (Deviation 1). Lettuce is inherently reactive — it is the correct client for non-blocking Redis I/O. Using `RedisTemplate` (blocking) would park virtual thread carriers on Lettuce I/O completions, which defeats the purpose of virtual threads for high-throughput event processing. The reactive Redis call is local and bounded; there is no unbounded reactive chain.

**The `publishOn(laneScheduler)` constraint is load-bearing:** without it, the result of a reactive Redis call is processed on the Lettuce I/O thread, which serializes all per-account lane processing onto the I/O thread pool and deadlocks under load (RPE Decision Record #01, Immutable Constraints). This constraint has no ChaosForge analogue because ChaosForge does not use reactive Redis in non-gateway code.

**Reversal cost:** HIGH — the entire per-account lane model relies on this threading model.

## Deviation 4 — Kafka-transactional exactly-once relay (ChaosForge uses idempotent producer + inbox dedup)

**ChaosForge canonical:** outbox relay uses `enable.idempotence=true` (idempotent producer, per-session dedup) and relies on consumer-side inbox dedup for at-least-once + idempotent-apply semantics. No `transactional.id`.

**RPE decision:** RPE's relay uses `transactional.id = RELAY_INSTANCE_ID` (injected from environment, never shared — RPE Decision Record #06) and `isolation.level=read_committed` on the alert consumer. This is Kafka's exactly-once semantics (EOS) producer.

**Rationale:** RPE's relay emits to `payment.alerts` which is consumed by the triage agent and potentially by downstream fraud systems. At-least-once + consumer-side dedup is correct but requires every downstream consumer to implement dedup. EOS at the producer means the relay itself guarantees exactly-once delivery; downstream consumers need no special handling. The `transactional.id` design (RPE Decision Record #06) requires one relay instance per `transactional.id` to avoid producer fencing — enforced via environment injection.

**The `isolation.level=read_committed` on the alert consumer** is a hard requirement for EOS to work correctly. Without it, consumers read uncommitted transaction data from aborted transactions — silently corrupting the dedup guarantee. This constraint has no ChaosForge analogue.

**Reversal cost:** MEDIUM — removing EOS simplifies the relay but requires adding consumer-side inbox dedup to the triage agent and any other downstream.

## Deviation 5 — `synchronous_commit=off` on Postgres writes

**ChaosForge canonical:** all Postgres writes use default `synchronous_commit` behaviour (effectively `on` or `local`). Durability is not traded for write latency anywhere in the ChaosForge data path.

**RPE decision:** outbox batch writes use `SET LOCAL synchronous_commit = off` (RPE Decision Record #12). This accepts a 200ms window where committed rows may not be WAL-flushed on a hard crash.

**Rationale:** Postgres is on the async path in RPE (batched outbox writes after alert detection). The hot path has already committed the Kafka offset and returned by the time Postgres is written. A 200ms loss window means at most one batch of outbox rows is lost on a hard crash. Recovery: the payment events are still on Kafka; they replay through the detection pipeline; the deterministic UUIDv5 `alert_id` ensures `processed_alerts` dedup catches re-detected alerts. The 200ms loss is bounded and self-healing.

**This trade is not available in ChaosForge** because ChaosForge's Postgres writes (CAS, outbox insert) are on the synchronous request path and must be durable for correctness.

**Production note:** the `SET LOCAL` is a single-line change to remove for production deployment (RPE Decision Record #12 §single-line prod fix). It is a conscious lab optimisation, not an architectural commitment.

**Reversal cost:** LOW — remove `SET LOCAL synchronous_commit = off` from the outbox batch writer.

## Deviation 6 — AI integration is agentic tool-calling (ChaosForge uses one-shot BeanOutputConverter)

**ChaosForge canonical:** AI integration uses Spring AI `ChatClient` with `BeanOutputConverter<ScenarioDraft>` for one-shot structured output. A single prompt → a single structured response → `@Valid` gate → persist or reject. No multi-round tool calling. No agent loop.

**RPE decision:** the `rpe-triage-agent` module uses an agentic tool-calling loop with a maximum of 3 rounds. Each round: ChatClient emits a tool-call request (e.g. "fetch transaction history for this account") → the agent executes the tool → the result is fed back → the LLM makes a verdict or calls another tool. Maximum 3 rounds enforced via a loop counter, not LLM trust.

**Shared principle — identical in both systems:**
- LLM is advisory only; never on the detection/replay/delivery path.
- LLM output is always schema-validated before it touches any domain state.
- Full Resilience4j stack (TimeLimiter + CB + Bulkhead + RateLimiter + Retry) on every LLM boundary call.
- Raw event/user data never enters the system prompt (OWASP-LLM01 structural separation).

**Why agentic in RPE and not ChaosForge:**
- ChaosForge authoring: the LLM produces a `ScenarioDraft` from a human description. One round of output is sufficient; the human reviews and edits. More rounds add latency without improving the authoring experience.
- RPE triage: the LLM must synthesise evidence from multiple tool outputs (transaction history, geo data, peer comparison) to produce a triage verdict. A single-shot prompt containing pre-fetched data would require the caller to decide in advance what data to fetch — defeating the purpose of the advisory enrichment.

**The `evidence[]` constraint** (tool-call IDs must be referenced in the verdict) is the RPE equivalent of ChaosForge's `@Valid` gate: the schema validator rejects a verdict that references no evidence, preventing hallucinated triage from reaching `payment.alerts.triaged`.

**Reversal cost:** MEDIUM — reducing to one-shot requires pre-fetching all evidence before the LLM call; possible but reduces triage quality.

## Deviation 7 — Build tool is Maven (ChaosForge uses Gradle)

**ChaosForge canonical (post ADR-0525 + architecture specification v1.6.0):** ChaosForge uses Gradle with `gradle/libs.versions.toml` version catalogue. Avro Gradle plugin registers subjects on `bootRun`.

**RPE decision:** RPE uses Maven (`mvn -q verify`, `mvn spring-boot:run`). All dependency versions pinned; no SNAPSHOT dependencies.

**Rationale:** RPE predates the ChaosForge Gradle decision. The workspace does not mandate a single build tool across all projects. RPE does not use Avro (payment events use Kafka with a different serialization strategy); the Avro Gradle plugin that motivated ChaosForge's Gradle adoption is irrelevant to RPE.

**No alignment required:** this is an intentional workspace-level divergence. If RPE adopts Avro in a future phase, the Gradle migration would be the natural trigger for a build-tool ADR on the RPE side.

**Reversal cost:** LOW — build tool change is mechanical; no architectural consequence.

---

## Deviation 8 — No replay engine, no CAS, no scenario concept

**ChaosForge canonical:** the replay engine (ADR-0522, CAS on `scenario_replay_state.replay_version`, fencing tokens, rule-set pinning) is the architectural centerpiece.

**RPE decision:** RPE has no equivalent. RPE is a stream-processing system: each payment event is an independent detection unit. There is no scenario, no replay_version, no CAS mutex, no fencing token on the hot path.

**The determinism guarantee in RPE** is achieved differently: UUIDv5 `alert_id` makes detection idempotent (same event → same alert_id → `processed_alerts` conflict → skip). The `inbox dedup on alert_id BEFORE the LLM call` constraint is the triage-path equivalent of ChaosForge's inbox dedup.

**Reversal cost:** N/A — the concepts do not apply.

## Summary Table

| Canonical Pattern | ChaosForge | RPE | Deviation Reason |
|---|---|---|---|
| Primary state store | Postgres | Redis | Hot-path latency; detection atomicity |
| Dedup primitive | UUIDv7 inbox `ON CONFLICT` | UUIDv5 `processed_alerts` | Replay safety requires deterministic ID |
| Reactive scope | Gateway only | Gateway + Redis hot path | Redis is primary state; Lettuce is reactive |
| Kafka delivery | Idempotent producer + inbox dedup | EOS (`transactional.id`) | Downstream consumers need no dedup |
| Postgres write durability | Default (full) | `synchronous_commit=off` | Async path; 200ms loss accepted; self-healing |
| AI integration | One-shot `BeanOutputConverter` | Agentic tool-calling loop (≤3 rounds) | Multi-source evidence synthesis required |
| Build tool | Gradle | Maven | Pre-existing; no Avro plugin need |
| Replay engine | CAS + fencing (ADR-0522) | None | Stream processing; no scenario concept |
| AI boundary rule | Advisory only; never on replay path | Advisory only; never on detection path | **Identical principle** |
| Resilience4j boundary | Per outbound integration | Per outbound integration | **Identical principle** |
| Micrometer observability | RED metrics per endpoint | RED metrics per component | **Identical principle** |
| Structured logging + trace_id | Yes | Yes | **Identical principle** |

## What Is NOT a Deviation (shared invariants)

Both systems enforce these identically:
- LLM is advisory only; never on the critical correctness path.
- Full Resilience4j stack on every LLM boundary.
- Raw user/event data never enters the system prompt.
- Structured output schema enforced with a validation gate before any domain state mutation.
- `tenant_id` / `account_id` is never a Prometheus metric label (cardinality discipline).
- No paid infrastructure.
- Lab benchmarks only; no production claims.
