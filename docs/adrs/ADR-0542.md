# ADR-0542 — Standing DLQ-Depth Signal: A Human-Triage Watermark, Not Another Counter

**Status:** ACCEPTED — implemented. CP Flyway `V11` (`dlq_triage_watermark`), `DlqTriageWatermarkDao`,
`DlqDepthGauge` (`chaosforge.dlq.untriaged_depth`), `DlqTriageWatermarkController`
(`PUT /v1/dlq/{topic}/reviewed`, OPERATOR-gated), and the `DlqTriageBacklog` alert. Proven by
`DlqTriageWatermarkIT`, `DlqDepthGaugeIT`, `DlqTriageWatermarkAuthIT` (real Postgres + embedded Kafka)
and the `alerts_test.yml` promtool cases. architecture specification SLIs/SLO now record the signal (§DLT untriaged depth).
**Date:** 2026-07-17
**Reversal cost:** MEDIUM (adds a CP table + one mutating endpoint + a gauge; advisory metadata only —
no wire contract, no Avro/schema change, no business-state migration — but it **relaxes a documented
read-only invariant**, so backing it out means dropping the table, removing the endpoint, and
re-asserting "triage is strictly read-only")
**Depends on:** ADR-0518 (DLQ triage is advisory, read-only), ADR-0519 (triage PII redaction),
ADR-0529 (retry consumer acks hard poison it never republishes — the root cause of lag→0),
ADR-0536 (DLQ triage OPERATOR-gated)
**Owner:** Principal Engineering

---

## Context

The 2026-07-17 architecture audit finding **F5** established that ChaosForge has **no standing-backlog
signal** for the DLQ. Two independent facts combine to make the obvious signals lie:

- **`chaosforge.dlq.routed` is monotonic.** It counts DLQ *routings*, never decrements, and is read
  everywhere as a `rate()` (`ExecutionMetrics.java`; `alerts.yml` `HardPoisonInDLQ`). It answers "how
  many have we ever routed", never "how many are sitting there now". architecture specification's old "DLT depth = 0" SLO
  was unachievable by construction against a counter that never returns to 0 (why it was renamed from
  `chaosforge.dlq.depth`).
- **Kafka consumer-group lag on a `.DLQ` topic reaches 0 with poison still present.** The retry consumer
  (`DlqRetryConsumer`, separate `dlq-retry` group) reads the `.DLQ`, and for a **hard-poison** reason
  (`SCHEMA_INVALID` / `FENCING_VIOLATION` / `STEP_FAILED` / `RETRY_EXHAUSTED`) it `ack.acknowledge()`s
  without republishing (ADR-0529, `dlq-rules.md`). So its group offset advances **past** records it will
  never act on. Kafka also retains records after ack. Lag therefore measures *un-consumed*, not
  *un-triaged* — the two diverge to exactly the records F5 cares about.

Operationally, no one can answer: **"how many poison records are sitting in `chaosforge.scenario.commands.v1.DLQ`
right now awaiting human triage?"** The `HardPoisonInDLQ` alert fires on *arrival rate* — a pulse when a
poison record lands — and is silent thereafter, whether the backlog is 1 record or 10,000, whether it was
triaged an hour ago or never.

**Why a naïve "depth" gauge is wrong — and why the fix is not a metric change.** "Depth" for a triage
queue means "records **not yet dispositioned by a human**". Kafka has no such notion: records are retained
after every consumer acks them, and there is no per-record "reviewed" bit. The only way to express
"un-triaged" is to record, out of band, **how far a human has reviewed** — a triage **watermark** — and
subtract it from the topic's end offset. F5's own note is explicit: *"a true depth gauge needs a
human-triage watermark — a design decision, not a metric tweak."* This ADR is that design decision, and it
carries a real cost that the rest of the document is mostly about: **it makes DLQ triage stateful**, which
today it deliberately is not (ADR-0518: the triage path *"never replays, never acks, never modifies an
offset, never writes state"*).

## Decision

Introduce a **per-`(topic, partition)` human-triage watermark**, persisted in Control-Plane Postgres, and
publish a gauge

```
chaosforge.dlq.untriaged_depth{topic, partition} = max(0, endOffset − max(reviewedOffset, beginningOffset))
```

emitted by the **Control Plane** (which already owns the triage surface, the LLM, and a Postgres +
Flyway). Four parts:

1. **Watermark store — new CP Flyway migration `V11`.** A small table, one row per DLQ `(topic, partition)`:

   ```sql
   CREATE TABLE dlq_triage_watermark (
       topic            text        NOT NULL,
       partition        int         NOT NULL,
       reviewed_offset  bigint      NOT NULL,   -- EXCLUSIVE high-water: all offsets < this are dispositioned
       reviewed_by      text        NOT NULL,   -- audit: the OPERATOR subject that advanced it
       reviewed_at      timestamptz NOT NULL DEFAULT now(),
       PRIMARY KEY (topic, partition)
   );
   ```

   Advance is **monotonic and idempotent**:
   `INSERT … ON CONFLICT (topic, partition) DO UPDATE SET reviewed_offset = GREATEST(reviewed_offset, EXCLUDED.reviewed_offset), reviewed_by = …, reviewed_at = now()`.
   The watermark is CP business metadata, not a Kafka offset — the retry consumer's `dlq-retry` group
   offset is untouched and unrelated.

2. **A new OPERATOR-gated write verb, kept off the read-only triage classes.**
   `PUT /v1/dlq/{topic}/reviewed?partition=N` with body `{ reviewedOffset }`. It lands under `/v1/dlq/**`,
   which `SecurityConfig` already binds to `hasRole("OPERATOR")` — so it inherits the ADR-0536 gate for
   free (a plain tenant token is 403; DLQ metadata is cross-tenant). It lives in a **new**
   `DlqTriageWatermarkController` + repository — **not** in `DlqTriageService` — so that class's
   "*never writes state*" Javadoc and the LLM advisory path stay literally read-only (see Consequences).

3. **Gauge via the established periodic-bean idiom.** A `@Scheduled` CP bean (same shape as
   `PartitionMaintenance`'s `default_rows` gauge) refreshes, per configured `*.DLQ` topic and partition:
   `endOffset` and `beginningOffset` via a **read-only** `KafkaConsumer` — no `group.id`, `assign` +
   `endOffsets`/`beginningOffsets` only, exactly the `DlqRecordReader` discipline (structurally cannot
   commit) — and `reviewedOffset` from the table. It writes each result into an `AtomicLong` that a
   registered `Gauge` reads, so Prometheus scrapes never trigger a broker round-trip. Cardinality is
   bounded: 1 command DLQ × `dlq-partitions` (default 12) = 12 series. **No `dlq_reason` label** (see
   Alternatives 1) and **never** a `tenant_id` label.

4. **Alert + runbook.** A `DlqTriageBacklog` rule on
   `chaosforge_dlq_untriaged_depth{job="control-plane"} > <N> for 1h`, pointing at the existing
   `docs/runbooks/dlq-and-outbox.md`. This is the standing-level signal to pair with the existing
   arrival-rate `HardPoisonInDLQ`.

**`reviewedOffset` semantics are exclusive-high-water**, mirroring a Kafka committed offset: all offsets
`< reviewedOffset` are reviewed. The `beginningOffset` clamp keeps records already deleted by DLQ log
retention from being counted as backlog (they are gone, not awaiting triage — with the retention caveat in
Consequences). Depth is clamped `≥ 0` so a watermark momentarily ahead of a stale cached `endOffset` reads
0, not negative.

## Alternatives Considered

1. **Break depth down by `dlq_reason` on the gauge (as F5's framing and this task's brief both suggested).**
   **Rejected — not soundly computable from offsets.** `dlq_reason` is a *per-record header*; a single
   partition interleaves all reasons. `endOffset − reviewedOffset` is an offset arithmetic that cannot be
   partitioned by a per-record attribute without **reading the records** in `[reviewedOffset, endOffset)`
   and tallying by header — an `O(depth)` scan on every refresh, pathological *exactly* when the backlog is
   large, i.e. the one time the number matters. And it is largely redundant: **per-reason arrival** is
   already `chaosforge_dlq_routed_total{dlq_reason}` (`rate()`), and hard-poison arrival is already
   `HardPoisonInDLQ`. The standing signal that is genuinely missing is a **level**, and
   `(topic, partition)` is a sufficient grain to page on ("N awaiting triage on `commands.v1.DLQ`"). We
   deliberately ship the sound `(topic, partition)` gauge, not an `O(depth)` per-reason scan. *(This is a
   correction to the task's suggested `topic/partition/dlq_reason` grain, recorded here rather than
   silently narrowed.)*

2. **Use Kafka consumer-group lag on the `.DLQ` topic as the depth proxy.** **Rejected — this is precisely
   the disproven idea in F5.** The `dlq-retry` group acks hard poison it never republishes (ADR-0529), so
   its lag → 0 with poison still in the topic. Lag measures un-consumed, not un-triaged; the whole reason
   F5 exists is that these differ.

3. **Auto-advance the watermark inside `DlqTriageService` on each triage GET (a "viewed = reviewed" model).**
   **Rejected on two counts.** (a) It would make the **LLM read path itself stateful**, breaking ADR-0518 /
   `ai-rules.md` literally, not just in spirit. (b) "An operator asked the AI for a hypothesis on this
   offset" is **not** "a human dispositioned this record" — auto-advancing would mark records reviewed that
   were merely glanced at through the advisory endpoint, defeating the definition of the queue. Disposition
   must be an **explicit** human act on a **separate** verb.

4. **A dedicated compacted Kafka "triage-state" topic keyed by `(topic, partition, offset)`.**
   **Rejected on complexity budget.** CP already owns Postgres; a single upserted row is far cheaper than a
   new compacted topic plus a consumer to materialize it into queryable state, and it avoids a second source
   of truth. This would be justified only if triage state had to be consumed by services other than CP,
   which it does not.

5. **Route each `dlq_reason` to its own `.DLQ` subtopic, so per-subtopic offset arithmetic yields
   per-reason depth "for free".** **Rejected — large blast radius for a reporting nicety.** It changes the
   DLQ topology touched by the recoverer, the retry consumer, and the same-index partition-routing contract
   (arch-audit L1, `KafkaTopicsConfig`), and multiplies topic/partition count. Not worth it to avoid one
   Postgres column.

6. **Do nothing — keep only the rate counter and document the gap.** **Rejected.** "How many are awaiting
   triage right now" is a legitimate operational question with no answer today; a runbook step that says
   "consume the topic and count by hand" is not an SLO. F5 is a real observability hole.

## Consequences

**Positive:**

- The standing-backlog question is **answerable and alertable for the first time** — F5's gap closes, and
  architecture specification's SLO table can finally carry a depth-level signal (once implemented) alongside the
  arrival-rate one.
- **Reuses existing idioms, adds no dependency:** the read-only `KafkaConsumer` (`DlqRecordReader`), the
  periodic-gauge `@Scheduled` bean (`PartitionMaintenance`), the `/v1/dlq/**` → `OPERATOR` gate
  (ADR-0536), CP Postgres + Flyway. Bounded cardinality (12 series), no `tenant_id` label.
- **The two load-bearing invariants are preserved.** (i) The **Kafka-read-only** guarantee is intact —
  nothing here acquires a `group.id`, commits, acks, replays, or modifies a Kafka offset; the watermark is
  a CP row. (ii) The **AI-advisory-only** guarantee (`ai-rules.md`) is intact — the LLM path still only
  advises; the new stateful action is a *non-AI* operator verb on a separate class.

**Negative:**

- **DLQ triage becomes stateful — this is the headline cost.** Today the triage surface is *uniformly*
  read-only, and ADR-0518 / `ai-rules.md` / the class Javadocs assert "*never writes state*" as a blanket
  property. After this ADR that blanket statement is false: one mutating verb joins the surface. The claim
  must be **re-scoped** in those docs to "**the AI advisory path** never writes state; the operator
  watermark-advance verb does (to CP Postgres, never to Kafka)". A reviewer can no longer assume "anything
  under DLQ triage is read-only" — they must distinguish the GET (LLM, read-only) from the PUT (operator,
  stateful). Confining the write to a new controller/repository limits, but does not eliminate, this.
- **The watermark is a human-asserted trust boundary, and advancing it lowers the gauge.** Marking records
  reviewed *is* the thing that shrinks depth — so a mistaken or malicious "mark everything reviewed" can
  **silence the `DlqTriageBacklog` alert without any real triage**. The only mitigations are the
  `OPERATOR` gate, the monotonic advance, and the `reviewed_by` / `reviewed_at` audit columns. The gauge
  reports what an operator *claims* to have reviewed, not what was actually dispositioned — state that
  plainly in the runbook; do not present the number as ground truth.
- **Depth is `(topic, partition)`-grained, not per-`dlq_reason`** (Alternative 1). An operator sees "N
  awaiting triage on this partition", not "N `SCHEMA_INVALID` vs M `STEP_FAILED`". Per-reason insight stays
  on the arrival-rate counter.
- **Kafka retention can evict un-triaged poison below the clamp.** If DLQ `retention.ms` deletes records
  with offset `< reviewedOffset`… fine (already reviewed); but records deleted while still **un-reviewed**
  (`beginningOffset` overtakes `reviewedOffset`) vanish and the gauge under-counts — poison silently lost.
  Therefore **DLQ retention must exceed the triage SLA**, and a follow-up signal (alert when
  `beginningOffset > reviewedOffset`: "un-triaged records aged out") is worth adding but is out of scope
  here.
- **A single monotonic high-water assumes roughly in-order triage.** If an operator dispositions offset
  100 but not 50, the watermark cannot advance past 50, so 50–99 still read as backlog until 50 is handled.
  Acceptable for a coarse level gauge; a per-record disposition model would be needed for out-of-order
  precision, and is not justified.
- **The signal is only as good as operator adoption.** Until the operator tooling actually records reviews,
  every watermark sits at 0 and the gauge reports full-topic depth. That is honest (nothing has been
  triaged) but means the number is a process signal, not a purely mechanical one.
- **New CP persistent state and a periodic broker read.** `V11` adds a table; the `@Scheduled` refresh does
  a bounded, read-only `endOffsets`/`beginningOffsets` call per DLQ topic on an interval — the same cost
  profile as the existing triage reader, on a timer rather than per-request.
