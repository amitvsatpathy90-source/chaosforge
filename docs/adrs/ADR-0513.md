## Context

A single OTel stretch experiment was carved out: introduce `opentelemetry-spring-boot-starter` on exactly one ChaosForge service — the Execution Service — and measure whether it earns its operational complexity over the existing Micrometer Tracing + Brave/Zipkin baseline. ADR-0507 fixed the scope to the Execution Service only.

The experiment is planned for Week 11. This ADR captures the decision frame now so that the game day produces a documented outcome rather than an informal conclusion. The Week 11 engineer writes **one word** into the Status field above and fills the Outcome section below.

---

## Experiment Design (to run at Week 11)

**Baseline (already in place):**
- Micrometer Tracing + Brave on all three ChaosForge services
- Zipkin-format traces exported directly to Grafana Tempo
- Prometheus scrape for metrics

**Experiment (Execution Service only):**
1. Add `io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter` to Execution Service.
2. Configure OTLP export to the same Tempo cluster (OTLP receiver enabled alongside Zipkin).
3. Keep Brave/Zipkin export live — dual-export metrics, OTel-only for spans (no dual-span to avoid parent-child confusion in Tempo per architecture §10.4).
4. Run the Week 11 self-chaos suite (concurrent replays, kill-switch test, reaper test) while observing both pipelines.

**Measurements to collect:**

| Measurement | Method |
|---|---|
| Startup time delta | Compare `ApplicationStartedEvent` timestamp with and without OTel starter |
| Memory overhead | Heap diff at steady-state (50 concurrent scenarios, 10 min) |
| Span fidelity | Manually verify Tempo shows correct parent-child for: claim tx → worker handoff → step execution → result tx |
| Tail-sampling value | Run OTel Collector with 100% error / 1% success policy; compare sampled traces vs Brave head-sampling for a 1000-scenario run |
| Metric name drift | Enumerate OTel `http.server.request.duration` vs Micrometer `http.server.requests`; document every mismatch |
| Operational cost | Time to set up OTel Collector (minutes); number of config files added; Grafana dashboard changes needed |

**Success criteria (for ACCEPT-ADOPT):** all of:
- Tail-sampling produces visibly better trace coverage for error scenarios with <5% overhead vs head-sampling baseline
- Span hierarchy is correct in Tempo (no orphaned spans, no missing parent links across thread handoffs at claim→worker boundary)
- No metric name drift that requires Grafana dashboard rewrites for existing P1-inherited dashboards
- Startup time delta < 500ms; memory overhead < 30MB heap at steady-state

## Decision Branches

### Branch A — ACCEPTED-ADOPT

**Trigger:** all four success criteria above are met at Week 11.

**Decision:** Retain `opentelemetry-spring-boot-starter` on the Execution Service. Remove Brave/Zipkin from the Execution Service only (dual-export period ends). Produce the migration playbook in the workspace. Trigger ADR-0514 (collector configuration).

**What this changes:**
- Execution Service: OTel SDK as the tracing provider; Micrometer still provides metrics (OTel metrics bridge active).
- Gateway and Control Plane: unchanged; Brave/Zipkin remains.
- ADR-0507: updated to reflect the experiment outcome.

**What this does NOT change:**
- No other service migrates without a separate ADR amendment.
- No P1 workspace service touches OTel.
- Micrometer stays as the metrics layer on all services; OTel Bridge emits the same metric names.

---

### Branch B — ACCEPTED-STAY

**Trigger:** one or more success criteria fail, OR the operational cost is judged disproportionate to the portfolio signal.

**Decision:** Remove `opentelemetry-spring-boot-starter` from the Execution Service. Execution Service reverts to Brave/Zipkin-only tracing (clean state; no residual OTel config). Document the specific failure mode(s).

**What this changes:**
- Execution Service: reverts to identical observability posture as Gateway and Control Plane.
- ADR-0507: updated with finding; scope remains Execution Service only for any future retry.
- ADR-0513 status: updated to ACCEPTED-STAY.

## Validating Assumptions

| Assumption | Type | Invalidator |
|---|---|---|
| OTel + Brave dual-export can coexist without duplicate spans | ASSUMED | If both emit spans for the same operation, Tempo shows duplicate traces. Mitigated by using OTel-only for spans; Brave retained for metrics bridge only during experiment. |
| OTel Collector does not become a single point of failure | REQUIRED | Direct OTLP-to-Tempo path active alongside Collector path during experiment. If Collector dies, traces still reach Tempo. |
| The claim→worker thread handoff produces a valid OTel span context propagation | ASSUMED | Virtual thread handoff with `Context.wrap()` is the standard pattern; verify with a single-scenario smoke trace before running the full suite. |
| Tempo OTLP receiver is available in the lab Grafana stack | REQUIRED | Verify `docker-compose_chaosforge.yml` Tempo config has `otlp` receiver enabled before Week 11. |

## Implementation Notes (pre-filled for Week 11 engineer)

**Dependency to add (experiment phase):**
```gradle
// execution-service/build.gradle — experiment branch only
implementation "io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter:${otelVersion}"
```

**Config (execution-service/src/main/resources/application.yml):**
```yaml
management:
  tracing:
    enabled: false         # disable Brave/Zipkin during OTel experiment
otel:
  exporter:
    otlp:
      endpoint: http://localhost:4317
  service:
    name: chaosforge-execution-service
  traces:
    sampler: always_on     # 100% during experiment; tail-sampling is at Collector
```

**Thread handoff context propagation (critical for claim→worker):**
```java
// Wrap Runnable with current OTel Context before submitting to worker pool
Context currentCtx = Context.current();
scenarioWorkerPool.submit(currentCtx.wrap(() -> worker.execute(cmd)));
```

Without `Context.wrap()`, the worker thread has no span context and all worker spans appear as root spans in Tempo — a clear FAIL for the span-fidelity criterion.
