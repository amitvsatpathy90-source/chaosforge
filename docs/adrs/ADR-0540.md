# ADR-0540 — Gateway Rate Limiting: Redis Lua Sliding Window, Globally Consistent, Fail-Open

**Status:** ACCEPTED
**Date:** 2026-07-15
**Reversal cost:** LOW (limiter is filter-local; no schema, no wire contract)
**Depends on:** ADR-0500 (WebFlux gateway; its token-bucket Context wording is amended), ADR-0537 (fail-open observability)
**Owner:** Principal Engineering

---

## Context

The Edge Gateway is the sole public ingress; per-tenant rate limiting is its first line of
blast-radius control. The limiter must be **globally consistent** across gateway pods (a per-pod
limit multiplies the effective ceiling by pod count), **atomic** under concurrent requests in the
same millisecond, and **Redis Cluster-safe** (every key a script touches must be declared and
co-located).

ADR-0500's Context described this as "Redis token-bucket rate limiting" — an early sketch. What was
actually implemented is a sliding window (`edge-gateway/src/main/resources/scripts/sliding_window.lua`
driven by `RateLimitWebFilter`), and no ADR ever recorded that choice or its fail-open failure mode.
The 2026-07-15 coverage audit flagged both as undocumented decisions; this ADR is the **backfill
record** of the implemented mechanism, not a new design.

## Decision

Per-tenant rate limiting is a **Redis Lua sliding window**: one script atomically prunes the window
(`ZREMRANGEBYSCORE`), counts (`ZCARD`), and admits (`ZADD` with an `INCR`-derived unique member) against
a single shared per-tenant key pair — `{tenant:<id>}:rate` / `{tenant:<id>}:rate:seq`, hash-tagged and
both declared via `KEYS` — so the limit is true-global and burst is bounded by the configured limit,
not N × limit. On breach the gateway returns `429` with `Retry-After` set to the window length in
seconds. On any Redis failure the limiter **fails open** — availability over rate-limit correctness —
and the failure is never silent: WARN log + `chaosforge.gateway.rate_limit{outcome="fail_open"}`,
alerted by `RateLimitFailingOpen` (ADR-0537).

## Alternatives Considered

- **Token bucket (the ADR-0500 sketch)** — burst-above-steady-rate is the token bucket's defining
  feature; ChaosForge wants a hard per-window ceiling ("burst = configured limit"). It also needs two
  atomically-coupled values (token count + last-refill timestamp) where the ZSET window needs one
  structure, and "N requests per rolling window" is the semantics operators actually configure and
  reason about. Rejected.
- **Fixed-window counter (`INCR` + `EXPIRE`)** — cheapest option, but admits up to 2× the limit across
  a window boundary (full quota at the end of one window + full quota at the start of the next). The
  ZSET sliding window closes that at bounded memory (≤ limit entries per tenant). Rejected.
- **Per-pod in-memory limiter (Resilience4j `RateLimiter` / Caffeine)** — no Redis dependency, but not
  globally consistent: N gateway pods yield an effective N × limit, and the ceiling silently rises with
  every scale-out. Rejected.
- **Fail-closed on Redis failure** — correct limits or no traffic. The gateway is the sole ingress, so
  fail-closed converts a Redis outage into total unavailability for every tenant. Rejected: fail-open
  with mandatory observability (ADR-0537) trades bounded abuse exposure for availability.

## Consequences

**Positive:**
- The configured limit is the real global ceiling — pods share one key, so scale-out never inflates it.
- Single-script atomicity: no read-modify-write race; same-millisecond requests all count (unique
  `seq` members).
- Cluster-safe by construction: hash-tagged keys, all declared in `KEYS`, verified same-slot.
- The limiter's own failure mode is observable and alertable, not silent (ADR-0537 discipline).

**Negative:**
- Redis is a rate-limiting SPOF: during a Redis outage there is **no rate limiting at all** (fail-open,
  single-instance lab Redis — disclosed in Known Limitations). The compensating control is detection
  (`RateLimitFailingOpen`), not enforcement.
- ZSET memory is O(limit) per active tenant per window — costlier than a token-bucket counter pair;
  acceptable at lab tenant counts, budget before any high-tenant-cardinality deployment.
- `Retry-After` is coarse (the full window length, not the precise next-free-slot time), so
  well-behaved clients back off longer than strictly necessary.
