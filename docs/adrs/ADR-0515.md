## Context

ADR-0515 is a pre-structured decision record. Its purpose is to ensure that Week 12 game-day findings produce documented architectural decisions rather than informal hotfixes. The game day is scheduled for Week 12. Each game-day hypothesis below maps to a potential ADR decision. The engineer running the game day fills in the Outcome column for each hypothesis; any hypothesis that produces a concrete change to the canonical patterns gets its own decision block written into §3.

This is not a placeholder — the decision frame is fully specified. The actual decisions are correctly deferred because they depend on empirical observation.

## 1. Game-Day Hypotheses and Decision Triggers

### H1 — Steady-state guard false-positive rate under normal load

**Test:** run 100 scenarios against a target with synthetic baseline variance (±15% error rate natural jitter). Observe how often the auto-abort circuit fires incorrectly.

| Outcome | Decision triggered |
|---|---|
| False-positive rate > 5% | Raise `autoAbortThreshold` default; add a warm-up window (e.g. 30s baseline settling before guard activates) |
| False-positive rate ≤ 1% | Defaults confirmed; no change |
| False-positive rate 1–5% | Add per-scenario configurable threshold |

### H2 — Reaper grace window adequacy under GC pause

**Test:** induce a 30s GC pause on the Execution Service worker JVM (using `jmap -histo` pressure or explicit `System.gc()` under `-XX:+ExplicitGCInvokesConcurrent` disabled). Verify reaper does not falsely mark in-progress runs as STUCK.

| Outcome | Decision triggered |
|---|---|
| Reaper fires at 10 min grace, GC pause ≤ 30s — no false STUCK | Grace window confirmed adequate |
| GC pause causes false STUCK | Increase grace window from 10 min to `max(maxDurationSeconds × 1.5, 15 min)` |
| GC pause + Kafka rebalance causes double-execution | Verify Phase 1 inbox dedup is effective; if not, tighten the inbox retention / dedup window |

**Fill at Week 12:**
- Observed false STUCK under 30s GC pause: `[ ] yes` / `[ ] no`
- Decision: `[ ] grace window confirmed` / `[ ] increase to ___ min`

### H3 — Kill switch delivery latency under control-source DB load

**Test:** under 50 concurrent scenarios running, write a HALT to the control-source DB. Measure time from HALT write to last worker emitting a terminal event.

| Outcome | Decision triggered |
|---|---|
| All workers HALT within 5s | Poll interval (2s) confirmed sufficient |
| Some workers HALT 5–15s late | Reduce poll interval to 1s; evaluate CPU cost |
| Workers exceed 15s | Investigate worker blocked in step; verify Resilience4j step timeout is firing; may require reducing `timeoutDuration` on target calls |

**Fill at Week 12:**
- P99 HALT delivery latency: _____ s
- Decision: `[ ] poll interval unchanged` / `[ ] reduce to 1s` / `[ ] investigate blocked step`

### H4 — Outbox partition-drop during live traffic

**Test:** run 20 concurrent scenarios. Simultaneously run the maintenance job that drops the previous week's outbox partition. Measure: any message loss? Any consumer errors?

| Outcome | Decision triggered |
|---|---|
| No message loss; no errors | Partition-drop approach confirmed safe under live traffic |
| Lock contention on `outbox` during DROP | Add `CONCURRENTLY` (Postgres 17+) or schedule drops during low-traffic windows |
| Active-partition confusion (rows routed to wrong partition) | Verify the maintenance job creates the next partition before the old one fills; add assertion |

**Fill at Week 12:**
- Message loss observed: `[ ] yes` / `[ ] no`
- Lock contention observed: `[ ] yes` / `[ ] no`
- Decision: `[ ] approach confirmed` / `[ ] schedule for off-peak` / `[ ] investigate routing`

### H5 — Schema Registry unavailability under experiment traffic

**Test:** kill the Apicurio Schema Registry container while 10 scenarios are running. Measure consumer behaviour: does the pre-warmed schema cache allow continued processing? How long before the cache misses?

| Outcome | Decision triggered |
|---|---|
| Consumers process all in-flight scenarios from cache; no new schema version needed → zero impact | Pre-warm approach confirmed; document TTL as sufficient |
| Cache miss occurs within < 5 min | Increase cache TTL; pre-warm more aggressively (fetch all registered versions, not just pinned) |
| Consumer CB opens and routes to DLT under cache miss | CB configuration confirmed correct; registry HA becomes a formal requirement before any production use |

**Fill at Week 12:**
- First cache miss observed at: _____ min after registry down
- Decision: `[ ] TTL confirmed` / `[ ] increase TTL to ___` / `[ ] registry HA = hard gate`

## 2. Findings That Do NOT Produce New ADRs

Some game-day findings are operational tuning, not architectural decisions. These go into runbooks or configuration files, not ADRs:

- Specific JVM GC settings that reduce pause duration
- Prometheus alert threshold tuning
- Grafana dashboard layout adjustments
- Docker Compose memory/CPU limit tuning
- Specific Resilience4j timeout values (unless the change contradicts an existing ADR)

If a finding contradicts an existing ADR's rationale (e.g. H3 shows the kill switch poll interval must be 500ms, contradicting the 2s choice documented in architecture §12.2), that finding **does** produce an ADR amendment.

## 4. If a Finding Requires a New ADR

If any hypothesis produces a cross-cutting finding that doesn't fit as an amendment to an existing ADR, write a new ADR starting from ADR-0528. Reserve nothing below that — the finding determines the content.

Examples of findings that would merit a standalone ADR:
- A new canonical pattern for chaos experiment result storage (H4 produces unexpected data model)
- A new resilience primitive not covered by existing Resilience4j config (H3 requires a novel circuit-breaker shape)
- A change to the partition strategy based on observed hot-partition behaviour (not currently hypothesised)
