# ADR-0504 — Edge Gateway Uses L1-Only Cache (No Redis L2)

**Status:** ACCEPTED
**Date:** 2026-05-20
**Reversal cost:** LOW
**Owner:** Principal Engineering

---

## Context

The Edge Gateway needs cached access to tenant policies and JWT public keys to avoid a Control Plane round-trip on every request. The standard ChaosForge two-level cache uses Caffeine L1 + Redis L2 + Kafka invalidation broadcast. The gateway is reactive end-to-end (ADR-0500), which creates friction with the L2 wiring.

---

## Decision

The Edge Gateway runs **Caffeine `AsyncLoadingCache` (L1) only**. No Redis L2 is wired. No Kafka invalidation consumer runs in the gateway process.

Rationale: wiring L2 into the gateway requires a reactive Kafka consumer for cache invalidation events and a reactive Lettuce path for L2 reads/writes — both in addition to the existing rate-limit Lettuce path. The marginal hit-rate gain from L2 does not justify the added reactive-context-propagation complexity for entities (tenant policies, JWT keys) that are long-lived and rarely mutated.

**Accepted trade-off:** cross-pod L1 variance for a brief window after a write. Each gateway pod has its own L1; a rule-set update propagates only when pods' L1 TTLs expire. Mitigated by long TTL on these entities and low mutation frequency.

---

## Alternatives

**Full L1+L2 (same as CP/Exec):** Correct and consistent. But adds reactive Lettuce L2 path + reactive Kafka consumer for invalidation into the gateway — significant complexity for entities that change rarely. Rejected.

**No cache (always hit CP):** Every gateway request adds a CP round-trip. Acceptable at low scale; unacceptable at the target RPS demonstration. Rejected.

---

## Consequences

**Positive:** Simpler gateway code; no Kafka consumer in the gateway process; one fewer Redis key namespace.

**Negative:** Cross-pod cache inconsistency window = L1 TTL. An updated tenant policy may be served stale by a gateway pod until its L1 expires. Acceptable for the lab; production would require the full L1+L2 pattern.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| Stale gateway cache after policy update | Manual test: update policy, verify stale serve window = L1 TTL | Set TTL ≤ acceptable stale window |

---

## Implementation Notes

- `AsyncLoadingCache<String, TenantPolicy>` via Caffeine. `maximumSize`, `expireAfterWrite`, `refreshAfterWrite` configured in `application.yml`.
- Loader delegates to `WebClient` → Control Plane `/internal/tenants/{id}/policy`.
