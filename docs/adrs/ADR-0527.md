# ADR-0527 — Schema Compatibility Mode: `FULL_TRANSITIVE` (`BACKWARD` Insufficient for Rolling Deploys)

## Context

Earlier documentation stated `BACKWARD minimum` as the schema compatibility mode. `BACKWARD` is the Confluent/Apicurio default but is **insufficient for ChaosForge's rolling deploy requirements**.

---

## Decision

**Schema compatibility mode = `FULL_TRANSITIVE` for all ChaosForge canonical topics.**

---

## Why BACKWARD Is Insufficient

| Compatibility Mode | New consumer reads old schema | Old consumer reads new schema | Safe producer-first deploy | Safe consumer-first deploy | Safe rollback |
|---|---|---|---|---|---|
| `BACKWARD` | ✅ | ❌ | ❌ | ✅ | ❌ |
| `FORWARD` | ❌ | ✅ | ✅ | ❌ | ❌ |
| `FULL` | ✅ | ✅ | ✅ | ✅ | limited |
| **`FULL_TRANSITIVE`** | ✅ (all versions) | ✅ (all versions) | ✅ | ✅ | ✅ |

With `BACKWARD` only:
- If a new producer deploys first (common in CI pipelines), old consumers cannot read the new schema → decode errors during the rollout window.
- Rollback requires deploying the old producer again — which writes the old schema that the new consumer may have already migrated past.

`FULL_TRANSITIVE` checks compatibility against **all registered versions**, not just the latest. This means any consumer at any registered version can read any producer at any registered version. Rolling deployments in any order are safe. Rollbacks are safe.

---

## Practical Constraints

`FULL_TRANSITIVE` requires stricter schema evolution discipline:

| Operation | `BACKWARD` | `FULL_TRANSITIVE` |
|---|---|---|
| Add field with default | ✅ | ✅ |
| Remove field with default | ✅ | ✅ |
| Add field without default | ✅ (new consumers only) | ❌ — must have default |
| Remove required field | ❌ | ❌ |
| Rename field | ❌ (use aliases) | ❌ (use aliases) |
| Change field type (widening) | ✅ | ✅ |
| Change field type (narrowing) | ❌ | ❌ |

**The `FULL_TRANSITIVE` constraint is enforced at Apicurio registration time** — the registry rejects a schema update that would violate it. This means incompatible changes fail the CI deploy pipeline, not silently corrupt consumers.

---

## Schema Migration Protocol (Expand-Contract)

1. **Expand**: add new optional field with `"default": null`. Deploy. All existing consumers ignore the new field. All existing producers do not write it. Compatible in both directions.
2. **Backfill** (if needed): populate the new field for live data outside any lock.
3. **Dual-write**: producers write both old and new representation for one release.
4. **Cutover**: drop old field from producers (still registered in schema; consumers still tolerate its absence via default).
5. **Drop**: after all consumers confirm they do not read the old field, remove from the schema registration.

Each step is independently reversible. No single long migration transaction. No DDL that locks `outbox` under live traffic.

## Configuration

```yaml
# Apicurio Registry subject configuration (applied via Gradle plugin at bootRun/deploy)
schema.registry.compatibility: FULL_TRANSITIVE

# Per-subject override if a topic genuinely needs weaker compatibility (requires ADR)
# Applies only to explicitly listed subjects
```

CI gate: the Gradle build runs `avro-schema-compatibility-check` task before any publish. A schema update that fails `FULL_TRANSITIVE` breaks the build — not a runtime consumer failure.
