# ADR-0536 — Authentication Is Not Authorization on Internal & Operator Surfaces

| Field | Value |
|---|---|
| **ID** | ADR-0536 |
| **Status** | ACCEPTED — implemented (gateway policy feed on a CN-scoped internal endpoint; operator-role kill switch) |
| **Date** | 2026-07-13 |
| **Reversal cost** | LOW (additive authorization + one endpoint; no wire/schema change) |
| **Deciders** | Principal Engineering |
| **Depends on** | ADR-0532 (per-peer `/internal` CN scoping), ADR-0524 (JWT re-verified at CP/Exec), ADR-0504 (two-level cache) |

---

## Context

An architecture audit surfaced two places where a request was **authenticated** but not **authorized**,
and one where the authentication itself was missing on the real path.

**H1 — the gateway tenant-policy feed was unauthenticated, so per-tenant rate limits never applied.**
The gateway's L1 policy cache loaded from CP `GET /v1/tenants/{id}` with **no** credential. That path is
JWT-guarded (ADR-0524), and the cache refresh runs outside any user-request context, so there is no JWT
to send — every load returned 401. The loader's `onErrorReturn(TenantPolicy.defaultFor(...))` then
silently handed **every** tenant the default policy (600/min). The configured per-tenant limits were dead
code, and nothing observed the failure. This is the mirror of the ADR-0532 problem: the gateway, like
exec, needs to read CP over a **process-authenticated** channel, not a user-JWT one.

**M2 — the kill switch was authenticated but not authorized.** `POST/DELETE /internal/kill-switch` (C19)
is a **global** control: engaging it aborts every in-flight run across all tenants. The exec
`SecurityConfig` gated it with `anyRequest().authenticated()`, so **any** valid tenant JWT could trip a
fleet-wide halt. Exec also had no `@EnableMethodSecurity`, so no method-level check compensated.

## Decision

1. **Gateway policy feed moves to a peer-scoped internal endpoint.** New CP
   `GET /internal/tenants/{id}/policy` returns a minimal projection (tenant id + rate limit — least
   disclosure on a peer-asserted path). The gateway's `ControlPlaneClient.fetchTenantPolicy` calls it
   instead of `/v1/tenants/{id}`, over the same internal-mTLS channel the gateway already uses. Under the
   `mtls` profile the CP `InternalMtlsSecurityConfig` (ADR-0532) is extended from single-peer to
   **per-path** cert-CN scoping:
   - `/internal/rule-sets/**` → the exec cert CN (`internal-peer-cn`);
   - `/internal/tenants/*/policy` → the gateway cert CN (`internal-gateway-cn`);
   - any other `/internal` path → `denyAll` (fail-closed — a new internal endpoint must be explicitly
     mapped to its peer, which is the intended prompt to make the peer-binding decision).

2. **Failure is observable, not silent.** The policy fetch stays fail-open (architecture specification posture) but now
   WARNs and increments `chaosforge.gateway.policy_load{outcome}` (success / fallback). A broken feed is
   an alertable condition (`TenantPolicyFeedDown`, ADR-0537), not an invisible default.

3. **Operator endpoints require a role.** The exec kill switch requires `hasRole("OPERATOR")`; a plain
   tenant token is 403. Roles come from the JWT `roles` claim mapped to `ROLE_*` via an explicit
   `JwtAuthenticationConverter` (the default `SCOPE_*` mapping would silently never match — the
   gateway/CP issue `roles`). Any future blast-radius-affecting operator endpoint must be role-gated the
   same way.

## Alternatives Considered

- **Forward a service JWT from the gateway to `/v1/tenants/{id}`.** Requires minting and rotating a
  machine token for a read the mTLS channel already authenticates at the process level; it also leaves
  `/v1` (a user API) serving an internal consumer. Rejected in favour of a purpose-built internal path,
  consistent with the exec rule-set read. (A service-JWT upgrade to make the internal **tenant** value
  cryptographic rather than peer-asserted remains the ADR-0532 §3 follow-up.)
- **Keep the `/v1` fetch but relax it to `permitAll`.** Exposes tenant records unauthenticated on a
  public-style path. Rejected outright.
- **Loosen `/internal` to "any internal-CA cert."** Reopens the ADR-0532 cross-tenant read (any peer
  could pass an arbitrary `tenantId`). Rejected — the whole point is per-path peer binding.
- **Kill switch: `@PreAuthorize` on the controller.** Equivalent effect, but exec had no method security
  enabled and the filter-chain rule keeps all authorization decisions in one place (`SecurityConfig`).
  Chose the request-matcher rule for locality.

## Consequences

- Per-tenant rate limits are actually enforced; a dead policy feed is visible and alertable.
- A global operator control can no longer be tripped by an ordinary tenant token.
- The `/internal` surface is fail-closed: unmapped internal paths 403 under `mtls` until explicitly bound
  to a peer — deliberate friction that forces the peer-binding decision.
- Proven by `ControlPlaneClientPolicyTest` (Docker-free: internal path is called; 401/500 fail open **and**
  count the fallback — the exact regression that hid H1), `InternalMtlsAuthorizationIT` (gateway cert
  reaches the policy path, exec cert is 403, and vice-versa for rule-sets), and `KillSwitchAuthorizationIT`
  (operator engages; tenant is 403; no token is 401).
- Enforcement constraints recorded in `mTLS security policy` (per-path CN table; operator-role
  requirement).
- Residual: the internal **tenant** value on these paths is still peer-asserted, not JWT-bound (ADR-0532
  §3). Dev/tests keep `/internal` `permitAll` (no `mtls` profile), unchanged.
