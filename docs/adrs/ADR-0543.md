# ADR-0543 — MCP Server Embedded in the Control Plane, Dual-Audience Auth Boundary

| Field | Value |
|---|---|
| **ID** | ADR-0543 |
| **Status** | ACCEPTED — implemented |
| **Date** | 2026-09-27 |
| **Reversal cost** | MEDIUM (one Spring AI starter, one security chain per service, one CP Kafka consumer; no Avro wire-schema change, no domain-data migration — `V12` only adds the `run_projection` cache table) |
| **Deciders** | Principal Engineering |
| **Depends on** | ADR-0524 (tenant identity from verified JWT), ADR-0510 (cross-tenant → 404), ADR-0518 (AI determinism boundary), ADR-0536 (authentication is not authorization), ADR-0511 (free-tier topology: Gateway is the public boundary) |

## Context

ChaosForge's portfolio pairing gives RPE a RAG surface and ChaosForge an MCP surface: an agent should be
able to read ChaosForge and, for one narrow action, operate it. That surface must inherit every existing
tenant-isolation and authorization guarantee rather than become a second, weaker front door.

## Decision

**Placement.** MCP is embedded in the **Control Plane** (`spring-ai-starter-mcp-server-webmvc`,
`STATELESS` protocol) and reachable only through the **Edge Gateway** at `POST /mcp`. The Gateway is a
protocol-unaware byte pass-through — it authenticates, rate-limits per tenant (plus per operate-scoped credential, see Amendments), and wraps the call in its
own circuit breaker + bulkhead (`gateway-mcp`, isolated from `gateway-cp`); it never parses JSON-RPC. The
Control Plane *is* the MCP server: protocol, tool registry, tool execution, tenant-scoped business logic.
A standalone adapter service was rejected (it would duplicate tenant resolution and service access CP
already owns); `STREAMABLE` was tried and reverted (no tool needs server-initiated messages, and its
session store has no story for CP horizontal scaling).

**MCP is a separate OAuth resource.** Gateway and CP each run a second `@Order(1)` chain matched on
`/mcp` + `/mcp/**` with its own `JwtDecoder` requiring `aud=chaosforge-mcp`
(`chaosforge.security.mcp.jwt.audience`). Isolation holds in both directions: an `aud=chaosforge` token is
rejected at `/mcp`, an `aud=chaosforge-mcp` token is rejected at `/v1`. The MCP chain reuses
`JwtTenantExtractionFilter`, so MCP requests carry the same verified `TenantContext` and `ROLE_*` as `/v1`.
Ordering was fixed before either chain existed: **auth before proxy** — `/mcp` was never reachable
without its own audience-scoped chain.

**Tool scope is a second, independent gate.** The standard JWT `scope` claim maps (allow-listed) to
`SCOPE_chaosforge.{read,operate,dlq}`; every `@McpTool` declares its own `@PreAuthorize`, enforced by an
ArchUnit rule. DLQ triage composes `hasRole('OPERATOR') and hasAuthority('SCOPE_chaosforge.dlq')` — role
and scope are independent axes (ADR-0536).

**Tools (8).** Read: `get_scenario`, `list_scenarios`, `get_rule_set`, `list_rule_sets`, `get_run_status`,
`get_dlq_triage`. Non-persistent AI authoring: `draft_scenario` (ADR-0518; gated on `operate` because it
spends inference, not because it writes). State-changing: **`start_scenario` only**, a thin wrapper over
the unchanged `ScenarioReplayOrchestrator`. Read tools delegate to the existing tenant-scoped services, so
ADR-0510 indistinguishability holds and is tested per tool.

**Excluded by design, not deferred.** `prepare_scenario_run` — the orchestrator has no prepare/start
split, and a tool minting a fresh `idempotencyKey` per call would defeat ADR-0528's at-most-once guarantee.
`mark_dlq_reviewed` — reversing ADR-0518/0542's "AI never writes triage state" would be a regression; the
watermark write stays HTTP-only and human-only. MCP also has no create-tenant/rule-set/scenario tool.

**In-band errors.** An uncaught tool exception surfaces as `HTTP 200` + `isError:true` + the raw message,
never through `ExceptionTranslationFilter`. Every tool therefore passes through only its own
verified-safe exceptions and masks anything else behind a generic message, logged server-side.

**`get_run_status` and CP's first Kafka consumer.** CP now consumes `chaosforge.scenario.results.v1`
(still producing `chaosforge.scenario.commands.v1`; it does not consume commands) into `run_projection`
(`V12`), a rebuildable read cache — never DLQ-routed. A decode failure is permanently skipped; a transient
persist failure is retried in place by the container (`DefaultErrorHandler`, 1 attempt + 2 retries, 2s
apart), then counted and skipped. Both permanent-loss paths feed `RunProjectionFailureRateHigh`. No schema
evolution is involved — Exec's producer and `ScenarioRunResult` are unchanged.

**Discovery on the Gateway.** RFC 9728 Protected Resource Metadata
(`GET /.well-known/oauth-protected-resource`) and the `WWW-Authenticate: Bearer resource_metadata=…` 401
header are served by the Gateway, the actual public boundary. Spring Security's native support is
servlet-only, so both are hand-built on the WebFlux side. Topology, config and verification:
`docs/chaosforge-mcp-design.md`.

## Alternatives Considered

- **Standalone MCP adapter service** — duplicate wiring, no isolation gain. Rejected.
- **`STREAMABLE` transport** — session state with no present need. Built, reverted.
- **Widen the existing audience validator instead of a second chain** — turns a resource-boundary decision
  into a config value and makes every `/v1` token valid at `/mcp`. Rejected.
- **`prepare_scenario_run` / `mark_dlq_reviewed`** — see Decision.

## Consequences

**Positive:** the MCP surface inherits ADR-0510/0524/0536 by construction; the state-changing surface is one
tool; the audience boundary is proven in both directions live and in tests.

**Negative:** two audience boundaries per service is more security configuration to keep straight; MCP
errors bypass the HTTP status channel, so catch-and-mask is a per-tool discipline with no framework
backstop; `run_projection` is a second, eventually consistent view of run outcome next to Exec's
`scenario_run`, and a record it permanently drops stays stale.

**Lab limitation:** RFC 8707 resource-indicator-at-issuance is not applicable — the lab JWKS stub has no
token endpoint, so lab tokens are minted directly by `docker/jwks/mint-jwt.sh`.

## Amendment (2026-10-03) — per-credential request ceiling for operate-scoped `/mcp`

**Gap.** The per-tenant limiter bounds aggregate traffic but not one operate-capable credential
retrying with fresh `idempotencyKey`s. CAS + idempotency make each attempt safe, not cheap: the CAS
rejects only a stale `expectedVersion`, so a loop that re-reads the version can keep starting runs.

**Decision.** The Gateway adds a second sliding-window limit, keyed by SHA-256 of the bearer token
(`{mcp-token:<sha256>}:rate|:seq`), using the existing Lua script and 60s window. It applies to
`/mcp` requests whose authorities include `SCOPE_chaosforge.operate`. It runs before the tenant
limiter; a token rejection returns 429 + `Retry-After: 60` and does not consume the tenant bucket.
Config: `chaosforge.security.mcp.operate-rate-limit-per-token` (`MCP_OPERATE_RATE_LIMIT_PER_TOKEN`).

**What it is.** A request-rate ceiling for operate-capable credentials, not a `start_scenario` limit.
Every operate-scoped `/mcp` request counts, whatever it carries: `initialize`, `tools/list`, reads,
polling, and any HTTP method. The Gateway stays protocol-blind; no JSON-RPC parsing, no second algorithm.
The path match is exact `/mcp` under `PathPattern` semantics; `/mcp/` does not engage the token limiter.

**Key choice.** Per credential, not per `tenant:sub`: the lab mint script defaults `sub` to `lab-user`,
which would collapse every lab credential into one bucket. Consequence: a refreshed token is a fresh
bucket, so the ceiling bounds a credential, not a principal. The tenant ceiling remains the aggregate
bound while Redis is up.

**Failure mode / Observability.** Superseded by Amendment 2.

**Default.** `10` per 60s is an unmeasured lab candidate (a test used `2`). It characterises lab
clients only and is to be replaced by a value derived from measured client cadence.

**Rejected.** A Control Plane Postgres start-budget table: new schema and a second enforcement
point for a gap the existing Gateway layer already covers.

## Amendment 2 (2026-10-04) — Redis-outage behaviour, polling guidance

**Polling.** The token limiter applies only to `SCOPE_chaosforge.operate`; `get_run_status` needs only
`chaosforge.read`. Agents should poll with a read-only token, which never touches the operate budget.
A token holding both scopes shares it by design.

**Failure mode.** Limiter Redis calls carry a timeout (`chaosforge.gateway.rate-limit.redis-timeout-ms`)
and a circuit breaker (`gateway-ratelimit-redis`, no health indicator). When the token limiter's call
fails, times out, or the breaker is open, the Gateway enforces the same limit on a local per-pod fixed
window (Caffeine) and still returns 429 + `Retry-After`. The tenant limiter still fails open (ADR-0540).
The local limit is an upper bound, not exact: N pods give up to N × limit, and a fixed window can admit
up to 2 × limit across a boundary. The CAS rejects only a stale `expectedVersion`, so this ceiling, not
the CAS, bounds run volume. ADR-0540's rejection of a per-pod limiter as the primary limiter stands;
it is used here only as an outage fallback.

**Observability.** `chaosforge.gateway.rate_limit` now carries `limiter=token|tenant`. Token-path Redis
failures count `outcome=local_fallback`; tenant-path failures keep `fail_open`, so `RateLimitFailingOpen`
still fires on an outage. One `allowed` is counted per admitted request, by the tenant limiter.

**Rejected.** Fail-closed 503 for operate tokens (turns a Redis outage into a write-path outage);
tool-aware limiting at the Gateway (needs JSON-RPC parsing, breaks protocol-blindness); `azp`+`sub`
keying (deferred until a real token endpoint exists; a refreshed token still gets a fresh bucket).
