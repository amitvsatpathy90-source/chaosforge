# ADR-0509 — Three-Layer Tenant Isolation

**Status:** ACCEPTED
**Date:** 2026-05-20
**Reversal cost:** MEDIUM
**Owner:** Principal Engineering

---

## Context

ChaosForge is multi-tenant. A tenant must never read, write, or execute resources belonging to another tenant — even if they know the resource's UUID. This must be enforced structurally, not by convention. A single enforcement point (e.g., controller only) is insufficient: a bug or a direct service-to-service call bypassing the controller would silently expose cross-tenant data.

---

## Decision

Tenant isolation is enforced at **three independent layers**. Each is necessary; none alone is sufficient.

**Layer 1 — Edge Gateway filter:** JWT validated; `tenant_id` extracted from claims and written to Reactor Context. Requests without a valid JWT are rejected at the gateway with `401`. This is the outermost defence.

**Layer 2 — Service security filter (CP + Exec):** `TenantContext` ThreadLocal populated from the JWT `tenant_id` claim (re-validated at each service). Method-level `@PreAuthorize` checks that the `tenant_id` in the JWT matches the resource's owner.

**Layer 3 — Repository predicate:** **No `findById(UUID)` method exists on any tenant-scoped repository.** Every query method accepts `tenant_id` as a mandatory parameter. Example:

```java
// Forbidden — returns any row regardless of tenant
Optional<Scenario> findById(UUID id);

// Required — tenant_id is a mandatory predicate
Optional<Scenario> findByIdAndTenantId(UUID id, UUID tenantId);
```

This is enforced by code review and ArchUnit rule: no Spring Data method named `findById` on any repository in a tenant-scoped package.

---

## Alternatives

**Controller-only enforcement:** A direct inter-service call, a background job, or a test helper bypassing the controller silently exposes cross-tenant data. Single layer is insufficient. Rejected.

**Row-level security in Postgres:** Correct and complementary but not a substitute — it requires the application to set the session-level tenant context on every connection, which is error-prone with connection pooling. RLS is the production upgrade path; not implemented in lab. Rejected as sole control.

---

## Consequences

**Positive:**
- A cross-tenant data leak requires bypassing three independent checks simultaneously — structurally difficult.
- Repository signature communicates the tenant-scoping invariant to every developer who reads it.
- Layer 3 is the last defence against internal callers (background jobs, integration tests, admin endpoints).

**Negative:**
- Repository methods are more verbose — every query carries `tenantId`.
- `TenantContext` ThreadLocal must be populated before any repository call; missing population silently causes `WHERE tenant_id = null` which returns zero rows, not an error. Mitigated by a `TenantContextMissingException` thrown by `TenantContext.require()`.

---

## Failure Modes

| Failure | Detection | Mitigation |
|---|---|---|
| `findById` without tenant added by a developer | ArchUnit rule: `noMethodsNamed("findById").inPackage("..repository..")` | CI hard fail |
| `TenantContext` not populated before repo call | `TenantContext.require()` throws `TenantContextMissingException`; surfaces as 500 | Integration test: call repo without populating context; assert exception |
| JWT `tenant_id` claim missing or tampered | Layer 1/2 rejects with 401/403; Layer 3 sees empty context → exception | Defence-in-depth; any single layer catching it is sufficient |

---

## Implementation Notes

- `TenantContext`: `ThreadLocal<UUID>` with `set(UUID)`, `require()` (throws if null), `clear()` (in filter finally block).
- ArchUnit rule: in `ControlPlaneArchTest` and `ExecutionServiceArchTest`.
- Cross-tenant access → `404` (ADR-0510); not `403`.
