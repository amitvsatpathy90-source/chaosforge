# ADR-0529: DLQ Retry Consumer — Fresh-message_id Republish over Step-Level Idempotency

**Status:** Accepted
**Date:** 2026-06-28
**Depends on:** ADR-0508 (failure taxonomy), ADR-0523 (consumer pipeline phases), ADR-0528 (outbox relay semantics, fencing token)
**Reconciles:** `DLQ policy specifications` (retry-consumer "preserve original message_id" wording — corrected here)
**Deciders:** Principal Engineering

---

## Context

`DLQ policy specifications` specifies a DLQ retry consumer: a separate consumer group that republishes the two
**replayable** reasons (`INFRA_TRANSIENT`, `STEP_TIMEOUT`) from `<command-topic>.DLQ` back to the main
topic with exponential backoff, and parks the rest as `RETRY_EXHAUSTED`. The component was deferred at
build time. Implementing it surfaced a correctness fork that the rule text got **wrong**.

The rule text says: *"Carry an attempt counter (`x-dlq-attempt`) and the **original** message_id so the
inbox dedup at the Execution Service still suppresses any duplicate business effect."*

That is unsafe **given the implemented pipeline** (ADR-0523):

- The consumer claims the inbox in **Phase 1** (`ClaimPhase`, a short `@Transactional`) and **commits
  it** before step execution.
- Step execution runs in **Phase 2** with **no surrounding transaction** — deliberately, so slow
  outbound HTTP never holds a DB transaction open (DB-hygiene: no network calls inside a tx).
- Therefore a Phase-2 failure (`INFRA_TRANSIENT` / `STEP_TIMEOUT`) leaves the **inbox row committed**.

The codebase already documents the consequence, in `RunLogDao.markStaleRunsIncomplete`:

> *"its message_id is already in the inbox, so redelivery is ack-skipped — no self-heal."*

So republishing with the **original** message_id would be **deduped at the inbox and never
re-execute** — the retry would be a silent no-op, and the operator would see the DLQ drain while the
work never completed. The literal rule is a latent footgun.

The real idempotency unit is **not** the message — it is the **step**. `scenario_run_log` has PK
`(scenario_id, replay_version, step_id)`; `ExecutePhase.isStepCompleted` skips finished steps; and the
outbound `Idempotency-Key` is the **stable** `scenario:replay_version:step_id` (independent of
message_id). Completed steps are durable across attempts; only the failed/unrun step needs to re-run.

---

## Decision

The retry consumer republishes a replayable record to the main topic with a **fresh** UUIDv7
`x-message-id`, preserving everything else (Avro `value`, partition key, `x-replay-version`,
`x-rule-set-id`, `x-rule-set-version`, `x-tenant-id`), incrementing `x-dlq-attempt`, and dropping
`x-dlq-reason`.

Correctness rests on three existing invariants — the retry rides on them, it does not add new ones:

| Layer | Mechanism | Effect on a republished retry |
|---|---|---|
| Inbox | dedup on `message_id` | **fresh** id ⇒ passes; the retry actually re-enters execution |
| Fence (ADR-0523) | stale iff `incoming < max_seen` | same `replay_version` ⇒ **equal**, passes; a newer replay since issued ⇒ correctly fenced out as `FENCING_VIOLATION` |
| Step (ADR-0523) | `run_log` PK + `isStepCompleted` + stable `Idempotency-Key` | completed steps skipped; only the failed step re-runs; target dedupes via the unchanged key |

This is **layered idempotency**: a fresh id at the Kafka/inbox layer, a stable key at the
target/step layer. The two layers answer different questions and must not be conflated.

### Disposition table

| `x-dlq-reason` on the DLQ record | Decision |
|---|---|
| `INFRA_TRANSIENT`, `STEP_TIMEOUT`, `nextAttempt ≤ max` | Republish to main (fresh id, backoff + jitter) |
| `INFRA_TRANSIENT`, `STEP_TIMEOUT`, `nextAttempt > max` | Park to `.DLQ` as `RETRY_EXHAUSTED` (terminal) |
| `SCHEMA_INVALID`, `FENCING_VIOLATION`, `STEP_FAILED`, `RETRY_EXHAUSTED` | Skip (ack past it; humans only) |
| `null` / unknown | Skip (fail closed — never guess replayable) |

Widening the replayable set is **forbidden without a new ADR** — replay safety is exactly the
step-idempotency argument above; a non-idempotent reason would double-apply.

## Implementation Contract

- **`DlqRetryPolicy`** — pure, no I/O. `decide(reason, currentAttempt) → RetryDecision` (sealed:
  `Skip | Republish(nextAttempt, backoffMillis) | Exhausted`). Backoff is a deterministic capped
  exponential ceiling (`base·2^(n-1)`, clamped to `cap`), computed by repeated doubling (overflow-safe).
- **`DlqRepublisher`** — rebuilds the `ProducerRecord`. `republishToMain` (fresh id, `+1` attempt,
  reason dropped) and `parkExhausted` (to `.DLQ`, reason = `RETRY_EXHAUSTED`, id kept for forensics).
  Bounded synchronous send (`get(10s)`); a send failure throws `DlqRepublishException` so the consumer
  does **not** ack.
- **`DlqRetryConsumer`** — `@KafkaListener` on `${command-topic}.DLQ`, group `dlq-retry`, returns
  `void`, manual ack **after** the action. Backoff sleep applies **full jitter** in `[0, ceiling]`;
  the ceiling is bounded below `max.poll.interval.ms` so the repair lane never self-triggers a rebalance.
- **Container factory** `dlqRetryListenerContainerFactory` — manual ack, **no**
  `DeadLetterPublishingRecoverer` (a failed republish must not chain to `.DLQ.DLQ`); a thrown
  `DlqRepublishException` is redelivered by a `FixedBackOff(2s, ∞)` — the repair lane keeps trying
  while the broker is unhealthy; nothing is committed, so nothing is lost.

### Config (`chaosforge.dlq.retry.*`)

```yaml
group-id: dlq-retry
max-attempts: 5
base-backoff-ms: 1000
cap-backoff-ms: 30000      # bounded well below max.poll.interval.ms (300000)
```

### Observability

`chaosforge.dlq.retry{outcome=republished|skipped|exhausted, dlq_reason}` — low-cardinality, **never**
a `tenant_id` tag. A rising `exhausted` rate ⇒ a target is down past the budget (alert surface). The
`dlq-retry` group's consumer lag (via the existing `MicrometerConsumerListener`) is the DLQ-depth SLI.

## Consequences

**Better:** replayable failures actually recover (the literal rule would have made them no-ops);
self-healing for transient target outages; a terminal `RETRY_EXHAUSTED` parking state; the DLQ never
stalls (hard poison is acked past). Cleanly testable: the policy and republisher are covered with zero
broker (`DlqRetryPolicyTest`, `DlqRepublisherTest`).

**Costs:** blocking backoff on the repair-lane listener thread (bounded < `max.poll.interval.ms`);
at-least-once republish can place two fresh-id copies on the main topic (both absorbed by step
idempotency); a re-issued newer replay turns a stale retry into a `FENCING_VIOLATION` (correct, but it
consumes one attempt first).

## Residual Risks (explicit)

1. **Step idempotency at the target is assumed, not enforced by us.** We send a stable
   `Idempotency-Key`; if the *target* ignores it, a re-run of an `INFRA_TRANSIENT` step whose first
   call actually reached the target double-applies. Out of our trust boundary — documented, not closed.
2. **Blocking backoff caps repair throughput.** One record per (jittered) backoff per partition. Fine
   for a low-volume repair lane; at high DLQ volume the scale-out path is non-blocking delay topics
   (Spring `@RetryableTopic`) or a tombstone-and-reschedule. New ADR if needed — do not silently widen.
2. **`RETRY_EXHAUSTED` is parked back on the same `.DLQ` topic.** The retry consumer re-reads it once,
   classifies it `Skip`, and acks past it — correct, but it costs one extra read per exhausted record.
   A dedicated parking topic would avoid that; deferred as not worth the extra topic in the lab.
4. **End-to-end over a real broker is now proven** (`DlqRoutingE2EIT`, Testcontainers Kafka): poison →
   DLQ `SCHEMA_INVALID`; replayable → republish to main with a fresh `message_id` + incremented attempt;
   budget spent → parked `RETRY_EXHAUSTED`; hard poison never replayed. Still not asserted end-to-end:
   that the re-delivered command re-executes *only* the failed step (the step-skip is covered by
   `ExecutePhase`/`RunLogDao` Postgres ITs, not stitched into the broker round-trip).
5. **Poison amplification is bounded only by `max-attempts`.** A mass target outage fans the whole
   in-flight set through the retry loop `max-attempts` times before exhausting. Bounded and observable
   (`exhausted` rate), but it is real load on the main topic during a wide outage.

## Options Considered and Rejected

| Option | Rejection reason |
|---|---|
| Republish with the **original** message_id (literal `DLQ policy specifications` wording) | Inbox dedups it away (claim commits in Phase 1 before execution) → retry is a silent no-op. The defect this ADR exists to fix. |
| Roll the inbox claim into the execution transaction so a failure un-claims it | Re-introduces network calls inside a DB transaction (violates DB-hygiene; ADR-0523 split the phases precisely to avoid this). |
| Auto-replay from the main consumer | Forbidden — the retry consumer is the sole republisher; manual triage otherwise. |
| Non-blocking `@RetryableTopic` delay topics now | More topics + machinery than the lab repair lane warrants; recorded as the scale-out path (Residual Risk 2). |
